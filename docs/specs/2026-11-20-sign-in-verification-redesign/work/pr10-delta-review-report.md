### B1 · The People marker acknowledges reply handling before React can settle the old update

The observer now runs through the newer DOM commit, and the old network finish is followed by a real application event. The remaining gap is the ordering of that event. The component queues `renderLookup` or `renderList` and emits the mark in `finally`. The observer can receive the mark while the DOM still shows the pending state. The driver then reads that state and releases the newer response without a barrier for the old React work.

Consider a wrong build that removes the stale-refusal branch for `reply`. It can queue `Invited` or the offset-50 rows and emit the handled mark. React can leave that update pending while the driver reads the old DOM and releases the newer reply. If React processes both queued updates together, the only committed DOM contains the newer result. Both the final assertions and the mutation observer can then pass on the wrong build. The source permits this ordering. Its occurrence in a browser run was unverified. Keep the newer reply held until there is evidence that the old generation was discarded or that its queued render has settled, and retain the observer through the newer commit.
