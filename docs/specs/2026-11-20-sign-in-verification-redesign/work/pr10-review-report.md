## Blocking

### B1. The People race can accept a stale publication

Both overlapping-reply cases end their publication observer too early. `OrganizationBrowserResponses.release()` waits for Chrome's `Network.loadingFinished`. The test then calls `readyWhen('true')`, which waits for fonts and one animation frame, and disconnects its observer before releasing the newer reply. The application still has to parse the response and handle it in the component. The later assertions see the final result. A wrong build that drops the stale-response guard can process the older reply after the observer disconnects, briefly publish `Invited` or the older page, then let the newer result overwrite it before the final assertion. D1 and the Organizations row require the browser to catch that publication. Keep the publication observer through a causal witness that the application handled the old result and committed the new one. The network terminal event alone leaves the application interval unobserved.

### B2. D4 loses assertion identity when two matchers share a line

The AST resolver finds a particular matcher but emits only its source file and line. The stack reader parses both line and column and discards the column before the verdict compares addresses. If the intended matcher stays green and another matcher on the same line produces the same assertion text, the failed case count, single error, path, line, text and exit status can all match. Green after restore would still complete this false sensitivity result. The unit test rejects a matcher on the next line and leaves the same-line case uncovered. Require a source-mapped location or equivalent identity that distinguishes the two sites.

### B3. Forced CLI sign-in can pass without ever entering the browser callback

`loginThroughNativeOwnerCli()` resolves browser completion at stdout EOF when no authorization URL was printed, even when it passed `--force-auth`. A wrong CLI that exits zero and leaves a schema-valid cache with a nonempty token without starting the authorization can satisfy the helper. The passkey case then writes `continuationPreserved: true` even though all of its browser and continuation assertions were inside the skipped callback. Restrict the no-browser success path to explicit cache reuse and make forced-auth success require exactly one completed callback.

### B4. The CLI journey can pass against source while the recorded CLI build is defective

The cold runner records the hash of `sign-in-owner-cli/dist/index.js`, but the child that drives the native authorization executes `scripts/verify-auth/owner-cli.ts`. The root import map sends that entry to `sign-in-owner-cli/src/owner-cli.ts`. The helper itself imports the built package for the cache schema, which does not establish that the built login implementation executed. A packaging regression affecting the exported login path can therefore leave the browser journey green while the runner lists the defective build as evidence. The source-entry result remains valid evidence for that entry. The delivered-build claim needs the same callback and cache observations through the built entry.

### B5. D6 cancellation can stop the page and leave its scenario alive

- Before the CLI prints an authorization URL, the helper is waiting for child exit or output and has no scenario signal. A live child that produces neither can leave `Promise.all()` pending. `onTestFinished()` aborts the page and then waits for the scenario, but the CLI helper reaches its kill-and-join cleanup only after its own operation settles. The cancelling test closes the page from inside the already-started browser callback, so it misses the pre-URL state. Express the CLI lifecycle as a closed state with distinct waiting-for-URL, browser-running and completed outcomes. The scenario's cancellation must reach the child in both pending states. `packages/sign-in-test-support/src/test-fixtures/playwright-browser.ts:27–40,143–151`, `packages/sign-in-test-support/src/test-fixtures/native-cli-proof.ts:136–181,188–214`, `packages/sign-in-test-support/src/test-fixtures/native-passkey-browser-scenario.ts:602–607`, `packages/sign-in-test-support/src/sign-in-native-browser.host.e2e.test.ts:26–34`.

Its progress observer can reject the completion snapshot after `launchProofBrowser()` returns and before `chrome = ...` assigns. The scenario then closes `chrome?.close()`, which has no browser to close. The signal listener can close the page, but the browser and context close live in `close()`. The harness acquisition already uses `observeNativeAcquisition` to retain the resource before completion logging. ## Should-fix

### S1. Add passkey can move after the hit test and lose the trusted click

The mounted registration readiness predicate requires an enabled button. It does not require the passkey list query to settle. The real manager can add the `No passkeys yet.` paragraph above the button when that query resolves. The driver measures and hit-tests inside one evaluation, then issues `page.mouse.click()` in a separate command. A render between those commands can shift the button far enough that the recorded click misses. The registration trace records the actual target and trust bit, but the verdict waits for the verification response or a manager alert. A missed click produces neither and can stall before `generate-register-options`. The driver fixture forces the move during `getBoundingClientRect()` before `elementFromPoint()`, so its green result cannot exclude the later gap. Fail the scenario on a trusted click that misses the intended control, or have the driver tie the input to a stable target through dispatch.

This fits the commissioned symptom for `passkey no-user-verification on cloudflare`. Enrollment is shared and occurs before the no-UV branch. The source establishes a possible ordering. The named run's click target and list-query completion were not inspected.

A build can suppress the actual refusal notice, render an empty or unrelated toast, and pass while the user sees no explanation of the refusal. Observe a visible error caused by this attempt. ### S3. D8 names both hosts but leaves the host evidence outside the verdict

The browser test files name Node and Cloudflare explicitly and the fixtures pass `host` into the harness. The host's resolved value is separately available as `signInHost`. The current source routes both variants explicitly. Assert the host witness before crediting each browser case. The fixture-only click and Enter tests correctly need no host matrix.
