Verification redesign Plan

Sign-in verification redesign

Keep the verification recipe that PR #9 rewrote: the short verify-auth skill with four journeys and a script for each. Throw away the browser machinery underneath it, which is our hand-written Chrome DevTools client, process groups, abort registry and acquisition state machine. A browser library takes its place, chosen by the running spike. Every claim gets checked at the cheapest place where it can actually break. The deployed app is the one place we have never checked, and it becomes a named journey that stays open until staging exists.

Supersedes docs/specs/2026-11-19-sign-in-verification-script/design.html. PR #9 does not merge.

What went wrong

  • A false premise. The B1-B and B1-C verification designs, which I wrote, chose raw DevTools over Playwright ("No Playwright, no timers"). "No Playwright" was never the owner's rule; the only rule is no wall-clock timers in tests. The owner said so again on 20 Nov ("i dont fuckign say not playwright", "i said no wall clock tiemrs"), and that ruling replaces the CDP choice. So we wrote a DevTools client (3,475 lines with its tests), and owning it meant owning Chrome's start and shutdown. That produced the B1-C Enter-key hang and every PR #9 race fix.
  • Verification turned into test-of-tests. The 14 security checks (break the code on purpose, then expect a named test to go red) became the main event, with an AST anchor and a stack-path decoder. That is a sensitivity check on our tests. It says nothing about whether the product works.
  • The deployed boundary has no entry in the recipe. BG already plans staging proof (SO15, SO16), and main's skill names hosted gaps. But the verify recipe has no staging journey to run or to report as open.
  • The recipe on main is hard to run cold. .agents/skills/verify-auth/SKILL.md on main does have target selection and a cold-run entry, but it sits inside a long block of history. PR #9's 29-line rewrite is easier to follow and is the part worth keeping. Main's B2 selections (organization statements, revision fences) must keep a route (D7).

Decisions

D1. One browser driver, owned by a library

The spike (running on Sunclaw) builds the passkey journey twice and recommends one:

  • A: Vitest browser mode with the Playwright provider on Chromium. One runner. cdp() gives the virtual authenticator. The open question is whether a test can follow full-page navigation and redirects to our host, because test code runs inside Vitest's iframe. A custom BrowserCommand with the Playwright context is the escape hatch.
  • B: the Playwright library driven from our existing Vitest host tests. Still one runner (Vitest). Playwright launches and closes Chromium.

Pass criteria for the choice:

  1. it follows full-page redirects;
  2. it drives the virtual WebAuthn authenticator;
  3. every wait is an event, with library timeouts at 0;
  4. Chromium starts and stops through the library;
  5. it gives the same result 5 out of 5 times on Sunclaw;
  6. it can observe what our retained tests depend on: hold and release a real response, order two live replies, read a real response body and HttpOnly cookie across navigation, trusted click and Enter, and the real CLI handoff (a small library-owned DevTools session is acceptable);
  7. a wait whose event never arrives has a defined cancellation that closes the browser, harness and CLI child;
  8. Chromium installs and is identified the same way on Sunclaw (macOS) and Linux CI;
  9. it needs the least code of ours.

Owner decision (20 Nov): use A, Vitest browser mode with the Playwright provider on Chromium, wherever it meets the criteria. For any interaction it cannot meet, use the Playwright library for that part only. The spike report says which interactions those are. The plan as a whole is approved.

Spike result (20 Nov, Sunclaw, main 7e32e00e, both hosts, 5 runs each): B, the Playwright library from Vitest Node tests. Browser mode cannot host the journey. Our pages send frame-ancestors 'none', so navigating Vitest's iframe to the app is blocked (ERR_BLOCKED_BY_RESPONSE), and the CSP stays as it is. Browser mode works only by driving a separate page with Playwright from a Node command, plus extra setup and a 10 s shutdown hang on every run (about 20 s per run, against about 10 s for B). All six interaction probes passed with B. Under the owner's rule, the journeys use the Playwright library. Wait correction: the spike used 8 s event deadlines; S1 sets every wait to timeout 0 and catches a missing event with the causal cancellation the spike proved (page.close({ reason })). Report: Sunclaw fleet-access-runner/spike-browser-tools/REPORT.md, SHA-256 5dde7f48. Moving jsdom page tests to real Chromium is a separate decision with its own test list. The choice comes back to the owner with the spike report before anyone builds on it.

D2. Delete our Chrome machinery

On main, removed or replaced in S1: native-browser-protocol.ts and its unit test, and native-browser-page.ts and its unit tests. Their importers are dispositioned one by one (removed, ported or kept): the scenario helpers (native-passkey-browser-scenario.ts, organization-browser-*.ts, native-browser-scenario.ts), native-passkey-registration-observation and native-browser-cleanup.ts. The cleanup behaviour worth keeping is that the first error survives when evidence capture or close fails. Only in PR #9, never merged: groups, acquisition, abort worker, test-cleanup and owned-process-group. Test-only browser dependencies belong to the private sign-in-test-support package. If A needs a Node-side BrowserCommand, it is registered in that package's browser project and owned there. The browser tests (native-browser-click, native-cli-keyboard-activation, people-organization-browser, sign-in-native-browser) move onto the chosen driver and keep their assertions. An assertion is never weakened to make the move easier.

D3. Keep PR #9's recipe and drop its lifecycle rules

The new verify-auth keeps PR #9's 29-line SKILL.md structure, its journey references and the four journey scripts. It drops the process-group, late-exit and SIGTERM rules, because the library owns Chrome now. It adds the Staging sign-in row, marked as a draft with its gap, and keeps the Machine login row as future. The skill stays honest about what the local fixtures fake.

D4. Security checks: sensitivity on change, with the intended assertion identified

Keep the 14 deliberate breaks. A red counts only when it comes from the intended assertion, identified unambiguously. Same file, test name and message is not enough: the anchor test shows two neighbouring matchers (lines 37 and 38) with identical text, and only one is right. Keep an exact assertion identity (today the AST anchor plus the stack reader; a simpler mechanism only if it still rejects the neighbour). Also keep the exact case set and failure count, clean setup and teardown, and green on the same selection after exact restore and rebuild.

When they run: pnpm verify:sign-in runs the journeys only. The skill names when to run controls: a change to a guarded product path, its test, or the test oracle or driver it uses. The help text and the skill example change with the default. For the driver migration, S1 runs each control whose test moved. A red from an event that never arrived is an incomplete observation, not a catch, unless a deciding failure names the affected behaviour.

D5. Staging follows BG's approved proof

The recipe gets a Staging row that points to BG's approved observations instead of inventing its own:

  • SO15: after each staging deploy, reset, create test identities and drive every journey signed in, using the staging-only testUtils routes.
  • SO16: the four production refusals, plus one real Google or GitHub sign-in on staging per release, by the dedicated test account or by the owner with a Verifier watching.

Screenshots support a visible sign-in only when they are tied to the deployed build and an observed session. They do not prove CSP or rate limits. Deployed CSP needs the actual response policy observed. A deployed limiter is claimed only from an observed refusal with state unchanged. Passkey sign-in stays proven locally (B1-B R67), and revocation belongs to B3. Until BG's staging exists, the row is open, and no claim says the product is verified on its deployed target.

D6. Waits

Inside tests, every wait is an event: navigation, a response, a DOM-ready signal or a waitForEvent, with library timeouts set to 0. No sleeps and no polling. Vitest's existing project timeouts in vitest.config.ts are a repository setting and stay unchanged (no gate changes). They bound the verdict, but cleanup still needs its own owner: each scenario closes its browser context, harness, CLI child and armed observers on every exit path, including a failed or cancelled wait.

D7. Runner and command cutover

PR #9's entry scripts are thin wrappers over shared code. S1 lists each piece and what happens to it:

  • Kept: selection, target checkout and build, and the report with its five facts.
  • Removed: the process adapter (it uses the group helper) and the up-front Chrome requirement. The agent-only journey needs no browser.
  • Replaced: the assertion resolver, as D4 describes.

The root command and import cut over from main's scripts/verify-auth/verify-auth.ts → auth-verification-cli.ts. Main's B2 selections (organization, revision-fence) and their evidence flags keep a route in the new recipe. Retiring them would need the owner. The cold pass proves that the four entries and the aggregate use the declared source and build, run the exact selected host cases, and report skips and cleanup accurately.

D8. Discovery, host matrix and CI

Today CI runs the e2e-host project once, with no SIGN_IN_TEST_HOST matrix. The native sign-in test parameterises both hosts itself, but the organization browser scenarios default to Cloudflare. S1 defines the Vitest project and file suffix for browser tests, makes each browser scenario run on both hosts explicitly (no environment default), and installs and identifies Chromium on Linux CI and on Sunclaw. Changing ci.yml or adding a CI step is a gate change and goes to the owner first. One deliberately failed run is observed through cleanup and private evidence retention.

Structure

  • Package: the browser adapter lives in packages/sign-in-test-support/src/test-fixtures/. It launches a context, adds a virtual authenticator, opens a page on a harness origin, and exposes the interaction seams in D1: response hold and release, response and cookie reads, trusted input. The scenario fixture owns the journey; the harness owns routes and storage. No other package depends on it.
  • Seams: the harness (startLocalAuthHarness) stays the only way a host starts. The driver only gets an origin.
  • State: no lifecycle state machine of ours. The library's context close is the single browser shutdown. The scenario owns the order of closing browser, CLI child and harness, and the first error survives.

What stays unverified after this redesign

  • A deployed app, real Google, a physical authenticator, and real Cloudflare counters across locations: open until staging.
  • Machine login journeys: they come with B3.
  • Chromium install and runtime on Linux CI: not yet run (needs a ci.yml step, owner first).
  • Public sign-out: /sign-out answers 404 on main. That is a product gap, handled with the navigation and Me work, not in S1.
