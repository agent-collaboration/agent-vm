## Blocking

### B1. D4 can count a red from the wrong assertion

The existing assertion-anchor unit test supplies the same file, test name, failure count, exit code and assertion text for two different locations. It accepts the intended matcher at line 37 and rejects the neighboring matcher at line 38. D4’s proposed rule accepts both. That counterexample is an assertion inside the selected test, so filtering out suite setup failures alone cannot fix it. The AST resolver gives the expected matcher identity and the stack reader supplies the observed one. Either implementation can be simplified if the replacement still identifies the intended assertion unambiguously. Preserve the neighboring-assertion rejection, exact case set and failure count, clean setup/teardown, and green on the same selection after exact restore and rebuild. See `design.html:87–88`; `PR9 scripts/verify-auth/verification-assertion-anchor.unit.test.ts:21–53`, `verification-assertion-anchor.ts:11–16,46–53`, `verification-decisions.ts:120–129,174–215`, `verification-runner.ts:393–423`.

### B2. The browser migration needs the seams that produce the real observations

A launch/context/virtual-authenticator/open-page wrapper leaves several retained assertions without a driver. The chooser test holds the real response after the server writes the session, reads that session, drops the response, and checks recovery from the rendered page. People deliberately orders two live replies and checks what was published. Passkey reads the real verification body across navigation, checks the HttpOnly cookie, and follows a real CLI-originated request through its original continuation into the CLI’s private cache. Replacing those interactions with canned responses, later manual navigation or synthetic DOM input can turn the journey green without exercising the failure. Have the spike establish that the chosen route can observe response-stage hold/release, cross-navigation response and cookie evidence, trusted input, and the real CLI handoff. A small library-owned CDP session can still be necessary. The fixture owns the scenario and the harness owns its routes and storage. See `design.html:64–82,106–110`; `plan.html:38–47`; `base packages/sign-in-test-support/src/test-fixtures/organization-browser-transport.ts:91–109,150–174`, `organization-browser-chooser.ts:246–285`, `organization-browser-people.ts:236–277,330–387`, `native-passkey-browser-scenario.ts:199–209,492–535,651–701`.

### B3. S1 needs an explicit runner and cutover inventory

The four PR #9 entry scripts are thin calls into shared selection, target checkout/build, runner and reporting code. The runner imports the assertion resolver and the process adapter uses the group helper. It also requires system Chrome before it examines the requested journeys, so copying the runner as written imposes a browser prerequisite on the agent-only journey. On the base, the existing entry delegates through a root import to `auth-verification-cli.ts`, which owns B2 organization and revision-fence selections, special evidence flags, and retention checks. S1 gives those selections no disposition. Keeping their files in CI alone would leave callers of the documented B2 recipe without its command and evidence. Name the runner pieces S1 ports/replaces, the root command/import cutover, and a retained route or explicit owner-approved retirement for each old selection. The cold pass should prove that the four entries and aggregate use the declared source/build and exact selected host cases, report skips and cleanup accurately, and expose the new controls default. ### B4. Browser discovery, host selection and failure cleanup are delivery requirements

S1 says both hosts go green and CI stays green, but the checked-in CI invokes the `e2e-host` project once without a `SIGN_IN_TEST_HOST` matrix. The native sign-in test parameterizes both hosts itself. The organization browser scenarios take `SIGN_IN_TEST_HOST` from the environment and default to Cloudflare. PR #9 gets both by explicitly selecting each host. A green CI status alone could therefore omit the Node organization browser case, or omit a new Browser Mode project entirely. Define the chosen project, discovery suffix, host matrix and browser installation/identity on Sunclaw and Linux CI. Preserve per-scenario cleanup of the browser owner, harness, CLI child and armed observers even when a wait fails. With waits set to zero, require a defined cancellation/cleanup route when an event never arrives. The existing Vitest timeout bounds the test verdict, and the cleanup still needs its own owner. Observe one failed run through cleanup and private evidence retention as part of the cold-run contract. See `design.html:43–46,64–79,103–110`; `plan.html:47`; `base vitest.config.ts:108–115,175–183`, `.github/workflows/ci.yml:43–70`, `.github/actions/setup-system-packages/action.yml:12–25`, `packages/sign-in-test-support/src/sign-in-native-browser.host.e2e.test.ts:6–17`, `test-fixtures/local-auth-harness.ts:238–243`, `test-fixtures/organization-browser-scenario.ts:54–67,194–231`, `test-fixtures/native-browser-scenario.ts:415–458`; `PR9 scripts/verify-auth/verification-runner.ts:168–205,474–482`.

### B5. The staging sequence cannot close the staging row as written

A screenshot of a successful path can support a real Google sign-in or a visible passkey flow when it is tied to the deployed build and an observed session. The same screenshots would still pass with an overly permissive CSP or a limiter that never refuses. CSP generation already has exact host HTTP coverage. Deployed CSP needs an observation of the actual response policy and the browser behavior it governs. Cloudflare counters need an observed refusal and state invariance, with reset and cross-location counting claimed only if directly observed. BG already calls for six scripted journeys after each staging deploy, production isolation checks, and one real Google **or GitHub** sign-in per release. B1-B R67 locates passkey sign-in proof locally. D5 needs to say whether its optional additional physical-authenticator run and revoke step supplement that scope, and who supplies the revocation oracle given B3’s separate machine-login row. Until then S2’s one screenshot run cannot graduate the row as written. See `design.html:30,57–58,90–101,113–116`; `plan.html:49,53–57`; [BG Getting in](../2026-11-02-fleet-access/deliverables/bg-getting-in.source.html#bg-proof), lines 176–201; [B1-B requirements](../2026-11-15-fleet-access-b1/b1-b-passkey/requirements.html#J5), lines 66–76; `base packages/sign-in-test-support/src/served-page-csp.host.e2e.test.ts:13–41`, `.agents/skills/verify-auth/SKILL.md:34–36`.
