Sign-in verification: one script that proves the user flows

Fleet access Lead, 20 Nov 2026 at about 00:50 UTC. This replaces how we prove sign-in work on Sunclaw. One checked-in script runs the user flows and the security checks against a commit, then prints a short verdict. It needs no hand-written packets, no record-keeping rules and no agent judgement to run.

pnpm verify:sign-in --commit <sha> runs these steps:

  1. check out that commit fresh;
  2. install and build;
  3. run each user flow in real Chrome on both hosts;
  4. run each listed security check: break the guard, expect the named test to fail, put the code back, expect it to pass;
  5. print one table with the five deciding facts.

It exits non-zero if anything is wrong. Anyone can run it: a person, me over SSH, or a runner agent. It never asks an agent to write a mutation, so there's nothing for Codex to refuse.

Why change it

  • Too much time went into proving the paperwork, not the flow. On 19 Nov about ten stops were about records: dependency fingerprints, environment names, process IDs and file checksums. None decided whether sign-in works.
  • Every run was a new hand-written JSON packet, 20–90 KB each. Writing and checking a packet cost more than running the tests. Each packet also invented its own setup scripts, and those had their own bugs: a wrong import, a launcher crash, a wrong file list.
  • The Codex runner refuses deliberate-break checks. Every one then needed a Claude agent or a relay.

Security checks (deliberate breaks)

These are kept in one checked-in file, verification/security-checks.ts. Each entry gives a file, the exact text to change, the test that must fail, and the assertion it must fail at. The script applies each one in its own temporary copy, runs that test, checks it failed at that assertion, restores the file, and checks the test passes again. Today's checks move into the file:

  • the removed-member guard (V5);
  • a failed sign-in is recorded;
  • the second factor is required when switching organization (B04);
  • the eight organization-access guards (HTTP checks 9–16);
  • the stale-reply guard;
  • both rate limiters.

What it prints

A table with one row per flow and host, and per security check. Each row shows the five deciding facts:

  1. the commit;
  2. the tests that ran, with counts;
  3. passed, or failed and at which assertion;
  4. for a security check, whether the code was restored exactly;
  5. whether anything was left running.

It also writes the same as a small JSON file and keeps raw logs only on failure.

How it gets built

  1. A Switchboard PR adds scripts/verify-sign-in.mts (TypeScript, per the repo standard for on-demand drivers), verification/security-checks.ts, a unit test for the report and pass/fail logic, and the pnpm verify:sign-in script entry. It doesn't change any CI gate.
  2. Proof: run it on Sunclaw at current main. Every flow must pass and every security check must go red, then green. Also run it once on a deliberately broken commit to show it fails.
  3. The same PR trims verify-auth guidance to point at the script.

Organizations (PR #1): its remaining proof becomes running this script at its head once the script exists. The hanging passkey test in the Chrome flows is the one open item.

Machine login (B3): its proofs move to the script as they land.
