Sign-in navigation: design

Switchboard's signed-in pages get one shell: a stock shadcn Sidebar, which opens as a Sheet from ☰ on phones, plus an organization switcher. Destinations are shown, and enforced on the server, by permission.

Phase 1 (this deliverable) ships only what is safe on today's server contracts:

  • the shell itself;
  • Me: passkeys, authenticator and recovery codes, recomposed in shadcn, with the layout-shift fix;
  • Sign out of the current session, through a sign-in-owned route;
  • People, moved into the shell.

Everything else is listed as a later phase, with the owner or contract it waits on (see Later phases).

Why it narrowed: the review found that Better Auth's native session list, revoke, invitation reject and organization delete aren't safe to open as shipped. Each needs its own server contract first. Review report.

It always applies to the person's server-confirmed active organization. A direct request to a denied page, read or action is refused with no data and no write.
N3The switcher (a DropdownMenu with a DropdownMenuRadioGroup of memberships) switches through the existing chooser readback (pages/islands/person-organization-choice.tsx:14–55). Only after the readback confirms the switch does it land on the first destination permitted there. If the switch is refused (403), the active choice is cleared, as B1-C S3 and the owner's foreign-switch decision already adopt (Better Auth crud-org.mjs:419–425). The readback then shows no active organization, and the person lands on the organization chooser (the existing choose step at /owner-ready). After a clear, every remaining live membership is choosable, including when only one remains; none is marked current or disabled. With no memberships left, it lands on the existing no-organization step. A 403 whose reply was lost reaches the same state through the readback. If the switch is unanswered, a fresh readback decides: either the old choice is still active, or the new one if it committed and the reply was lost.
N4Me: passkeys, authenticator and recovery codes, the current content, recomposed. Card/CardHeader with Add passkey in CardAction. The list goes in a reserved CardContent slot with a Skeleton while loading. Rows use Item, which replaces the hand-styled <li> at auth-ui/.../passkey-manager.tsx:72. The existing hooks, audited deletion and guarded factor operations are unchanged. Factor actions (set up or replace the authenticator, replace recovery codes, confirm a factor) open the existing factor pages unchanged. They return to /owner-ready, as on main today, and its ready state links back to /me. That keeps the form transport and island remount as they are. Folding these forms into /me is a later phase.
N5Sign out of the current session. A sign-in-owned route (POST /api/auth/switchboard/sign-out, a working name) deletes the current session through the existing fenced session-deletion path (authorization-fenced-adapter.ts:71–79,95–105). It reads back that the session is gone, and only then clears the cookie and redirects to /sign-in. Native /sign-out stays closed, because it clears the cookie even when deletion throws (Better Auth api/routes/sign-out.mjs:41–54). The contract:
  • Origin first: the route checks the sign-in origin (CSRF) itself, before any effect, with the same guard the admin forwarder uses (fleet-admin-forwarding.ts:65–81). It then resolves the session from the cookie on the server.
  • Exact absence: it verifies the cookie's signature and takes the session token from it. It looks the row up with a new store read, sessionRowByToken(token), which answers Present{id} | Absent | Unavailable. If Present, it deletes through the fenced path and reads again by token. readPersonSession can't be used for this, because it returns null for expired or unverified rows too.
  • Idempotent: if the lookup says Absent (and only Absent; Unavailable is a failure), that's success. The route clears the cookie and redirects to /sign-in. So a retry after a committed delete whose readback or reply was lost always finishes.
  • Failure: if the delete fails, nothing changes, the cookie is kept, and the person sees "Couldn't sign you out; try again".
N6People moves into the shell at /people, as the existing product island. Its reads (GET /api/auth/organization/people-list, GET /api/auth/organization/people, POST /api/auth/organization/person-membership) and their server checks are unchanged.
N7Entry without breaking setup or the CLI: the shell is entered only once the person is ready (BG's page decision: factor set up, organization chosen, no pending CLI continuation). /owner-ready keeps its current job unchanged: resuming authorization, factor and organization steps, the Fleet CLI continuation and its deadline (sign-in-http-handler.ts:231–316). Its "ready" state shows a link into the shell, not a redirect. The phase 1 readiness predicate, from stored facts and checked on every shell route (the link and any direct GET): a live verified session, and the person's factor set up and confirmed, and a confirmed active membership, and no pending continuation on the request: no authorize or client_id parameter, the actual continuation inputs, which /owner-ready validates into its internal resume. If the predicate fails, a request with no live session goes to /sign-in. Any other request goes (303) to /owner-ready, with its original query string preserved for /owner-ready's existing validation, so a continuation is never dropped. When BG lands its shared page decision, this predicate moves into it.
N8Loading a list never moves the Add passkey button, or the next persistent control on the page.
N9Components: shadcn primitives already in the shared tool-access-ui package (Sidebar, Sheet, Card, Table, Alert, Button, Skeleton, Separator, Badge, AlertDialog), plus two official Base Mira registry additions, dropdown-menu and item. Nothing is hand-built; each element maps to the inventory.
N10The existing admin page stays: /organization-admin (create workspace, workspace lookup and change records, with factor confirmation) is not retired in phase 1. The switcher links to it as "Organization admin", for owners only, until a later phase replaces each of its functions.
