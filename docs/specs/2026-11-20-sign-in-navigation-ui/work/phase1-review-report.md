## Blocking

### B1. A denied shell GET can delete a session and advance authorization revisions

`/me` and `/people` call native `getSession` with `disableRefresh: true`. In pinned Better Auth 1.7.11 the expired-row branch runs before the `disableRefresh` branch and calls `internalAdapter.deleteSession` when `deferSessionRefresh` is unset, as it is here. The composed adapter fences that delete. The request can therefore redirect to `/sign-in` while deleting the expired row and advancing the person's retained authorization revisions. That breaks the no-write rule for refused direct requests in N2. The current N7 signed-out case sends an empty cookie, which misses this branch. Use a read-only live-session acquisition for the new shell entry and cover a still-present expired row on both new GETs, observing the redirect, row and revision together.

### B2. A cross-origin 403 can come from the provider before the sign-out guard runs

The sign-out endpoint calls the shared origin guard before parsing the signed cookie, as N5 requires. The HTTP control asserts only 403, no `Set-Cookie`, and unchanged stored facts. Better Auth installs an origin middleware ahead of all endpoint handlers. Where that middleware is active, it can produce all three observations even if the endpoint guard is removed. Its test-environment skip behavior makes the two host results especially important to distinguish. The control also leaves a late guard after the token lookup indistinguishable from the required ordering. Keep the public cross-origin control and add a check that reaches the production endpoint guard, identifies its refusal, and observes that cookie and lookup processing have yet to start. Confirm that removing or reordering the endpoint guard fails for that reason.

### B3. The permission checks can pass if authorization uses a different organization’s role

The allow and deny fixtures use different people and the same organization. The positive case uses its owner. The negative case uses a person whose sole membership is `member`. The switch case uses the same owner role in both organizations. A wrong build that grants People whenever the person owns any organization can satisfy the full matrix. The browser also never goes Back to a formerly allowed `/people` after a switch that removes that permission. Exercise one person with an owner membership and a plain membership, hold the active organization to the plain one, and check the hidden links and refused direct page, list and lookup. Include a direct checked read naming the inactive owner organization and Back from the owner-to-member switch. Assert the server outcomes and absence of returned People data.

## Should fix

### S1. Sign-out proof never presents a valid cookie for a non-live row

The live-success and faulted-lookup cases are meaningful, including the same-cookie retry after a committed delete. They leave the reason for N5’s exact token lookup untested. An implementation that routes expired or unverified-but-present rows to an already-signed-out outcome can escape these cases. The suite also has no distinct control for a cookie whose signature fails validation. Cover a signed cookie with an expired row still present and observe the fenced delete before cookie clearing. Check a rejected signature against an unchanged row, revision, and cookie response.

Anchors `packages/sign-in-test-support/src/test-fixtures/sign-in-navigation-sign-out.ts:72`, `:132`, `:151`, `:175`, `packages/sign-in-core/src/storage/person-session-store.ts:113`, `:144`, and `packages/sign-in-core/src/better-auth/sign-in-sign-out.ts:35`. [N5](../design.html#N5)

### S2. The switch proof observes the eventual destination and misses premature navigation

The N3 test holds the `set-active` response after the server has executed it, then checks the final document. `afterNavigation` captures an event that can occur while the action is still running. An implementation that starts the destination GET before delivery or loss of the held reply can pass if the switch commits before the GET reads it. Record the destination request relative to the held reply's settlement, with an assertion at that boundary on the committed and refused paths. The zero-membership branch also checks that *some* session row has a null choice. Use the browser session's exact row, as the earlier cases do, so another session cannot satisfy that assertion.

### S3. The readiness and continuation inputs are only partially varied

The N7 browser fixture starts with the owner enrolled and an organization already created. It then signs the same owner in again and reaches the confirmation step. That covers confirmation pending. A build that overlooks first enrollment can pass those assertions. The N3 post-clear case separately covers a missing active choice while the factor is confirmed. The continuation case tests `authorize` only on `/me` and raw `client_id` only on `/people`, with the actual CLI callback driven from `/people`. The shared predicate handles both today. The checks would still pass on a route-specific regression that preserved only the respective tested form. Exercise fresh owner setup through enrollment and organization selection, and pair each route with both continuation forms for exact `Location` equality. One real callback for the same attempt still provides the composed continuation observation.
