The proposed account and organization routes need explicit server contracts, and the release sequence needs to preserve setup and existing admin behavior.

## Blocking

### B1. The proposed session list and revoke routes cannot enforce the token boundary as written

`design.html:85,93–95` proposes adding the native routes and marking Current with a safe session ID. Native `list-sessions` returns an array of parsed sessions that includes `token`. Switchboard’s redaction helper operates on a single `{session}` object and its after-hook runs on `/get-session` and `/passkey/verify-authentication`. It would leave the list array untouched even if invoked there. Native `revoke-session` accepts a token and returns `status: true` even if the target was absent or belonged to somebody else. The pinned `ActiveSession` example compares tokens for Current and passes the session to its revoke hook. Native `sign-out` clears the browser cookie even when session deletion throws. A successful response or a vanished row in the UI cannot establish revocation. Evidence `session-read-without-token.ts:13–21`, `provider-configuration.ts:261–280`, Better Auth `api/routes/session.mjs:347–368,377–415`, `db/schema.mjs:52–54`, core `db/get-tables.mjs:105`, `api/routes/sign-out.mjs:41–54`. [Provider hook](https://github.com/agent-collaboration/switchboard/blob/7e32e00e993af5ecfcdb8ce366c5f0dea47bf335/packages/sign-in-core/src/better-auth/provider-configuration.ts#L261-L281) · [Session row](https://github.com/better-auth-ui/better-auth-ui/blob/2b028ec5256d6f04879c1a6a1d83822ac23e896f/examples/start-shadcn-baseui-example/src/components/auth/settings/security/active-session.tsx#L57-L120)

Define a token-free browser response and cookie-authenticated, person-scoped revocation by session ID. Keep any provider token lookup on the server and use the existing fenced session deletion path. Specify current-session sign-out and what the UI reports if deletion or readback fails. Show that another browser session is revoked while the caller’s survives, and bind any CLI claim to issuer session state and Central acknowledgment. Evidence `authorization-fenced-adapter.ts:71–79,95–105`, `authorization-fence-mutations.ts:233–244,410–415`, B2X `requirements.html:57`, `decisions.html:60–73`. [B2X decisions](../2026-11-15-fleet-access-b2x/decisions.html#device)

### B2. Native Reject contradicts the adopted Decline rule

`design.html:93–96` opens `organization/reject-invitation` while invoking BG’s guarded Decline. BG S6 requires a verified recipient, a pending and unexpired invitation at the write, and preservation of an Accept that has already landed. It explicitly keeps native Reject closed. In 1.7.11 Reject reads `pending` first, has no expiry check, and writes without `fromStatus`. The adapter adds a status predicate only when supplied. Accept supplies `fromStatus: "pending"`. If Accept commits between Reject’s read and its write, the native Reject can overwrite its status. The native personal list also filters status alone and can expose expired rows as actionable. The copied `UserInvitationRow` calls the native Reject hook. Evidence Better Auth `crud-invites.mjs:264–290,373–397,592–599` and organization `adapter.mjs:715–726,793–808`. [BG S6](../2026-11-15-fleet-access-bg/specification.html#S6) · [BG guarded write](../2026-11-15-fleet-access-bg/program-design.html#m2) · [Invitation row](https://github.com/better-auth-ui/better-auth-ui/blob/2b028ec5256d6f04879c1a6a1d83822ac23e896f/examples/start-shadcn-baseui-example/src/components/auth/organization/user-invitation-row.tsx#L32-L87)

Bind the Me row to BG’s `/api/auth/organization/decline-invitation`, preserve the existing guarded Accept and membership readback, and define pending-unexpired list visibility. Make BG’s guarded write a prerequisite for this surface. Verify both race winners and expiry at the real stores, with a wrong-recipient refusal and no membership or status leak. Evidence `organization-provider-options.ts:102,148–155` and BG `program-design.html:123–130`. [BG program design](../2026-11-15-fleet-access-bg/program-design.html#m2)

### B3. Organization Delete requires a guard before any provider side effect and a defined settlement

`design.html:76,93–97` requires a fresh second factor but offers only native allowlisting and a confirmation dialog. Native Delete checks membership and `organization:delete`. It can clear the caller’s active organization **before** its `beforeDeleteOrganization` hook and has no native second-factor gate. Switchboard’s configured hooks have no delete gate. Native deletion then removes members, invitations and the organization in separate adapter calls. Switchboard’s composed adapter executes the provider’s transaction callback without an outer transaction, with each fenced write committing its own batch. An interruption can therefore leave a partially deleted organization. There is an organization deletion fence in the store, but this design gives no outcome for partial writes, stale active choices, Central propagation, or which fleet resources survive deletion. Evidence Better Auth `crud-org.mjs:237–291`, organization `adapter.mjs:370–398`, Switchboard `organization-provider-options.ts:128–179`, `authorization-fenced-adapter.ts:95–105`, `authorization-fence-mutations.ts:417–479`. [Provider hooks](https://github.com/agent-collaboration/switchboard/blob/7e32e00e993af5ecfcdb8ce366c5f0dea47bf335/packages/sign-in-core/src/better-auth/organization-provider-options.ts#L128-L179) · [Fenced adapter](https://github.com/agent-collaboration/switchboard/blob/7e32e00e993af5ecfcdb8ce366c5f0dea47bf335/packages/sign-in-core/src/better-auth/authorization-fenced-adapter.ts#L89-L105)

Keep the destructive action gated in the plan until the Lead establishes its lifecycle and authority. Require the live verified session, intended organization, permission, origin and fresh stored factor before any mutation, including clearing active selection. Specify the result and readback under failure. A direct request from an owner with a stale factor must leave the active selection, membership, invitation and revision state unchanged. The pinned example dialog’s typed confirmation and native mutation provide presentation precedent only. [Delete dialog source](https://github.com/better-auth-ui/better-auth-ui/blob/2b028ec5256d6f04879c1a6a1d83822ac23e896f/examples/start-shadcn-baseui-example/src/components/auth/organization/delete-organization-dialog.tsx#L31-L102)

### B4. Permission-filtered links need a shared server-side rule for pages, reads and actions

`design.html:51–54,74–76,86–88,120–121` names “matching permissions” and tests visible links. A build with a correct-looking member sidebar can still serve `/people`, `/machines`, `/workspaces/:id`, Settings or Audit directly, or accept a stale action after an organization switch. The current role map has `organization:view` and `readAudit`, machine mutation grants and workspace mutation grants. It has no independent Machines or Workspaces read permission keys. The shipped People path already rechecks the live session, selected organization and `organization:view` on the server. The signed forwarder also binds the operation’s organization to the caller’s credential. Native Update/Delete accept explicit organization IDs and check the role in that target, so menu scope alone will not bind an action to the currently confirmed choice. Evidence `organization-access-control.ts:4–22`, `organization-membership-read-plugin.ts:59–85,106–129,195–201`, `fleet-admin-forwarding.ts:65–98` and Better Auth `crud-org.mjs:196–212,259–274`. [People guard](https://github.com/agent-collaboration/switchboard/blob/7e32e00e993af5ecfcdb8ce366c5f0dea47bf335/packages/sign-in-core/src/better-auth/organization-membership-read-plugin.ts#L59-L85) · [Central forwarder](https://github.com/agent-collaboration/switchboard/blob/7e32e00e993af5ecfcdb8ce366c5f0dea47bf335/packages/sign-in-core/src/better-auth/fleet-admin-forwarding.ts#L65-L98)

Name the actual read and action permissions per route, including Audit, allowed-machine reads and workspace detail. Bind nav, page renders and calls to the authoritative choice. Define what happens on no active membership, a denied or unanswered switch, a lost reply after a committed switch, and browser Back. Require server refusal for direct denied and cross-organization requests, without protected data or writes. The chooser helper supplies unconditional readback, while the destination and refusal handling need new logic. Evidence `person-organization-choice.tsx:14–55`. [Chooser](https://github.com/agent-collaboration/switchboard/blob/7e32e00e993af5ecfcdb8ce366c5f0dea47bf335/packages/sign-in-core/src/pages/islands/person-organization-choice.tsx#L14-L55)

### B5. The shell landing can drop unfinished setup and the CLI continuation

`design.html:51,55,74–77,109` treats `/owner-ready` as an account redirect and `/setup` as unchanged. On the pin, `/owner-ready` carries authorization resume, renders factor or organization steps, and is also reached after browser sign-in, passkey sign-in and the Fleet CLI confirmation prompt. `/setup` is absent from the current allowlist. BG’s planned page decision gives pending steps precedence and retires `/owner-ready`. A blanket redirect can skip a required step or discard the authorize URL and fixed deadline. Evidence `sign-in-http-handler.ts:231–316`, `sign-in-request-handler.ts:64–86`, `owner-page.tsx:301–354`, `factor-page.tsx:28`, `fleet-cli-commands.ts:157`, BG `specification.html:35–43` and `program-design.html:49,57–73`. [BG page order](../2026-11-15-fleet-access-bg/specification.html#S1) · [BG caller migration](../2026-11-15-fleet-access-bg/program-design.html)

Define the cutover from BG’s account-ready decision into the shell. Carry the validated continuation and unchanged deadline through shell navigation, organization selection and factor confirmation. Specify which CLI clients are covered and which session entry appears after each flow. On the pin, the loopback code flow starts a 300-second timer and validates state at its callback, but the opened URL carries no deadline and the existing browser form supplies only Continue. Browser-authorized Fleet CLI tokens are bound to the authorizing browser session. B2X’s proposed `--device` route creates its own real session. A separate, revocable CLI row after ordinary Continue needs an explicit session or credential contract. Bind Cancel to a terminal refusal of the same attempt and show that reload, Back and continuation at expiry cannot revive it. Evidence `loopback-authorization.ts:18–58,74–95`, `owner-page.tsx:228–249`, BG `program-design.html:64–73,135–142`, B2X `decisions.html:60–73`. [Loopback flow](https://github.com/agent-collaboration/switchboard/blob/7e32e00e993af5ecfcdb8ce366c5f0dea47bf335/packages/sign-in-owner-cli/src/loopback-authorization.ts#L18-L95) · [B2X device session](../2026-11-15-fleet-access-b2x/decisions.html#device)
