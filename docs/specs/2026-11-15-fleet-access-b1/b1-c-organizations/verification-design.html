B1-C · Organizations finished: Verification Design

Choose twice through the delivered UI and read the stored result. Then look up real member and invitation rows as the owner and try the same requests as callers who must learn nothing. The chosen component's real browser traffic must contain no roster. Every observation below is a plan; none has run.

The three things for you

V2 and V6 fail on today's hide-after-selection build. V3/V4 prove the organization filter and live permission, including a session ending during the read. V5 reads actual native replies, so a projection that exists but is never called cannot pass.

The three owner answers determine the UI under test. The detailed observations cover the recommended separate page, exact email and shipped switcher. A roster or embedded page choice requires its new branch to be reconciled before the build packet is released.

U9/R14 require the requested organization's answer only; U51/R62 require choice on the account surface. The owner chose “returning sign-in (step-up only for changes)” (Fleet transcript:86867). The old real-service tests are retained, but their inspected source is not a fresh proof receipt. A passing local run would still not establish staging or release sign-in.

What stays real in each observation

Blue is pure contract proof, teal the actual service/storage boundary, amber the browser, green the deciding state, rose the sensitivity control. Stand-ins remain outside the membership/permission/selection interaction being claimed.

V1–V5 and V8's concurrency/decoding cases use the existing local auth harness, with provider, Turnstile and central test peers, controlled clock and private database root. Membership, invitation, session, Better Auth and injected Drizzle are real. Every host file runs twice: default local workerd/D1 and SIGN_IN_TEST_HOST=node for Node/better-sqlite3. V6 parameterizes both hosts in one real-browser file. Heavy runs are on Sunclaw, after B1-A merges. V8's pure Hegel families run in the existing unit lane and do not substitute for host/browser observations.

V1 · Own context is current, scoped and fail-closed (S1/S4)

Proven by: asking the new public self-context endpoint from real cookie sessions and comparing its strict body with the actual membership/session rows, on both hosts.

  • Cases: signed out; expired session; a verified invited person with zero memberships; one membership; two memberships; selected ID no longer among those memberships. Use the existing injected-clock control for expiry. An available empty list must differ from unavailable.
  • Each choice has exactly organization ID, name and role; only the signed-in person's rows occur. No token, user record, invitation list, metadata or another person's membership field is present. Attempts to supply personId in query fail as invalid rather than select that person's view.
  • Snapshot the selection and authority rows before/after the context read: unchanged. Missing/old second-factor confirmation does not prevent the read or change the confirmation stamp.
  • Pure cases for readPersonOrganizationContext cover each unavailable port and malformed stored row, with no I/O; both-host fault cases cover the actual database failure mapping.

Wrong builds: query memberships by a supplied person ID; keep a stale active ID; catch a failed store read as an empty list. Each has a separate deciding assertion. An allowed change in membership display order still passes because the oracle compares identities/content rather than a cosmetic order.

Lifetime/target: lasting regression, new people-organization-context.host.e2e.test.ts plus beside-module unit cases, on the frozen PR head. Unverified: deployed cookies and hosts.

V2 · Choose twice, then observe the actual session (S2/S3/S4)

  4. With a valid O1 selection, submit a real foreign organization to native set-active. Expect 403 and read null from that same stored session. Re-read self-context and inspect the UI: no old current-choice label remains after settlement. Membership and role rows are unchanged.
  5. Advance beyond the confirmation window but within session expiry. Selection succeeds; confirmation fields stay unchanged. A protected invite still gets the existing second-factor refusal.

Wrong builds: today's hide-after-selection condition; retain the old self-context after a mutation; restore the old selection after native 403; treat selection as factor confirmation. Each must fail its named row, while an unchanged native clearing implementation passes. The short-lived optimistic label is allowed only while pending, never as the settled authorization answer.

V4 · Caller removal, ended sessions and store failures reveal no subject (S5/S7)

Waiting is on explicit query/settlement events, never a delay. Changing the owner-role row directly is an adversarial fixture; it does not claim the public API permits owner removal or demotion.

  • Run the same O1 subject request as member, another organization's owner, removed/noncurrent actor, expired/ended session, no cookie, and agent/bot/fleet-session bearer credentials. Expect the documented 401/403 body and unchanged rows. Initial refusal makes zero subject queries.
  • Hold the actual subject read, end that session using fixture Drizzle or advance its controlled expiry, then release it. The final check refuses. Repeat with a fixture role change removing organization:view. Do not replace the native permission helper with a stand-in.
  • For the permission-name discriminator, a unit case records the endpoint's actual call to checkOrganizationPermission with a forwarding spy that invokes the real helper. Assert the requested permission is exactly organization:view at both checks. Temporarily changing the endpoint literal to organization:readAudit must fail that assertion, even though today's owner holds both. The host cases still exercise real native permission; no third production role or configurable permission port is introduced just for the test.
  • Fail each real membership/permission/subject database read through the test query watcher, while leaving later reads usable. Expect unavailable/503, no subject result and no audit outcome. Run owner success after restoring the fixture to distinguish a broken setup from the intended failure.
  • With valid session but no recent second factor, the lookup succeeds and the protected invite remains refused. Authentication, permission and confirmation are different decisions.

Test seam: extend the existing recordingD1Database and Node query logger test boundaries, following B1-B's fault-control pattern. The permanent harness exposes holdNextPersonMembershipRead() returning reached/release events and failNextOrganizationRead(); only test hosts serve their control routes. They wrap the real statement, not a replacement membership answer. Node and workerd each must exercise the same cases.

Wrong builds: skip initial permission; replace it with role-name success; skip final recheck; catch a database error as absence. Keep one failing receipt per mutation, then restore and observe green. Lifetime: lasting host cases plus unit permission/schema cases. No source-only “looks guarded” check closes this observation.

V5 · The shipped switcher gets safe native replies (S10)

Proven by: actual GETs to native list/full-organization, containing real seeded member/invitation/metadata canaries before projection, through the public service as owner and ordinary member on both hosts. Inspect the serialized HTTP body, not a locally reconstructed projection.

  • The full body is null or exactly id, name, slug, logo, createdAt; list contains only those summaries for the caller's organizations. Recursively reject members, invitations, totals, metadata, Fleet stamp fields, session token and planted canaries. The strict field check applies to owners too.
  • Native foreign full-read still refuses and clears selection; signed-out reads refuse. Wrong methods stay 404. list-members and all other unselected native routes remain closed, with their old assertions retained.
  • For a stored stale/foreign active selection, a query-free full read retains native refusal/clearing. Explicit organizationId, slug, member-limit or any query key instead gets generic 400 before native dispatch, identically for a real O2 and a nonexistent ID. Session/membership snapshots are unchanged by that invalid request, and the query watcher sees no native subject read. Test unverified and expired stored sessions too; public native self reads cannot bypass V1's authentication.
  • In a real-component integration fixture, an internal native provider.api.getFullOrganization call with the same authorized cookie still has its native full shape. This proves the public fence did not change internal semantics.
  • Unit cases for the projection cover full null, full summary, array, future fields, invalid UUID/date, malformed JSON and missing fields. A malformed success becomes 503; native error status/body survives except the documented lookup 400 normalization. Test no-store on successes/errors, multiple set-cookie values and removal of old content-length; no session-token string appears in JSON.

Wrong builds: omit projection dispatch; spread the full body while deleting only members; pass malformed success through; project internal API results; allow a caller-selected native organization query; skip fresh self-session authentication. Each fails a distinct assertion. A native upstream extra field remains an allowed change because the whitelist excludes it without needing an updated deny list.

Lifetime: lasting people-organization-read-projection.host.e2e.test.ts, projection unit cases and an internal/public boundary integration case. If the existing chooser is chosen, these route-open observations are replaced by explicit closed-route assertions; the owner lookup remains required.

V8 · Exhaustive local transitions and native write races (S13)

Proven by: four lasting Hegel families for M1–M4, compile-time exhaustiveness sensitivity, and actual native writes/strict decoders on both database hosts. This implements the owner's pure-transition/Hegel ruling. It does not introduce a wrapper around Better Auth or count model agreement as proof of a native race.

The two tables are implemented independently. The amber native proof observes stored writes, not a fake transition result. There is no effects runner for these local machines.

Generator, oracle and lane shared by all four families

Add active-organization-transitions.hegel.unit.test.ts, invitation-read-transitions.hegel.unit.test.ts, membership-answer-transitions.hegel.unit.test.ts and lookup-request-transitions.hegel.unit.test.ts under packages/sign-in-test-support/src/core-tests/. Test-support already declares @hegeldev/hegel@0.4.10; do not add it to runtime core or create a gate. Follow the actual src/person-identity-contracts.unit.test.ts:118–145 usage: hegel.test, testCase.draw(generators.integers(...)), settings { testCases: 1000, derandomize: true, database: hegel.Database.disabled }. Run through existing pnpm test:unit. Record the seed/settings and minimized example text with each red receipt.

Draw sequence length 0–40, then an index into an explicit finite event catalog at each step, using bounded integer generators. Fixture IDs are validated UUIDv7 constants for two own organizations, a foreign organization and distinct invitation identities; indices shrink to small stable fixtures. Generate time from a fixed epoch plus integer offsets around expiry (−1, 0, +1 and wider forward/backward moves), always through transition context. Generate retries, duplicate events and paired completion orderings explicitly; mix random sequences with templates that contain both orders of each named pair. An exhaustive small state × event-kind census also covers every refused pair, so random selection is not the coverage guarantee. No test reads or sleeps on wall-clock time.

Each family has its own simple reference table and payload constructors in the test, independent of production transition/helper/constructor code. Generated histories start at the machine's initial state; the separate state/event census draws valid payloads for every state, without claiming an arbitrary starting candidate has a proven authorization history. Compare the entire next/refused result including reason, state and all payloads after every prefix; then compare retained current state and invariants. Freeze/copy inputs to detect mutation. Parse generated states/events through their actual schemas, and separately challenge raw decoders with unknown literals/malformed values. Use only public wire projections for release assertions, not a copied serializer. A refused transition retains the old state; time invariants refer to the context of the last applied row/clock event, not an unprocessed external clock move.

M1 family · Native active-selection observations

Generate all three states and events, null/own/foreign IDs, both refusal origins, read failures and retries. Pair a refusal with a competing native selection's observed readback in both orders. Oracle: row null means none; row ID means chosen(ID); known refusal plus null means cleared(origin); known refusal plus a competing ID means chosen(that ID). Invariants: no fabricated clearing cause on hydration, no sole-membership auto-selection during read, no chosen ID substitution, no role/membership grant. Independently test self-context projection with own-membership sets; a stale/foreign chosen ID is exposed as null, without a write.

Mutants → expected shrunk shapes: keep previous choice after native clearing → [row(O1), refusal(foreign-choice, null)]; infer clearing on ordinary null → [row(null)]; auto-select the only membership on a null read → that same row with choices [O1]; confuse clearing origin → one full-read/null event; make cleared sticky despite another winner → [refusal(full-read, O2)] yields chosen(O2). A read-unavailable mutant that releases the retained old state must fail the context's unavailable-body assertion, not merely its transition kind.

M2 family · Invitation read states and injected expiry

Generate each raw native status, same/different IDs, unread initialization, expiry-adjacent clock values, forward/backward moves and repeated snapshots. The independent classifier uses a test table for the four raw statuses and a direct strict time comparison. Invariants after each applied step: identity stable, pending iff last-observed raw pending and expiry > the applied now, expired iff that row is pending and expiry ≤ now, nonpending status unchanged by clock-only events, wrong-ID/refused input unchanged. Snapshot events can change native status in any observed direction; no terminal-write guarantee is invented.

Mutants → shrunk shapes: use ≥ for lookup expiry → one pending snapshot at expiry = now; make expired sticky → [pending snapshot at T, clock(T − 1)] with expiry T, expected pending; expire an accepted row → [accepted snapshot, clock(after expiry)], expected accepted; accept a different ID → one wrong-ID snapshot; allow an unknown stored status → one invalid raw snapshot rejected at decoding. A pending-only SQL filter cannot be detected by a pure transition test: the host decoder case below is its required red.

M3 family · Private candidate before authorized release

Generate idle/reading/candidate/completed states, every event kind, member roles, empty histories and permutations of mixed invitation histories with zero/one/several current pending rows. Advance injected now before subject observation. Generate final permission failure, store failure, retries and duplicate final events. The reference table independently derives a candidate from member facts or invitation history; it never calls M2's production classifier. Invariants: only answered can release subject data; candidate has both an initial authorization and subject observation but no release authority; refused/unavailable have no subject payload; completed states cannot be revived by a late event; each retry is a new idle invocation.

Mutants → shrunk shapes: release candidate immediately → [authorized, subject(member)], still private candidate; confirm before facts → [permission-confirmed], transition refused; use only the first invitation → [authorized, subject([cancelled, pending-future])], invited candidate; skip final denial → [authorized, subject(member), permission-refused], completed refused without answer; turn a store error into absence → [authorized, store-unavailable], unavailable; revive a completed denial → a denied prefix followed by confirmation. Member-first query precedence is also observed at the real store, because member facts deliberately contain no invitation branch.

M4 family · Current browser generation

Generate all seven states, every event kind, valid/invalid submissions, all strict result variants, network/malformed failures, old/current/future integer generations, input/organization changes and unmount. Reference generation arithmetic is implemented locally in the test, without the production helper. Pair replies A/B in both orders around input changes and new submissions, plus failure/answer duplicates and unmount races. Invariants: generation never decreases, only answered contains subject output, matching pending generation alone may settle, stale or wrong-phase completion performs no assignment, disposed is terminal, edits/failures clear old output. Assert the island adapter commits pending before starting the request and reads current state at callback time; pure tests alone cannot prove that wiring.

Mutants → shrunk shapes: remove generation comparison → [submit(A), edit, submit(B), reply(A)], B remains pending; let an older reply replace the newer answer → the same prefix with reply(B) before reply(A); retain a member result on a later denial → [submit(A), reply(A, member), edit, submit(B), reply(B, refused)], next state refused has no answer; settle after unmount → [submit(A), unmounted, reply(A)], disposed unchanged; accept duplicate completion outside pending → [submit(A), reply(A), reply(A)], second transition refused. V6 still releases real held HTTP responses to prove the adapter and rendered result.

  1. Two valid set-active requests for O1/O2: hold both after their native membership checks and before writes, then release/observe commit and settlement in each order.   2. A valid selection versus foreign-choice clearing, and versus native full-read clearing when that route is selected: force both write orders after admission.   3. Two accepts of one ordinary unexpired pending invitation: hold both before the native conditional pending→accepted claim. Release in each order. Exactly one claim succeeds and one membership is created; the losing claim refuses. BeforeAccept hooks can have recorded a losing intent that remains unconfirmed. Preserve existing audit assertions; do not invent a confirmed loser or infer history from membership.
  4. Lookup still answers member. Also force the accepted→pending rollback condition after an existing injected member-work failure, with and without an intervening cancel; rollback must not overwrite canceled. Native terminal immutability is not an invariant. These cases observe native writes; no project CAS wrapper is allowed.

Unknown status must produce 503 rather than be hidden by a SQL status filter. Assert no lookup-side row changes. Rejected rows can be labeled fixtures; public reject remains closed.

A query-watcher inability to force a named interleaving is an open fixture/proof gap, not a reason to accept random simultaneous requests.
