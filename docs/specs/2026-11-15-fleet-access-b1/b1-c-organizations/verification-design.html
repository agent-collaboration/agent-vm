V1 · Your organizations read (S1, S4)

Proven by: calling GET /api/auth/organization/self-context with real cookies and comparing the body to the stored membership and session rows, on both hosts.

  • Cases: no cookie; expired session (controlled clock); verified person with no memberships; one; two; a stored choice that is no longer a membership. Empty available and unavailable must differ.
  • Each choice has exactly ID, name and role, only the caller's. A personId query key gets 400.
  • Session and membership rows are unchanged by the read. An old second-factor confirmation doesn't block it and isn't touched.
  • The session read fails (fault seam on the session select): 503 unavailable, not 401. The memberships read fails: 503, not an empty list.

Wrong builds that must fail: acquire the session with getSessionFromCtx (session-fault case returns 401); return the stored choice without checking memberships (stale case); turn a membership-read failure into []. Lasting: new packages/sign-in-test-support/src/people-organization-context.host.e2e.test.ts plus unit cases beside the reader.

V2 · Switch twice, then Continue (S2, S3)

Proven by: extending people-owner-page.host.e2e.test.ts:65–115, keeping its real-CLI and foreign-refusal assertions.

  1. Two organizations, one person in both. Choose O1; read session.activeOrganizationId: O1. The page still offers the switcher; the title is not “Choose your organization”; Continue is enabled.
  2. Choose O2 in the same session; stored value is O2.
  3. Press Continue to CLI; the real CLI completes and its token names O2.
  4. From O1, submit a foreign organization: 403; stored value null; self-context shows no current choice; memberships and roles unchanged.
  5. Advance the clock past the confirmation window, inside session expiry: switching works and confirmation fields are unchanged; a protected invite is still refused.

Wrong builds: today's hide-after-choice condition (step 1 fails); keep organizationChoices.length driving Continue (step 3 fails: button disabled); restore the earlier choice after a 403 (step 4); stamp a confirmation on switch (step 5). Lasting, both hosts.

V4 · Who is refused, and a removal mid-read (S5)

  • As a member of O1, owner of O2 only, removed owner, ended session, expired session, no cookie, and agent, bot and Fleet-session bearer tokens: the documented 401 or 403 body, and the facts query never runs (seam counter is zero).
  • Hold the real subject read; end the session through fixture Drizzle; release: 401, no subject. Repeat changing the role row so organization:view is lost: 403. Changing the role row is a fixture, not a claim the public API can demote an owner.
  • Permission name: a forwarding spy around the real checkOrganizationPermission records organization:view at both checks. Changing the literal to organization:readAudit must fail that assertion even though owners hold both.
  • Fail the permission's role read, the session read and the facts read in turn: 503, no subject.
  • With an old second-factor confirmation the lookup succeeds while an invite is refused.

Wrong builds: skip the first check (facts counter is nonzero); compare the role name instead of calling the permission check; skip the second check (held case returns the subject); swallow a store error as not-member. Lasting, same host file as V3, both hosts.

V5 · Shipped switcher: the two native reads are cut down (S10)

Proven by: seeding real members, invitations and metadata containing canary strings, then calling native list and get-full-organization through the public service as owner and as member, and inspecting the serialized HTTP body.

  • Bodies contain only id, name, slug, logo, createdAt; no canary appears anywhere. Owners get no more than members.
  • Any query key (an organization ID, a slug, a member limit, for a real O2 and for a nonexistent ID): identical 400 before Better Auth runs; the session and membership rows unchanged.
  • Session read fault on these paths: 503. Signed out: 401.
  • A server-internal provider.api.getFullOrganization call still returns the full native shape.
  • Unit cases for the projection: null, one, array, extra future fields, bad UUID, bad date, bad JSON. A malformed success becomes 503. Cookies survive; content-length is removed.

Wrong builds: never call the projection; copy the object and delete only members; pass a malformed success through; allow query keys. With today's card instead, V5 becomes: both routes stay closed (existing route tests). Lasting: people-organization-read-projection.host.e2e.test.ts.

V6 · Real Chrome on both hosts (S2, S3, S9, S10, S12)

Proven by: one new browser file run against both hosts with startLocalAuthHarness, startHeadlessChrome and B1-A's event-driven DevTools helper. No Playwright, no timers.

  1. Open the delivered page as a person in two organizations. Use the actual switcher by label and keyboard; creation, personal account and settings are absent; the summary shows roles.
  2. Choose O1 then O2; after network settlement, the page and the stored session agree. Captured native bodies pass V5's check; no list-members request is ever sent.
  3. Lost reply: pause the O1→O2 set-active response at the response stage, let the server commit, fail the request. Without any focus change or reload, the summary, switcher and stored session all show O2.
  4. Foreign switch: refusal, then no current choice shown; reload; nothing restored from local storage.
  5. Open the lookup from its entry; look up a member, an invited email and an absent email through the field; then make the next read fail: the old result disappears and “unavailable” shows.
  6. Hold the first lookup reply after the server computed it, submit a second, let it land, release the first: only the second shows. Repeat with an edit before release.
  7. At 400 px in dark mode: one top heading, no horizontal overflow, controls reachable by keyboard. Screenshots with synthetic data; record Chrome version, host and commit.

Wrong builds: no mutation-cache reset (step 3 shows O1); a copied switcher with roles on (step 2 sends list-members); M3 without the generation check (step 6); keep the old result on failure (step 5). Lasting: people-organization-browser.host.e2e.test.ts with test-fixtures/native-organization-browser-scenario.ts.

V8 · The three machines (S13)

Proven by: one Hegel family per machine in packages/sign-in-test-support/src/core-tests/ (test support already declares @hegeldev/hegel 0.4.10), using hegel.test, testCase.draw(generators.integers(…)) and settings { testCases: 1000, derandomize: true, database: hegel.Database.disabled }, as in src/person-identity-contracts.unit.test.ts:118–145. Run by pnpm test:unit.

Shared method: draw a sequence of 0–40 steps, each an index into a finite event catalogue; clock values are a fixed epoch plus integer offsets around expiry (−1, 0, +1, and wider moves both ways), always passed through context. Each family has its own reference table written in the test, independent of production code. After every prefix compare the full result (next or refused, reason, state) and check the invariants. Inputs are frozen to catch mutation. A small exhaustive census also covers every state × event-kind pair, so coverage doesn't depend on random draws.

Exhaustiveness: add one new literal to each state union and each event union, one at a time; pnpm typecheck must fail at that machine's satisfies never; restore. That's six receipts. Each semantic wrong build is run to its shrunk red, restored, and rerun green. A type or setup failure never counts as a semantic red.

Better Auth's own concurrency (two set-active calls, accept versus cancel) is not re-tested here: we neither own nor wrap those writes. Our reads of their results are covered by V2 and V3.
