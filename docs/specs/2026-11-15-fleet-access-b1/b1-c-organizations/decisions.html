B1-C · Organizations finished: Decisions

Three choices are open: where the owner opens person lookup, how they identify the person, and which organization chooser they use. The underlying rule is settled: read only your own memberships, or, as the permitted owner, one person's membership in your organization. Recommendations below are not answers.

The three things for you

Each choice has the current picture, corresponding gains/costs, a picture of each option and what waits. The source checks behind the shipped switcher are explicit; the assumption table names what source compatibility has not proven.

Open: lookup page, lookup input, organization component. I recommend a separate page, exact email and the shipped component with narrowed server replies. Neither the owner nor the Lead has picked those options.

Open 2 · How do you identify the person?

R14 fixes the answer—member with role, invited, or not a member—but names no input control. Invitations name an email before a user account exists. A list-only picker cannot ask about someone absent from both membership and invitation lists, so the credible list option retains an exact-email fallback.

Blue is the subject the owner asks about; teal the existing stored states; amber acceptance; green the required negative answer. An account ID alone cannot identify a not-yet-created invitee.

What you see

One Email field and Look up. Type the whole email; receive its state in this organization.

What you gain

The same input reaches a current member, an invited person without an account and someone absent here. No directory needs to be returned to the browser.

Cost and who pays

The owner must know and type the exact address. The developer maintains normalization and invalid-input feedback. Typos can truthfully produce not-member; no fuzzy matching is promised.

Picture

What you see

An owner-only member/pending-invitation list to choose from, plus exact email for someone not listed.

What you gain

Known people are discoverable without retyping an address; the fallback preserves the absent-person question.

Cost and who pays

This exposes a roster of this organization to its owner and changes Stage 1's author-proposed “no roster” scope. The developer must design authorization, pagination, list privacy and stale-list proof; the owner scans a list and still needs exact email for absence. It must not simply open native list-members to every member.

Picture

One narrow lookup covers member, invitee and absence; no roster release. It requires knowing the address.

Adds owner-visible discovery and a new list contract. Selecting B explicitly reopens the list scope and its design/proof before implementation.

I recommend exact email because it covers invitees before any person row exists and answers the complete R14 question without a directory. “No roster” was my proposed boundary, not a direct prohibition from the owner; B can be chosen, but its additional disclosure and contract must be designed openly. A list alone is not offered as a complete R14 solution.

The request schema, input component and final implementation packet wait. The fixed permission and answer semantics remain designable. No agent assumes exact email merely because it is recommended.

Open 3 · Which organization-choice component?

The standing rule is to use Better Auth UI as shipped, adjust our side, and bring a named divergence to the owner. Keeping Switchboard's existing chooser instead is therefore an explicit choice. The shipped component is feasible in source with narrow server replies; it is not yet runtime-proven.

Blue identifies UI, teal the existing mutation, amber the read/route boundary and rose the data that must not reach ordinary members. Native membership is not owner permission.

What a person sees

The existing organization rows, now retained after selection, with own organization names and roles.

What it gains

Reuses the existing narrow self-context/native mutation path. No native full-read exposure or new copied switcher dependency closure.

Cost and who pays

This is a named exception to using the shipped component. Switchboard's developer owns the custom selector and request settlement; the owner sees that existing interaction instead of the upstream dropdown.

Picture

What a person sees

Better Auth UI's unchanged dropdown with creation, personal-account and settings entries hidden, plus a separate own-membership summary for role labels.

What it gains

Follows the standing UI rule. The shipped cache handles selection and refetch, while the public server releases organization summaries only, not a directory.

Cost and who pays

The developer adds current verified-session checks, mandatory native list/full response projection, eight copied auth components, avatar/dropdown primitives and a declared Pacer dependency. These public reads accept no explicit organization/slug query: the component uses only the stored session choice. The native full GET can clear a stale/foreign current selection before refusing. Selecting B would accept that disclosed native behaviour; proof covers body privacy, query refusal and cache settlement on both hosts.

Picture

Named reason for divergence: avoid the shipped switcher's broad native read and own the existing narrow rows. Native selection itself is unchanged.

Keep upstream UI unchanged and project public native reads. It costs copying/import mapping, dependency closure and explicit privacy/cache proof.

The shipped switcher:33–44 provides the three hide settings. Its organization views pass hideRole, disabling member-list queries. The active cache:12–21 intentionally uses the smaller list shape, so it need not cache a roster. Its onSettled:100–105 always refetches after success or error. These are source facts, not a passing browser run.

The Lead requested this “adjust our side” option and recommended preferring it if feasible. My check supports it. Neither of us can supply the owner's answer. Projection is applied to all public callers including owners; the internal native full API remains unchanged, and owner lookup remains a separate permission-guarded read.

The selector binding, selected native route openings and implementation packet wait. Contract, scoped lookup and proof design can continue. No component is forked and no native full route is opened merely to get a page working.

Each picker is a separate answer. Selecting locally does not notify an agent or authorize implementation; use the existing Comments handoff to return the answers. No open option has pick.
