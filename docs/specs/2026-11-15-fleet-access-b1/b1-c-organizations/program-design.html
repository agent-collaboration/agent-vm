B1-C · Organizations finished: Program Design

How the rules are built. The existing sign-in store supplies the facts; Better Auth keeps owning sessions and switching; one new Better Auth plugin adds three endpoints; the page splits “your memberships” from “you must choose”; a browser island hosts the chooser and the lookup. All paths are under packages/sign-in-core/src/ unless stated.

The three things for you

Session reads call Better Auth's own getSession endpoint so a database failure stays a failure. The page model gains selectionRequired, so showing your memberships no longer disables Continue. The chooser refreshes your summary from the query client's mutation cache, which fires even when the switch request gets no reply.

The detail below follows the recommended answers (separate page, exact email, shipped switcher). Branch notes say exactly what changes for each alternative. There is no runtime flag; the unchosen branch is deleted from this design before build.

Built on S1–S13. Source read at Switchboard f3b2b88b, Better Auth 1.7.11 (installed copy under switchboard.item2-b2-central-organizations/node_modules/.pnpm/) and Better Auth UI 2b028ec5. Design only; nothing built.

Shapes

Its two type users, owner-page.tsx:25 and sign-in-http-handler.ts, import from the new home; no forwarding re-export. All types are z.infer of these schemas.

An available context is built by one constructor that sorts choices by organization ID and enforces that activeOrganizationId is null or one of the choices. The core package's src/index.ts exports the context reader and these schemas for BG and test support.

Reading the session without hiding failures

Better Auth's getSessionFromCtx catches every error and returns null (dist/api/routes/session.mjs:247–265), and returns any session already on the context (:248). The native getSession endpoint it wraps returns null for no or expired session (:164) and throws INTERNAL_SERVER_ERROR/FAILED_TO_GET_SESSION on an adapter failure (:229–232). getSession is a public export of better-auth/api.

acquireReadSession(context) calls getSession()({ ...context, method: 'GET', asResponse: false, headers: context.headers, returnHeaders: true, returnStatus: false, query: { disableCookieCache: true, disableRefresh: true } }), the same call getSessionFromCtx makes, without the catch. It copies returned set-cookie headers the same way (:266–271), so an expired cookie is still cleared. Its result is a closed union: session, signed-out (null, or an UNAUTHORIZED APIError), unavailable (any other error). An unverified email is signed-out.

In provider-configuration.ts:230–238 the before-hook today calls getSessionFromCtx for every /organization/ path. Change it so that for exactly these read paths it calls acquireReadSession instead, stores the result on ctx.context.session (returning it through the hook's context, as the hook already does for the person-proof case), and throws APIError('SERVICE_UNAVAILABLE') for unavailable:

  • /organization/self-context, /organization/person-membership, /organization/people (new);
  • shipped-switcher branch only: native /organization/list and /organization/get-full-organization.

This is the first acquisition on those paths, so nothing earlier can have refreshed the session or swallowed an error, and Better Auth's own middleware on the two native reads reuses the stored session (:248) instead of acquiring again. The actor capture for people changes is unchanged for every other /organization/ path. Refresh stays off: a read never extends a session.

Your organizations: readPersonOrganizationContext

Signature: readPersonOrganizationContext(props: { readonly session: ReadSession; readonly store: Pick<OrganizationMembershipRecords, 'membershipsForPerson'> }): Promise<PersonOrganizationContext>, where ReadSession is acquireReadSession's union.

  1. signed-out → signed-out; unavailable → unavailable.
  2. Read that person's memberships through the existing membershipsForPerson. A store failure is unavailable, never an empty list.
  3. activeOrganizationId = currentSelectionAmong(choices, session.activeOrganizationId): the stored ID if it is one of the choices, otherwise null. Pure; no write.

GET /api/auth/organization/self-context accepts no query keys (any key: 400) and returns 200 available, 401 signed-out or 503 unavailable, strict bodies, cache-control: no-store.

The chooser and settling after a switch

The shipped mutation (use-set-active-organization.ts:87–105 at 2b028ec5) uses mutationKey = organizationMutationKeys.setActive (set-active-organization-mutation.ts) and already refetches the active organization on settle. It does not know our self-context query. sign-in-pages-island.tsx:34 creates the one module-level QueryClient. Subscribe once to queryClient.getMutationCache(); on an updated event whose mutation key equals organizationMutationKeys.setActive and whose state is success or error, call queryClient.resetQueries({ queryKey: selfContextQueryKey }). Reset clears old data so the summary shows loading, not the old choice, until the fresh read lands. A fetch that rejects with no reply still ends the mutation in error, so this runs then too. No polling, no local storage, no custom set-active callback; the upstream component is unchanged.

The rest of the page follows the server. The title, setup steps, Continue button and the selected organization's Fleet setup card are rendered once by the server (owner-page-document.tsx:15–38, page-document.tsx:188–210); the island can't patch them. The page is rendered with the context it was built from (activeOrganizationId and selectionRequired, in the island's initial state). When the fresh self-context arrives after a switch and either value differs, the island calls location.replace(location.href), keeping the URL's authorize continuation parameters, so the server renders every selection-dependent part from stored state. This needs no user action and works the same after a lost reply, because it is triggered by the fresh read, not by the mutation's outcome. If the values are unchanged (for example a refused switch from no choice to no choice), nothing reloads.

Shipped branch: cutting down the two native reads

New response-release/organization-read-projection.ts, called in handleSignInRequest right after the provider handler and before the existing response release:

  • For GET /api/auth/organization/list and get-full-organization: any query key gets a generic 400 before Better Auth runs. A successful reply is parsed and rebuilt from a whitelist only: id, name, slug, nullable logo, createdAt. List is an array of those; full is one or null. A body that doesn't parse becomes 503. Status, cookies and other headers are kept; content-length is dropped; cache-control: no-store is set.
  • For the lookup's POST: a non-JSON content type or Better Auth's own JSON-decode 400 is replaced by the generic { error: 'invalid-request' }.
  • Internal provider.api calls never pass through this code and keep the native shape.
  • Better Auth's own effect is kept: get-full-organization for a session whose current organization is no longer one of the caller's memberships writes activeOrganizationId: null before answering 403 (crud-org.mjs:353–372). The projection doesn't change that; the island reads self-context again after any 403, and the reload rule above re-renders the page.

The three machines

Common shape: closed Zod unions for state and event, a pure function transition(state, event, context): { kind: 'next'; state } | { kind: 'refused'; reason }, an inline x satisfies never as the default branch of every switch over state and event, closed refusal reasons per machine. A refused step keeps the old state and writes nothing. No library, no effects runner: none of these machines calls out; the callers perform the I/O and feed the results in as events.

M1 · An invitation as the lookup sees it

Input: a strictly parsed invitation row { id: Uuid7, status: 'pending' | 'accepted' | 'canceled' | 'rejected', expiresAt: EpochMilliseconds } (an unknown status or bad expiry fails parsing, so the lookup is unavailable). States: pending | expired | accepted | cancelled | rejected. Events: row-read(row), clock-moved; context { now }.

FromEventNext
anyrow-read, status pendingpending if expiresAt > now, else expired
anyrow-read, accepted / canceled / rejectedaccepted / cancelled / rejected
pending, expiredclock-movedrecompute from the retained expiry and now (backwards movement can return to pending)
accepted, cancelled, rejectedclock-movedunchanged

Invariant after every step: pending exactly when the last row read was pending and its expiry is after the step's now; the clock never changes a non-pending status. Better Auth's own accept uses “expiry before now” (crud-invites.mjs), so the two policies differ at exact equality; we don't change Better Auth.

M2 · One lookup on the server

States: start | checked | candidate { answer } | answered { answer } | refused | unavailable. Events: first-check-passed, facts-read { facts }, second-check-passed, check-failed, store-failed. Context { now }.

FromEventNext
startfirst-check-passedchecked
checkedfacts-readcandidate: member facts give member and role; otherwise each invitation through M1, any pending gives invited, else not-member
candidatesecond-check-passedanswered, same answer
start, checked, candidatecheck-failed / store-failedrefused / unavailable; any candidate dropped
every other pairanyrefused (unexpected-event)

Only answered can be serialized. The endpoint runs the checks and the store read, feeds events in, and replies from the final state: answered 200, refused 401 (no session) or 403, unavailable 503.

M3 · The lookup page's request

States, each with a nonnegative integer generation: idle | invalid | pending { request } | answered { answer } | refused | unavailable | disposed. Events: edited, organization-changed, submit-valid { request }, submit-invalid, reply { generation, reply }, failed { generation }, unmounted.

FromEventNext
any live stateedited, organization-changedidle, generation + 1
any live state but pendingsubmit-validpending, generation + 1
pendingsubmit-validrefused (already-pending)
any live statesubmit-invalidinvalid, generation + 1
pendingreply / failed, same generationanswered, refused or unavailable from the parsed reply / unavailable
any live statereply / failed, other generation, or not pendingrefused (stale), nothing assigned
any live stateunmounteddisposed
disposedanyrefused (disposed)

The island keeps one current-state reference. apply(event) calls the transition and assigns only a next; React state is a render of that reference. It commits pending before starting the fetch and captures that generation; callbacks apply events against the current reference. A malformed reply is turned into failed before the transition.

The subject read

Add to OrganizationMembershipRecords: readPersonMembershipFacts(request: { organizationId: OrganizationId; email: string }): Promise<SignInStoreResult<PersonMembershipFacts>>, with PersonMembershipFacts = { kind: 'member'; role } | { kind: 'invitations'; rows: readonly InvitationRow[] }.

  1. Injected Drizzle: select member.role from member joined to user where member.organizationId = organizationId and user.email = email, limit 1. Parse the role. No global “does this user exist” query.
  2. If a member is found, return it without reading invitations.
  3. Otherwise select id, status, expiresAt from invitation where organization and email match, ordered by ID, with no status filter and no limit. Parse every row; any failure makes the whole result a store failure.

Uses the existing readStoreValue / SignInStoreFailure conventions (storage/store-query-results.ts). No migration, raw SQL or index change; fields exist in storage/sign-in-schema.ts:355–393. The two queries share no transaction; the promise is per read.
