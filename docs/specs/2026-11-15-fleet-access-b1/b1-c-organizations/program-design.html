B1-C · Organizations finished: Program Design

How the rules are built.

  • The existing sign-in store supplies the facts, read through injected Drizzle.
  • Better Auth keeps owning sessions and switching.
  • One new Better Auth plugin adds four endpoints.
  • The page splits “your memberships” from “you must choose”.
  • Today's card becomes the always-available chooser.
  • A shadcn page shows the owner this organization's people and the lookup.

All paths are under packages/sign-in-core/src/ unless stated.

The three things for you

Session reads call Better Auth's own getSession endpoint, so a database failure stays a failure. The page model gains selectionRequired, so showing your memberships no longer disables Continue. The people list is owner-only, checked twice, and carries no IDs.

This follows your 15 Nov picks: today's card, its own page in shadcn like Better Auth UI, and a list with email fallback. After a refused switch it follows Better Auth, and the card's re-render is the redirect you asked for (your pick on Decisions).

Reading the session without hiding failures

Better Auth's getSessionFromCtx catches every error and returns null (dist/api/routes/session.mjs:247–265), and returns any session already on the context (:248). The native getSession endpoint it wraps returns null for no or expired session (:164) and throws INTERNAL_SERVER_ERROR/FAILED_TO_GET_SESSION on an adapter failure (:229–232). getSession is a public export of better-auth/api.

acquireReadSession(context) calls getSession()({ ...context, method: 'GET', asResponse: false, headers: context.headers, returnHeaders: true, returnStatus: false, query: { disableCookieCache: true, disableRefresh: true } }), the same call getSessionFromCtx makes, without the catch. It copies returned set-cookie headers the same way (:266–271), so an expired cookie is still cleared. Its result is a closed union: session, signed-out (null, or an UNAUTHORIZED APIError), unavailable (any other error). An unverified email is signed-out.

In provider-configuration.ts:230–238 the before-hook today calls getSessionFromCtx for every /organization/ path. For exactly /organization/self-context, /organization/person-membership, /organization/people-list and /organization/people it calls acquireReadSession instead. It assigns the result directly to ctx.context.session, null included, as Better Auth's own getSession does. Returning { session: null } through the hook's context is lost, because the hook-context merge (defu) ignores null, so an expired session that getSession had already placed on the context would survive. Each of the four read endpoints copies the hook's accumulated set-cookie headers into its own response headers, because the endpoint starts with fresh headers that would otherwise drop the native cookie clearing. (Corrected 17 Nov from a real Better Auth pipeline reproduction.) It throws APIError('SERVICE_UNAVAILABLE') for unavailable. This is the first acquisition on those paths, so nothing earlier can have refreshed the session or swallowed an error. The actor capture for people changes is unchanged for every other /organization/ path. Refresh stays off: a read never extends a session.

Your organizations: readPersonOrganizationContext

Signature: readPersonOrganizationContext(props: { readonly session: ReadSession; readonly store: Pick<OrganizationMembershipRecords, 'membershipsForPerson'> }): Promise<PersonOrganizationContext>, where ReadSession is acquireReadSession's union.

  1. signed-out → signed-out; unavailable → unavailable.
  2. Read that person's memberships through the existing membershipsForPerson. A store failure is unavailable, never an empty list.
  3. activeOrganizationId = currentSelectionAmong(choices, session.activeOrganizationId): the stored ID if it is one of the choices, otherwise null. Pure; no write.

GET /api/auth/organization/self-context accepts no query keys (any key: 400) and returns 200 available, 401 signed-out or 503 unavailable, strict bodies, cache-control: no-store.

The people list (your pick: list with email fallback)

Endpoint. GET /api/auth/organization/people-list?organizationId=…&offset=…. The query is parsed with organizationPeopleListRequestSchema: any other key, a non-UUIDv7 ID, or an offset that isn't a non-negative multiple of 50 gets the generic 400. Its two checks are exactly the lookup's:

  • the before-hook's session is present;
  • a fresh stored read (persons.readPersonSession, person-session-store.ts:88–119) shows the session current, verified and current in this organization;
  • checkOrganizationPermission({ permission: 'organization:view' }) passes.

The read runs between them. M2 drives it; replies are 200 available, 401 or 403 { kind: 'refused' }, and 503 { kind: 'unavailable' }, all with no-store.

Store read. Add listOrganizationPeople(request: { organizationId; offset }): Promise<SignInStoreResult<OrganizationPeoplePage>> to OrganizationMembershipRecords, through injected Drizzle, like the existing membershipsForPerson. It runs three selects:

  1. member.role, user.name and user.email, from member joined to user, where member.organizationId matches, ordered by member.createdAt then member.id, limit 50, offset.
  2. count(*) of that organization's members.
  3. invitation.id, status, expiresAt, email and role, where the organization matches and no member of that organization has that email (a NOT EXISTS over member joined to user). No status filter, so every row is parsed and classified by M1.

A bad role, status, expiry or email fails the whole read, so the list is unavailable, never shorter. The endpoint keeps only invitations M1 calls pending, drops their IDs, and returns nextOffset = offset + 50 when that is below the total, otherwise null.

The three selects share no transaction: a page is a snapshot (S8). This is the codebase's existing way to read Better Auth's tables (membershipsForPerson, storage/sign-in-schema.ts:355–393). It keeps the same hold and fault seams on both hosts. It never opens Better Auth's list-members or list-invitations routes, which let any member read the roster (crud-members.mjs:437–478, crud-invites.mjs:525–542). Better Auth's server API (auth.api.listMembers, listInvitations) could do the same reads without opening those routes. The direct store read is chosen for the typed failures and test seams above; the Decisions page records that call. No migration, raw SQL or index change.

The people page

GET /api/auth/organization/people?organizationId=… runs the same first check, with no subject read, and renders pages/organization-people-page.tsx through pageDocument, using mintPageNonce(platform.crypto) from B1-A. It answers 200 HTML, 303 to /sign-in (no email in the URL), 403 or 503. The organization's name comes from the actor's own memberships. The organization admin page is served to any current member (sign-in-http-handler.ts:152–161), so the link needs its own guard. That handler is outside any Better Auth endpoint, so it has no endpoint context for checkOrganizationPermission. Instead it calls Better Auth's server API, provider.api.hasPermission({ headers: request.headers, body: { organizationId: membership.organizationId, permissions: { organization: ['view'] } } }) (dist/plugins/organization/organization.mjs:21–74, registered at :854). Better Auth builds the real context itself, and /organization/has-permission stays out of the public route table. The call's success boolean is passed as a new showPeopleLink: boolean input to organizationAdminPage. That renders one escaped People link only when it's true. A failed permission read hides the link and changes nothing else. The page's existing B2 content is untouched, and the People page and list keep both their server checks.

The page uses the shared shell and tool-access-ui's shadcn parts, laid out like Better Auth UI's people tables (examples/start-shadcn-baseui-example/src/components/auth/organization/organization-members.tsx, organization-invitations.tsx at 2b028ec5):

  • a Card titled “People” with the organization's name;
  • a members Table (name, email, role Badge), Skeleton rows while loading, an Empty state, and Previous and Next Buttons driven by offset and nextOffset;
  • an invitations Table (email, role Badge, “Invited”);
  • an InputGroup email Field with a Look up Button;
  • an aria-live result region.

No invite, remove or role controls. The island pages/islands/organization-people.tsx runs two M3 instances, one for the list page and one for the lookup. It fetches with authClient.$fetch, parses replies with the shared schemas and renders text nodes only. Clicking a row fills the email field and runs the lookup, so the result shown is always a checked S6 answer.

The three machines

Common shape: closed Zod unions for state and event, a pure function transition(state, event, context): { kind: 'next'; state } | { kind: 'refused'; reason }, an inline x satisfies never as the default branch of every switch over state and event, closed refusal reasons per machine. A refused step keeps the old state and writes nothing. No library, no effects runner: none of these machines calls out; the callers perform the I/O and feed the results in as events.

M1 · An invitation as the lookup and list see it

Input: a strictly parsed invitation row { id: Uuid7, status: 'pending' | 'accepted' | 'canceled' | 'rejected', expiresAt: EpochMilliseconds } (an unknown status or bad expiry fails parsing, so the read is unavailable). States: pending | expired | accepted | cancelled | rejected. Events: row-read(row), clock-moved; context { now }.

FromEventNext
anyrow-read, status pendingpending if expiresAt > now, else expired
anyrow-read, accepted / canceled / rejectedaccepted / cancelled / rejected
pending, expiredclock-movedrecompute from the retained expiry and now (backwards movement can return to pending)
accepted, cancelled, rejectedclock-movedunchanged

Invariant after every step: pending exactly when the last row read was pending and its expiry is after the step's now; the clock never changes a non-pending status. Better Auth's own accept uses “expiry before now” (crud-invites.mjs), so the two policies differ at exact equality; we don't change Better Auth.

M2 · One checked read on the server

Used by the lookup and by each list page. The read's kind (lookup or list) is fixed at start and carried, unchanged, in every live state. States: start { kind } | checked { kind } | candidate { kind, result } | answered { kind, result } | refused | unavailable, where kind is the closed union 'lookup' | 'list' and result's shape is fixed by it. Events: first-check-passed, facts-read { facts }, second-check-passed, check-failed, store-failed. Context { now }.

Only answered can be serialized. The endpoint runs the checks and the store read, feeds events in, and replies from the final state: answered 200, refused 401 (no session) or 403, unavailable 503.

M3 · One request on the page

Generic over its request and parsed reply; the people page runs one instance for the list and one for the lookup. States, each with a nonnegative integer generation: idle | invalid | pending { request } | answered { reply } | refused | unavailable | disposed. Events: edited, organization-changed, submit-valid { request }, submit-invalid, reply { generation, reply }, failed { generation }, navigated { request }, unmounted. For the list, page entry is submit-valid. Previous and Next are navigated with the new offset: they supersede whatever page is loading, so the latest page asked for always wins. A repeated Look up click is still submit-valid and is refused while one is pending.

The island keeps one current-state reference per instance. apply(event) calls the transition and assigns only a next; React state is a render of those references. It commits pending before starting the fetch and captures that generation; callbacks apply events against the current reference. A malformed reply is turned into failed before the transition.

The lookup's subject read

Add to OrganizationMembershipRecords: readPersonMembershipFacts(request: { organizationId: OrganizationId; email: string }): Promise<SignInStoreResult<PersonMembershipFacts>>, with PersonMembershipFacts = { kind: 'member'; role } | { kind: 'invitations'; rows: readonly InvitationRow[] }.

  1. Injected Drizzle: select member.role from member joined to user where member.organizationId = organizationId and user.email = email, limit 1. Parse the role. No global “does this user exist” query.
  2. If a member is found, return it without reading invitations.
  3. Otherwise select id, status, expiresAt from invitation where organization and email match, ordered by ID, with no status filter and no limit. Parse every row; any failure makes the whole result a store failure.

Uses the existing readStoreValue / SignInStoreFailure conventions (storage/store-query-results.ts). No migration, raw SQL or index change; fields exist in storage/sign-in-schema.ts:355–393. The two queries share no transaction; the promise is per read.

The four endpoints

better-auth/organization-membership-read-plugin.ts uses createAuthEndpoint like passkey-confirmation-plugin.ts:58–70, and is registered beside the organization provider plugin in provider-configuration.ts. Each endpoint reads the session the before-hook stored directly from ctx.context.session, parsed through the ReadSession helper, and never calls getSessionFromCtx. That helper reuses only a truthy stored session (session.mjs:248): a stored null (signed out) would trigger a second getSession() with refresh on, whose .catch(() => null) hides failures. So signed-out requests would break the one-acquisition rule. (Corrected 17 Nov from the Implementer's source read of Better Auth 1.7.11.)

After a refused switch (your pick: Better Auth's behaviour, then redirect)

Better Auth clears the current choice and answers 403 (crud-org.mjs:419–425). The card shows “That organization isn't available” and calls location.replace(location.href), as in every ending. The server then renders the page from the stored session:

  • Two or more memberships: it leads with “Choose your organization” and the card, so you pick again, with no wrapper of ours.
  • Exactly one membership left: the case S2 names. In B1-C the card offers nothing to switch to. BG's page decision closes it: a waiting CLI selects that organization first (select-first), and otherwise it's the account page.
