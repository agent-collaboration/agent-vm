B1-C · Organizations finished: Specification

What must be observably true when B1-C is done. Each rule names the need it serves and is decided by an observation in the Verification Design. Your three 15 Nov picks set the page, the input and the chooser component. The list you picked adds one owner-only read (S8). No other permission or privacy rule changed.

The three things for you

S2: switching stays available and the CLI Continue still works once a choice exists. S5: the lookup checks permission before it reads and again before it answers. S6: “elsewhere” and “nowhere” give byte-identical answers. S1 and the failure table: a database failure is never reported as “signed out” or “not a member”.

S8, S9 and S10 follow your 15 Nov picks: its own page in shadcn like Better Auth UI, a list with email fallback, and today's card. After a refused switch, S3 keeps Better Auth's behaviour and the page re-renders so you pick again (your pick on Decisions).

Sources are U9, U21/U46, U27, U43, U51 and OD25/OD26 on Requirements, with the approved R13, R14, R53, R58 and R62. Nothing here has been built or run.

Your organizations and switching

S1 · You read only your own organizations

From U27, U51, R62. A current, verified person MUST be able to read their memberships, each with organization ID, name and their role, plus the session's current organization if it is still one of those memberships. The read takes no person ID from the caller, returns no tokens, no other person's data and no organization roster. It has exactly three endings: signed out, available, unavailable. Zero memberships is an empty available answer. A stored choice that is no longer a membership reads as no current choice, without rewriting the session. A database failure while reading the session or the memberships MUST be unavailable, never signed out.

S2 · Switching stays available, and Continue still works

From U51, R58, R62. Whenever a person has two or more memberships, the card MUST offer switching, including after a valid choice exists. A person in O1 and O2 can choose O1, then O2, in the same session without signing in again. The page MUST treat two facts separately: “these are your memberships” (always shown when there is at least one) and “you must choose before continuing” (only when there are two or more memberships and no valid current choice). Only the second fact makes choosing the page's pending task, changes the title to “Choose your organization” or disables Continue to the CLI. After a switch settles, every part of the page that depends on the choice (title, steps, Continue, the selected organization's setup card) MUST reflect the stored state without any user action. With a valid choice, Continue to the CLI MUST work as today and complete the CLI authorization for that organization. Sign-in still auto-selects a sole membership; a read never selects one. One case stays as it is today: a person with exactly one membership whose current choice was cleared later (for example by Better Auth's native refusal of a foreign switch). The card offers them nothing to switch to, and their CLI Continue is refused. Today's page behaves the same way (sign-in-http-handler.ts offers choices only for more than one membership). BG's continuation closes this case by selecting the sole membership first (BG Program Design, select-first). B1-C does not claim it.

S3 · Better Auth does the switching

From U27. Switching MUST use Better Auth's native set-active. Only a real membership can be chosen; signed-out or expired callers can't choose; switching creates no membership, changes no role, and confirms no second factor. Better Auth's own behaviour stays: a foreign choice returns 403 and clears the current choice. After success, refusal, or a request that ends with no reply, the page MUST read the stored state again before showing a current organization. It MUST NOT restore an earlier choice from memory or replay the request. Concurrent switches follow Better Auth's write order; no lock or version is added.

S4 · Reading and switching need no fresh second factor

From U43, R53, your returning-sign-in answer. A valid person with an absent or old confirmation MUST be able to read their organizations, switch, and (as owner) look someone up. None of these confirms or extends a second factor. Enrolment order and the protection on invite, cancel, accept, remove and create are unchanged.

The owner's lookup

S5 · Only the requested organization's owner, checked twice

From U21/U46, R13, OD25. The caller MUST hold a current verified session whose current organization is the requested one, and pass a fresh native hasPermission check for organization:view using their current role with caching off. Today only owners hold it. A member, an owner of another organization, a removed owner, an ended or expired session, and agent, bot or Fleet-session credentials MUST be refused with no subject data, before any subject read. After the read, the same checks run again against a fresh read of the stored session (never the copy cached at the start of the request); if they fail, the read result is discarded and the answer is refused. Removal that commits after the second check is outside this promise; there is no cross-read transaction.

S6 · The answer is about this organization only

From U9, R14, C4. The answer MUST be exactly one of: member with role owner or member; invited, when a pending invitation for this organization and email has expiry strictly after the injected clock's now; not-member, otherwise. Membership wins over a pending invitation. If there is no membership, every invitation row for that organization and email is read and classified, so an older cancelled row can't hide a newer pending one. Someone who belongs only to another organization and someone with no account MUST get byte-identical bodies. No answer contains another organization's ID, name or existence, a user ID or a count. A malformed stored role, invitation status or expiry among the rows read MUST make the answer unavailable, never not-member. This is equal content, not equal timing.

S7 · The lookup changes nothing

From OD26. The lookup MUST NOT create or change users, memberships, invitations, roles, second-factor confirmations or audit records, and it does not say which earlier change completed. Existing people-change tests stay as they are. No schema change or migration.

S8 · The owner picks from this organization's people, or types an email (your pick)

From U9, U21/U46 and your 15 Nov pick. On the lookup page the owner MUST see this organization's people:

  • Members: name, email and role, 50 per page, in the order Better Auth returns them by join time, with the total number of members.
  • Invitations: email and role for each pending, unexpired invitation (expiry strictly after the injected clock's now) whose email isn't already a member.

The list is read with the same two checks as S5: before the read, and again on a fresh session read before it is released. Anyone else is refused with nothing listed. A list reply contains no user ID, membership ID, invitation ID, inviter or another organization's anything. A malformed role, status or expiry in the read rows makes the list unavailable, never a shorter list. Picking a row runs the S6 lookup for that email, so every answer shown comes from one checked lookup.

The email field remains for anyone not listed, for example someone removed or never invited. It takes one email, trimmed and lowercased, plus the organization ID, in a JSON POST body, never a URL. A blank or invalid email is a field error with no read; there is no prefix or wildcard search, and the list has no search. Reading the list or a page changes nothing. A page is a snapshot: a person who joins or leaves between pages may be skipped or shown twice. That is named, not hidden.

S9 · The lookup's own page, in shadcn like Better Auth UI, and how results behave (your pick)

A separate page, linked from organization admin and guarded on its own. It is built from the same shadcn parts Better Auth UI's people tables use, already in tool-access-ui: Card, Table, Badge, InputGroup, Field, Button, Empty and Skeleton. It follows their layout:

  • a card titled “People” with the organization's name;
  • a members table (name, email, role badge) with previous and next page buttons;
  • an invitations table (email, role, “Invited”);
  • an email field with a Look up button;
  • a result area.

It is read-only: no invite, remove or role controls (those stay on their existing pages with their step-up). No administration is on the account page.

A changed input or organization, a new submit, a refusal, a malformed reply or a network failure MUST clear the previous result. A late reply for an older request (list page or lookup) MUST NOT replace the current one. A signed-out visit goes to sign-in, with no email in the URL. Emails and results are kept out of logs and screenshots; browser proof uses test identities.

S10 · The chooser is today's card, and no native organization read opens (your pick)

The chooser is today's Switchboard card, extracted from the owner page and always available as S2 says. It uses only the S1 read and Better Auth's native set-active. Better Auth's native organization/list, get-full-organization, list-members and list-invitations routes stay closed to the browser, as today. The S8 list reaches Better Auth's own reads only inside the server, after the owner check. The card MUST meet S1 to S4.

Boundaries and quality

S11 · BG gets facts, and still owns getting in

B1-C supplies the S1 read, native switching and a reusable choice surface. BG owns which page comes next, invitations and Decline, the account page shell, the return destination, the CLI deadline and the six journeys. B1-C keeps today's CLI continuation working (S2) and adds no setup engine, destination store or account route. BG removes /owner-ready in its own cutover.

S12 · Both hosts, the design system, and old code removed

The new paths MUST work on local workerd with D1 and local Node with better-sqlite3. New screens use Switchboard's shared React and shadcn components, one top heading, labelled keyboard-reachable controls, and a 400 px dark layout. New core code passes B1-A's injected-capability, allowed-globals and UUIDv7 checks; tests use controlled time and event waits; heavy runs go to Sunclaw; no new CI gate. The overloaded organizationChoices field, the hide-after-choice condition and the old inline set-active listener are removed.

S13 · Closed states, pure transitions, Hegel

From your 15 Nov rule (Fleet transcript 142100, 142119). Every state our code moves MUST be a closed union with a pure transition(state, event, context) that returns the next state or a closed refusal, with an inline x satisfies never at each switch over states and events, and its stored inputs parsed strictly at the boundary. That covers three machines: the invitation read view (M1), one checked read on the server, used for both the lookup and a list page (M2), and the page's request lifecycle, one instance for the list and one for the lookup (M3). The session's current organization has no project transition (only Better Auth writes it), so it is read through one pure function, not a machine. Each machine has a Hegel family with an independent reference model, checks after every step, controlled clock moves, retries and paired events, fixed settings, and wrong builds that Hegel must shrink to a named counterexample. Better Auth's writers stay native and unwrapped.
