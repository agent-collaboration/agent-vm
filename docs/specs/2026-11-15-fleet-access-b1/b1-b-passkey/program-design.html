B1-B · Passkey sign-in: Program Design

How the code changes to meet the Specification: which packages, which types, which call paths. Everything is at switchboard main f3b2b88b, with Better Auth 1.7.11 and @better-auth/passkey 1.7.11 as pinned.

The three things for you

  • Where the session is marked as both factors: in the service's request handler, after Better Auth answers, not in a Better Auth hook. A failure there lands in the handler's existing clean-up, which deletes the new session. That's how S9 holds.
  • How the Turnstile token reaches the challenge request: through Better Auth's own client request hook, so Better Auth UI's button stays as shipped.
  • The sign-in page now loads the browser components, which it didn't before.

The button and autofill: open for you. This page is written for the recommended answer: Better Auth UI's button with its one autofill line removed.

Your approved Program Design (line 1738) says passkey sign-in "uses the plugin's own endpoints", that the user-verification hook "refuses an assertion without user verification, so no session exists", and that "an after-hook stamps the new session". This page keeps all three. The stamp runs after Better Auth answers, in the service's handler rather than a Better Auth hook; why. Line 1826 says "the sign-in page sends the token on the challenge request itself", and so it does.

The sign-in path, end to end

Participants are coloured automatically; the colours carry no meaning.

  • Without user verification: the plugin's afterVerification throws before createSession (pinned dist/index.mjs:487–500). The handler sees a 401 and no issued session, so it records failed and stamps nothing.
  • If the stamp or the record fails: the handler throws. Its existing catch deletes every session this request issued and answers 503 (below).

Key: amber is new; blue is changed. No host package changes: both hosts serve the same core.

S6 · The token removed from verify's body

The after-middleware in better-auth/provider-configuration.ts:268–271 strips the token for /get-session with sessionReadWithoutToken (better-auth/session-read-without-token.ts:15–22). That helper takes a { session, user } body and returns it without session.token. Better Auth's verify answer has exactly that shape (pinned dist/index.mjs:504–510). So the condition becomes:

The cookie is set by Better Auth's setSessionCookie before the body is returned, and context.json keeps the response headers, so the cookie survives, as it does for /get-session today.

S4, S9, S12 · Marking the session, and recording the sign-in

A new module, packages/sign-in-core/src/better-auth/passkey-sign-in-completion.ts:

Where it's called: in sign-in-http-handler.ts, beside today's social sign-in record (lines 383–390), after the login-link check:

  • The stamp: store.factors.stampSession already exists (storage/second-factor-store.ts:70–106). It sets session.secondFactorAt to the injected clock's now and secondFactorMethod to the method, in one atomic write that also checks the session is live and the person's email verified. It returns stamped, session-not-live or store-unavailable; requireStoredValue turns store-unavailable into a throw.
  • The failure path (S9): any throw lands in the handler's existing catch (lines 392–402). It deletes every session in state.issuedSessions with Promise.allSettled and answers 503 {"error":"sign-in-unavailable"}. The new session was pushed onto issuedSessions by the session-create hook (provider-configuration.ts:294–300), so it's the one deleted.
  • The record (S12): the same recordSignIn the social callbacks use, with method: 'passkey'. Its method parameter is already a string (storage/owner-bootstrap-store.ts:61–65), so the store doesn't change.

Why the handler and not a Better Auth after-hook: Better Auth turns an APIError thrown in an after-hook into its own error answer, and merges the response headers it already had, the session cookie included (better-auth 1.7.11 dist/api/dispatch.mjs:119–130). The handler wouldn't throw, its clean-up wouldn't run, and the session created moments earlier would stay, with its cookie sent. Running after Better Auth answers, in the handler, puts a failed stamp on the path that already deletes issued sessions. The approved design's word was "after-hook"; this is still after the session exists, and it's my call.

Why not mark it as it's created: a session-create hook doesn't know which request created the session without reading the path, and it runs before the plugin has updated the passkey's counter. The handler knows the request and sees the finished answer.

S5 · Who may sign in

No new code. The plugin creates the session through internalAdapter.createSession, which runs the service's session.create.before hook (provider-configuration.ts:283–293). That hook refuses a person ensurePersonActive rejects, and sets the active organization to the person's only membership, the same as for Google or GitHub. A refused person gets an error answer and no session.

S2, S7 · A fresh Turnstile token on each challenge request

The constraint: the passkey client sends the challenge request with no per-call options (pinned @better-auth/passkey dist/client.mjs:6–11), so the button can't attach a header itself. Your approved design already says the page sends the token itself (Program Design line 1826).

The seam Better Auth gives us: createAuthClient({ fetchOptions: { onRequest } }) becomes a hook on every request the client makes, plugin requests included (better-auth 1.7.11 dist/client/config.mjs:31–37). The hook is awaited and may return a changed request (@better-fetch/fetch index.js:448–449).

A new module, pages/islands/passkey-sign-in-turnstile.ts:

  • passkeySignInTurnstileToken() waits for Turnstile to load, through a sign-in-turnstile-ready event that owner-page-script.ts's onSignInTurnstileReady now dispatches on window, or at once if window.turnstile is already there.
  • The widget: rendered once into #sign-in-passkey-captcha with action: 'passkey_sign_in', execution: 'execute' and appearance: 'interaction-only'. It shows only if Cloudflare needs the person to interact.
  • Each call: runs turnstile.reset(widgetId) then turnstile.execute(widgetId). It resolves with the token from the widget's callback, and rejects from its error-callback.
  • A rejection makes the client's request fail. The button then shows Better Auth UI's error notice, and no challenge request is sent.

Why two widgets: Turnstile fixes a widget's action when it's rendered, and the service checks the action (expectedAction: 'passkey_sign_in', turnstile-captcha.ts:136–137). The Google and GitHub widget's tokens carry sign_in_social and would be refused.

The page's security policy

The sign-in page already allows Turnstile's script and frames (challenge: 'turnstile', owner-page-document.tsx:21). The island script is the service's own, loaded with the page's nonce, as on the factor pages. WebAuthn needs no policy entry. So the policy text doesn't change; served-page-csp.host.e2e.test.ts confirms it on the sign-in page.

Failure and concurrency

  • Turnstile fails or is refused: no challenge is stored (S2). The button shows its error notice.
  • The person cancels the prompt: the challenge stays unused and expires. Better Auth stores it with a lifetime and the signed cookie names it; nothing else reads it.
  • Two tabs: each challenge request stores its own challenge and sets its own cookie. The later cookie wins, so the earlier tab's verify request finds no challenge and is refused. No session is created by the refused one.
  • Replay: the plugin consumes the challenge before checking the signature (pinned dist/index.mjs:459, then the check at 470–484), so an answer works at most once.
  • A no-UV answer still consumes its challenge and doesn't move the counter (S3).
