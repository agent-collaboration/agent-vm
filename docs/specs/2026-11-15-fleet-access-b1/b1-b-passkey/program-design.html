B1-B · Passkey sign-in: Program Design

How the code changes to meet the Specification: which packages, which types, which call paths. Everything is at switchboard main f3b2b88b, with Better Auth 1.7.11, @better-auth/passkey 1.7.11 and Better Auth UI 1.7.34 as pinned.

The three things for you

  • The session is born confirmed: both factors are written in the same insert that creates a passkey sign-in's session, through the service's existing session-create hook. No unconfirmed passkey session ever exists, even for a moment.
  • How the Turnstile token reaches the challenge request: through Better Auth's own client request hook, so Better Auth UI's button stays exactly as shipped.
  • The sign-in page now loads the browser components, which it didn't before.

None open. You chose click only on 15 Nov (Decisions): one setting on Better Auth UI's own passkey plugin, passkeyPlugin({ autoFill: false }).

Your approved Program Design (line 1738) says passkey sign-in "uses the plugin's own endpoints", that the user-verification hook "refuses an assertion without user verification, so no session exists", and that the new session's secondFactorAt is stamped with method passkey. This page keeps all three. The stamp goes into the session's own insert rather than an after-hook, which makes "confirmed from that moment" literal; why. Line 1826 says "the sign-in page sends the token on the challenge request itself", and so it does.

The sign-in path, end to end

Participants are coloured automatically; the colours carry no meaning.

  • Without user verification: the plugin's afterVerification throws before the counter update and createSession (pinned dist/index.mjs:487–500). The handler sees a 401 with no issued session, and records failed.
  • If Better Auth fails after creating the session (for example its user read at line 502), the handler sees an error answer with an issued session. It treats that as a failed sign-in: it records failed and throws, and its existing catch attempts to delete the session and answers 503 (below).

S4, S9 · The session is born confirmed

The seam: Better Auth runs each session.create.before hook with the session data and the current endpoint's context, and merges the hook's returned data into the insert (better-auth 1.7.11 dist/db/with-hooks.mjs:7–30). The service already uses that hook to set activeOrganizationId (provider-configuration.ts:283–293).

The order inside the plugin's verify request (pinned dist/index.mjs):

  1. the challenge is consumed (459);
  2. the signature is checked (470–484);
  3. afterVerification refuses without user verification (487–491);
  4. the passkey's counter is updated (492–499);
  5. createSession runs the hook and inserts the row (500).

So when the hook runs on this path, the person has passed user verification.

The change to the existing hook, in provider-configuration.ts:

  • The fields: secondFactorAt and secondFactorMethod are already declared as server-only session fields (provider-configuration.ts:170–171; input: false), so a client can't set them. 'passkey' is one of the allowed methods (second-factors/second-factor-step-up.ts:8).
  • The clock: the host's injected clock, the same one stampSession uses.
  • Every other session (Google, GitHub, a factor replacing a session) is inserted exactly as today.

A new module, pages/islands/passkey-sign-in-turnstile.ts:

Turnstile's script: ready, or failed

owner-page-script.ts runs before the Turnstile script tag is parsed. It records one page-wide state, window.signInTurnstile, with three values: loading, ready or failed.

  • Ready: its existing onSignInTurnstileReady sets ready and dispatches sign-in-turnstile-ready on window.
  • Failed: a capturing error listener on window sees the script element's load error (resource errors don't bubble, but they reach a capturing listener on window). When the target is #sign-in-turnstile-script, it sets failed and dispatches sign-in-turnstile-failed. The existing Google and GitHub status line also shows "Sign-in verification is unavailable."

Each token request

  • If Turnstile has failed: passkeySignInTurnstileToken() rejects at once, with "Sign-in verification is unavailable. Reload the page to try again."
  • If it's still loading: it waits for whichever of the two events comes first.
  • The widget: rendered once into #sign-in-passkey-captcha with action: 'passkey_sign_in', execution: 'execute' and appearance: 'interaction-only'. It shows only if Cloudflare needs the person to interact.
  • Each call: runs turnstile.reset(widgetId) then turnstile.execute(widgetId), and settles on the widget's own callbacks:
    • callback resolves with the token;
    • error-callback, expired-callback and timeout-callback each reject that attempt with the same message.
  • Overlapping requests: two token requests can be pending at once. With autofill on, Better Auth UI's background challenge runs under a separate mutation key (["auth", "passkey", "autoFill"], passkey-mutation-keys.ts at 2b028ec5), so it doesn't disable the button, and a click can start a second request. The helper therefore serves token requests one at a time, first in, first out:
    • a request that arrives while another is executing waits in the queue;
    • when the current execution settles (a token, or a failure callback), the next request in the queue runs its own reset and execute;
    • each request settles with its own token or its own failure. No request replaces another's execution, and no token is given to two requests;
    • after a script failure, every queued request rejects at once.
  • A rejection makes the client's request fail before it's sent. The button shows Better Auth UI's error notice and is enabled again. The next click starts a new attempt; after a script failure, every attempt fails at once until the page is reloaded.

The queue as a pure, exhaustive transition (owner rule, 15 Nov)

The owner, on 15 Nov: "make srue we use hegel then an dpure transiton fucitons with exatsutiveness", and "make srue even in current prs and designs that we are usign x satfisvers enver". So the token helper is split in two:

  • a pure state machine, pages/islands/passkey-sign-in-turnstile-queue.ts;
  • a thin DOM runner, passkey-sign-in-turnstile.ts, that performs its effects.
  • Exhaustive: the switch over QueueEvent ends in event satisfies never, the codebase convention (owner-page.tsx:105). The runner's switch over QueueEffect ends the same way. Adding an event or effect without handling it fails to compile.
  • Pure: no DOM, no window, no Turnstile calls. B1-A's allowed-globals rule doesn't reach islands, but this module uses none anyway.
  • The runner (passkey-sign-in-turnstile.ts) does the work, and nothing else:
    • holds the current state;
    • turns the window events, widget callbacks and attachPasskeySignInTurnstile calls into QueueEvents;
    • performs each QueueEffect: render, reset then execute, or settle the pending promise for that id.
  • The protocol, defined for every state and event. The starting state is { script: 'loading', executing: null, waiting: [] }.
    • "Execute" always means the same two effects, in order: ensureWidget, then resetAndExecute, wherever a request starts. That's from idle, from scriptReady, and in a handoff.
    • ensureWidget is idempotent and owned by the runner. It renders the widget the first time and does nothing after that, because the runner holds the widget handle. So the pure state needs no "rendered yet" fact, and the same state always gives the same effects.
    • scriptReady while loading becomes ready, and starts the head of waiting if there is one. In any other state it's a no-op with no effects.
    • scriptFailed while loading or ready becomes failed. It rejects the executing request, then every waiting one in order, with no resetAndExecute. Once failed, it's a no-op. failed is terminal.
    • tokenRequested(id):
      • while failed, it rejects at once;
      • while ready with nothing executing, it executes;
      • otherwise, while loading or busy, it joins the back of waiting.
    • widgetToken and widgetFailed while a request is executing settle it first (resolve or reject). Then, in the same effect batch, they start the head of waiting with resetAndExecute, if any. With nothing executing, they're no-ops: a stray callback changes nothing.
  • Safety, after every step:
    • at most one request is executing;
    • a request is never both executing and waiting;
    • each request is settled at most once;
    • no token resolves two requests;
    • settlements happen in arrival order;
    • no resetAndExecute once the script has failed;
    • within one effect batch, a resetAndExecute comes only after the previous execution was settled, earlier in that batch or before it. A new execution never starts while another is still live.
  • Completion, at a drained end: after a final scriptFailed, or after scriptReady plus one widget outcome per started execution, every request is settled exactly once and waiting is empty. Unsettled requests in the middle of a run are normal, not a violation.

Why two widgets: Turnstile fixes a widget's action when it's rendered, and the service checks the action (expectedAction: 'passkey_sign_in', turnstile-captcha.ts:136–137). The Google and GitHub widget's tokens carry sign_in_social and would be refused.

Test harness changes

Three changes in packages/sign-in-test-support/src/test-fixtures/, all test-only. The Verification Design uses them.

A domain issuer for the real browser

  • The problem: the harness fixes its issuer to http://127.0.0.1:<port> (local-auth-harness.ts:411–416). The provider takes its WebAuthn relying-party ID and origin from the issuer (provider-configuration.ts:431–433). Browsers refuse WebAuthn on an IP-address origin: the WebAuthn Level 3 specification and Chromium's origin check (components/webauthn/core/browser/webauthn_security_utils.cc) both reject IP hosts. So Chrome can't register or use a passkey against today's harness, even with a virtual authenticator.
  • The change: startLocalAuthHarness takes a new option, issuerHostname?: 'localhost'. When it's set, issuer becomes http://localhost:<port>. The socket still listens on 127.0.0.1. Everything built from issuer follows: the siteverify URL, the provider callbacks, both hosts' configuration, and so the provider's RP ID and origin.
  • Chrome's side: the browser launch in native-browser-protocol.ts (lines 241–257) adds --host-resolver-rules=MAP localhost 127.0.0.1, so localhost reaches the IPv4 listener.
  • Who uses it: observeNativeSignInBrowser passes issuerHostname: 'localhost'. Every other test keeps 127.0.0.1.

One fault control

harness.failNextPasskeyUserRead(), with POST /__auth-proof/fail-next-passkey-user-read, follows makeLimiterUnavailable(). It makes Better Auth's user read right after a passkey sign-in's session insert fail once (pinned dist/index.mjs:502), and lets every later read and the deletion through.

  • workerd: handled beside auth-proof-rate-limit-bindings.ts:14. recordingD1Database (recording-d1-database.ts) throws for the first select from "user" after an insert into "session" in that request.
  • Node: handled in node-auth-proof-host.ts beside limiter-unavailable (line 384). The Node database's query logger (logQuery, lines 112–125), which already watches every statement, throws for the same statement.
  • The harness method goes in local-auth-harness.ts, beside makeLimiterUnavailable (line 874).
  • The same two watchers also keep the last insert into "session" statement and its parameters. harness.lastSessionInsert() returns them, read through GET /__auth-proof/last-session-insert, so a test can see what the insert itself carried.

A command-line login through the real browser

The existing loginThroughNativeOwnerCli({ target, repositoryRoot, browser }) (native-cli-proof.ts:92) runs the real owner CLI with its loopback and hands the sign-in address to browser. The new scenario passes a browser that drives real Chrome to that address and clicks Continue with Passkey. No new fixture is needed.

Failure and concurrency

  • Turnstile's script fails to load: every click shows the error at once, and no challenge request is sent.
  • Turnstile refuses, or the widget errors: no challenge is stored (S2). The button shows its error notice.
  • The person cancels the prompt: the challenge stays unused and expires. Better Auth stores it with a lifetime, and the signed cookie names it; nothing else reads it.
  • Two tabs: each challenge request stores its own challenge and sets its own cookie. The later cookie wins, so the earlier tab's verify request finds no challenge and is refused. The refused one creates no session.
  • Replay: the plugin consumes the challenge before checking the signature (pinned dist/index.mjs:459, then the check at 470–484), so an answer works at most once.
  • A no-UV answer still consumes its challenge and doesn't move the counter (S3).
  • A crash between the session insert and the answer: the row is already marked both factors, by its own insert, and the cookie never reached the browser.
