B1-B · Passkey sign-in: Specification

What must be observably true when B1-B is done. Each rule says where it comes from and what would show it's wrong.

The three things for you

  • S3: no fingerprint, face or PIN means no session, ever.
  • S4: a passkey sign-in is confirmed from the moment it happens, so your 15-minute window starts then.
  • S6: the session token never reaches the page's scripts.
  • S9: either the person gets a confirmed session, or no session at all.

S7, the sign-in page: a "Continue with Passkey" button. Whether it also offers passkeys in the browser's autofill list is open for you; S7 is written for the recommended answer, click only.

Every rule traces to your approved design: OD21 ("A passkey with fingerprint, face or PIN signs you in and counts as both factors", decided 31 October), and rules R5, R52, R53, R63 and R67 in the approved Specification (lines 174, 270, 241, 254 and 261).

In one list

  • S1: the two passkey sign-in requests reach Better Auth through the public service. Nothing else opens.
  • S2: the challenge request needs a Turnstile pass for passkey_sign_in.
  • S3: without user verification, no session.
  • S4: with it, the new session counts as both factors from that moment.
  • S5: only a person who may sign in today can sign in with a passkey.
  • S6: the session token stays in the cookie.
  • S7: the sign-in page offers the passkey.
  • S8: the flood limit covers it.
  • S9: a confirmed session or none.
  • S10: journey 5 is proven in a real browser on both hosts.
  • S11: the "passkey sign-in stays off" fallback is gone.
  • S12: each passkey sign-in is recorded, as Google and GitHub sign-ins are.

The rules

S1 · The two passkey sign-in requests are public; nothing else opens

From R5 and approved Program Design line 2095. The public service MUST pass the challenge request (GET) and the verify request (POST) to Better Auth's own passkey endpoints. Every other passkey path keeps today's answer. In particular, Better Auth's /passkey/delete-passkey stays closed, because removal goes through the service's audited /passkey/remove.

Wrong if: either request answers 404, or the wrong method passes, or another passkey path's answer changes.

S2 · The challenge request needs a Turnstile pass

From R52: "A person's sign-in MUST also pass a Cloudflare Turnstile check … when asking for a passkey sign-in's challenge."

  • A challenge request with a missing, rejected, wrong-action, reused or unreachable Turnstile check MUST be refused, with no challenge stored and no cookie set. The refusal is logged as captcha-refused with action passkey_sign_in, as today's private-provider cases show.
  • The verify request isn't checked again: a Turnstile token works once, and the verify request is bound to its stored challenge (approved Program Design line 1826).

Wrong if: any of those five gets a challenge through the public service.

S3 · Without user verification, no session

From R53: "a passkey without user verification MUST NOT sign in or confirm anything."

  • A verify request whose signed answer is valid but not user-verified MUST get 401 with code USER_VERIFICATION_REQUIRED.
  • No session row is created, no session cookie is set, and the passkey's signature counter is unchanged.
  • The challenge is used up: the same answer sent again is refused as "challenge not found".

Wrong if: any session or cookie exists after a no-UV answer, or the counter moved.

S4 · With user verification, the new session counts as both factors from that moment

From OD21 and R53: "A passkey sign-in with user verification counts as both factors, so its new session is confirmed from that moment."

  • A user-verified answer gets 200 and a session cookie.
  • That session's secondFactorAt is the service's clock at the sign-in, and its secondFactorMethod is passkey.
  • A protected change made within 15 minutes, for example inviting a person, goes through with no separate confirmation.
  • The same change after 15 minutes is refused with "a second factor is needed", as for any other session.

Wrong if: the new session is asked for a second factor within 15 minutes, or its second-factor time is anything but the sign-in moment.

S5 · Only a person who may sign in today can sign in with a passkey

From R5: passkey sign-in follows the same people rules as Google or GitHub.

  • A passkey that belongs to a person who can't sign in today, for example one who was removed and has no other membership, MUST be refused with no session. The service's existing session-create check (ensurePersonActive) decides this, as for Google or GitHub.
  • An unknown credential gets 401, with no session.
  • The new session's active organization is set the same way as for Google or GitHub: the person's only membership, or none.

Wrong if: a person refused on Google or GitHub gets in with a passkey.

S6 · The session token stays in the cookie

From your 12 Nov rule: "The session token is stripped from get-session before it reaches scripts." The same holds for every answer the page's scripts read.

  • The verify request's 200 body MUST NOT contain the session token, anywhere in it.
  • The cookie carries the session, as for Google or GitHub.

Wrong if: the token's value appears anywhere in the body.

S7 · The sign-in page offers the passkey

From U20 and OD21, and your rule to use Better Auth UI as shipped.

  • Under Google and GitHub there's a third button: Continue with Passkey, Better Auth UI's own button.
  • Clicking it: the page gets a fresh Turnstile pass for passkey_sign_in, sends it with the challenge request, then the browser asks for the passkey. On success, the person lands where Google or GitHub would have taken them: the same continuation address, so a command-line login started first still continues.
  • Cancelling, or a refusal, shows Better Auth UI's own error notice. The person stays on the sign-in page, signed out.
  • Autofill: the button doesn't offer passkeys in the browser's autofill list, and loading the page sends no challenge request. This is the recommended answer to the open decision.
  • At 400 px the button follows the page column, like Google and GitHub.

Wrong if: the button is missing, sends no token, lands somewhere other than Google or GitHub would, or loading the page creates a challenge.

S8 · The flood limit covers passkey sign-in

From R52. Both requests are in the callback-passkey class: 10 per 60 seconds per client address, at the outer limit and at Better Auth's own limit (request-limit-policy.ts:32–35). Past that, a request gets 429 and nothing is created: no challenge, no session.

Wrong if: an eleventh request in a minute from one address creates anything.

S9 · A confirmed session, or none

  • If marking the session as both factors fails (the session is gone, or storage is unavailable), or the sign-in record can't be written (S12), the person MUST end up with no session. The service deletes the session it just created and answers 503 {"error":"sign-in-unavailable"}, its existing answer for a failed sign-in (sign-in-http-handler.ts:338–344, 392–402).
  • No session exists that was created by a passkey sign-in but isn't marked as both factors.

Wrong if: after a failed stamp, the cookie still works or a session row remains.

S10 · Journey 5 is proven in a real browser on both hosts

From R63 journey 5 and R67. In real Chrome with Chrome's virtual authenticator, on local workerd with D1 and on Node with better-sqlite3:

  1. a person signs in with Google, confirms with their app, and adds a passkey;
  2. signs out;
  3. clicks Continue with Passkey, with fingerprint, face or PIN on;
  4. lands on their account page;
  5. invites a person, with no confirmation step.

The same journey with user verification off stops at step 3, signed out. Both runs must fail on today's build.

Wrong if: the journey passes on f3b2b88b, or runs on one host only.

S11 · The "stays off" fallback is gone

The approved design kept passkey sign-in off until the user-verification hook was proven. This feature proves it and removes the fallback:

  • the test assertion that both routes answer 404;
  • the guidance that says passkeys only confirm, in .agents/skills/verify-auth/.

Wrong if: any test or guidance still says passkey sign-in is off.

S12 · Each passkey sign-in is recorded, as Google and GitHub sign-ins are

Today every Google or GitHub sign-in callback writes one sign_in_audit row: kind sign-in, the person (or anonymous), the outcome succeeded or failed, and the method (sign-in-http-handler.ts:383–390). A passkey sign-in MUST do the same, with method passkey:

  • every verify request writes one row;
  • a success records the person and succeeded;
  • a refusal (no user verification, unknown passkey, a person who can't sign in) records anonymous and failed.

If the row can't be written, the sign-in fails with no session, as it does for Google or GitHub today (S9).

Wrong if: a passkey sign-in, successful or refused, leaves no row, or a row names the wrong outcome.
