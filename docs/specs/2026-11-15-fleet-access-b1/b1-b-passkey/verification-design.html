B1-B · Passkey sign-in: Verification Design

How each rule will be shown to hold. Nothing here has been run yet.

  • Who runs it: the paired Verifier, on the pinned PR commit.
  • Where: heavy runs (both hosts, real Chrome) on Sunclaw, as you decided.
  • No wall clock: every time-dependent check moves the harness's controlled clock. Waits are on events only, as B1-A delivers.

The three things for you

  • V8, journey 5 in real Chrome on both hosts: add a passkey, sign out, sign in with it, invite someone with no confirmation step. Run again with user verification off: refused.
  • V3 and V4: no session without user verification. With it, a session that counts as both factors, and no token in the answer.
  • Every check must fail on today's build or on a deliberate break, so a green run can't hide a gap the way the old 404 test did.

None here. V7 checks the button as your autofill decision sets it.

Your approved Verification Design names the driver: "a real-browser driver … over the Chrome DevTools Protocol (headless Chrome; not Playwright). It uses CDP's virtual WebAuthn authenticator for passkeys" (journey SO14). Your rule R67 puts passkey sign-in's proof on local runs. V8 is that, for journey 5.

How the checks fit together

Key: blue is the unit lane, teal the host lane, amber real Chrome, green the clean-up check.

What the host checks share

V2 to V6 are cases in one new host test, packages/sign-in-test-support/src/people-passkey-sign-in.host.e2e.test.ts. It reuses what the existing passkey tests use:

  • startLocalAuthHarness(), with the controlled clock and the Turnstile stand-in (harness.turnstile.issueToken({ action, hostname, verdict }));
  • a person signed in with Google and confirmed with their app (signInConfirmedPeopleBrowser);
  • a passkey registered with user verification by the software authenticator (createSoftwarePasskeyAuthenticator, registerBrowserPasskey);
  • then sign out, so the browser has no session before the passkey sign-in.

Both hosts: the harness picks Cloudflare (local workerd with D1) by default and Node with better-sqlite3 when SIGN_IN_TEST_HOST=node (local-auth-harness.ts:219–221). Every host check runs twice: pnpm test:e2e:host <file> and SIGN_IN_TEST_HOST=node pnpm test:e2e:host <file>.

On today's build, every case in this file fails at its first passkey sign-in request, which answers 404.

The checks

V1 · The two routes are public; nothing else opens (S1)

  • Test: unit cases for isPublicSignInRoute:
    • GET /api/auth/passkey/generate-authenticate-options and POST /api/auth/passkey/verify-authentication are public;
    • the same paths with the other method aren't;
    • /api/auth/passkey/delete-passkey isn't, by either method.
  • Fails on: today's code (the first two aren't public), and a deliberate break that adds delete-passkey.

V2 · The challenge request needs a Turnstile pass, through the public service (S2)

  • Test: host cases, one per check: no token; a token Turnstile rejects; a token for sign_in_social; a token already used; siteverify unreachable. Each challenge request through the public service:
    • is refused;
    • leaves the verification table unchanged;
    • sets no challenge cookie;
    • logs captcha-refused with action passkey_sign_in and its reason.
    An accepted token gets 200, one new verification row and the cookie.
  • Reference: R52 and V44; today's private-provider cases (turnstile-provider.host.e2e.test.ts:76–167) give the expected reasons.
  • Fails on: a deliberate break that removes /passkey/generate-authenticate-options from the captcha plugin's endpoints (turnstile-captcha.ts:136): the no-token case gets a challenge.

V3 · Without user verification, no session (S3, S12)

  • Test: host case. With an accepted Turnstile token, a challenge, then the software authenticator's answer with userVerified: false.
  • Passes when:
    • the verify request gets 401 with code USER_VERIFICATION_REQUIRED;
    • the answer has no set-cookie for the session;
    • the session table is unchanged, and so is the passkey's counter;
    • sending the same answer again gets 400, challenge not found;
    • one new sign_in_audit row: kind sign-in, actor anonymous, outcome failed, method passkey.
  • Fails on: a deliberate break that removes the user-verification check from authentication.afterVerification (provider-configuration.ts:445–451): a session appears.

V4 · With user verification, both factors; no token in the body; a confirmed session or none (S4, S6, S9, S12)

  • Test: host cases, and unit cases for completePasskeySignIn.
  • Passes when, on a user-verified answer:
    • 200, with a session cookie;
    • no token in the body: the cookie's session token doesn't appear anywhere in the response body's text;
    • both factors: the new session row has secondFactorMethod = 'passkey' and secondFactorAt equal to the controlled clock's time at the request;
    • a protected change goes through: with that cookie, inviting a person (POST /api/auth/organization/invite-member) succeeds with no confirmation step;
    • the window still closes: after the controlled clock moves 15 minutes and 1 millisecond, the same invite is refused with "a second factor is needed";
    • the record: one new sign_in_audit row with the person, succeeded and passkey.
  • Passes when the stamp fails (S9): a new harness control, harness.makePasskeyStampUnavailable(), makes the next stamp write fail.
    • The verify request gets 503 {"error":"sign-in-unavailable"}.
    • The person's session rows are as before the request.
    • /api/auth/get-session with whatever cookie came back returns no session.
    The control follows makeLimiterUnavailable(): POST /__auth-proof/passkey-stamp-unavailable, handled in test-fixtures/node-auth-proof-host.ts beside its limiter-unavailable case (line 384) and in the workerd proof application beside auth-proof-rate-limit-bindings.ts:14. On Node it wraps store.factors.stampSession once, through decorateNodeProofStore (test-fixtures/node-proof-store.ts). On workerd it fails the next D1 batch that updates session.secondFactorAt, through recordingD1Database (test-fixtures/recording-d1-database.ts). Either way the store answers store-unavailable.
  • Unit cases (sign-in-test-support/src/core-tests/passkey-sign-in-completion.unit.test.ts):
    • a 200 with one session stamps, then records succeeded;
    • session-not-live throws, with no record;
    • a throwing record throws;
    • a 200 with no session throws;
    • a 401 records failed with anonymous and stamps nothing.
  • Fails on: today's build (no stamp: the invite asks for a factor), and three deliberate breaks, each run on its own:
    • skipping the /passkey/verify-authentication path in the token-stripping condition: the token appears in the body;
    • skipping the stamp: the invite is refused;
    • catching the stamp failure instead of throwing: a session remains after the 503 case.

V5 · Only a person who may sign in today (S5)

  • Test: host cases.
    • A member registers a passkey, then the owner removes them, so they have no membership left. Their user-verified passkey sign-in is refused, with no session.
    • An answer from a credential the service doesn't know gets 401, with no session.
    • A person with one membership signs in with a passkey and their session's activeOrganizationId is that organization.
  • Reference: today's Google and GitHub admission (ensurePersonActive), the same cases on the social path.
  • Fails on: a deliberate break that skips ensurePersonActive in the session-create hook: the removed member gets a session.

V6 · The flood limit covers it (S8)

  • Test: a host case in people-request-limits.host.e2e.test.ts, on the real binding as B1-A leaves it. From one browser address, eleven challenge requests within the window, each with a fresh accepted token.
    • The eleventh gets 429 with Retry-After, and no new verification row.
    • A request from a second browser address gets 200.
  • Fails on: a deliberate break that moves /api/auth/passkey/ to the other class (300 per minute): no 429.

V7 · The sign-in page's pieces (S7)

  • Host test: the served /sign-in page has:
    • an island root with state { kind: 'passkey-sign-in', continueLocation: '/owner-ready' }, or with ?authorize=… when the page was opened from the CLI;
    • the #sign-in-passkey-captcha container with data-action="passkey_sign_in";
    • the island script, carrying the page's nonce.
    The page's security policy is unchanged (served-page-csp.host.e2e.test.ts passes as it is).
  • Unit tests, in the unit lane with Vitest's DOM environment as the existing island tests use:
    • attachPasskeySignInTurnstile leaves other requests unchanged;
    • for the challenge request, it calls reset then execute on a fake window.turnstile, and sets x-captcha-response to the token the fake's callback gives;
    • two challenge requests get two different tokens;
    • an error-callback rejects;
    • onSignInTurnstileReady dispatches sign-in-turnstile-ready.
  • Autofill, as you decide: with the recommended answer, loading the sign-in page in V8 sends no challenge request (counted from the browser's network events). With autofill kept, this check is reversed: the page sends exactly one.
  • Fails on: today's page (no root, no container), and a deliberate break that sets the same token twice.

V8 · Journey 5 in real Chrome, on both hosts (S3, S4, S7, S10)

Proven by: the existing real-browser test driving journey 5 with Chrome's virtual authenticator, on both hosts, and failing on today's build.

  • Where: sign-in-native-browser.host.e2e.test.ts, which already runs observeNativeSignInBrowser(host) for 'node' and 'cloudflare'. A new scenario step list, passkey-journey, in test-fixtures/native-browser-scenario.ts.
  • The virtual authenticator: new calls through native-browser-protocol.ts's existing call:
    • WebAuthn.enable;
    • WebAuthn.addVirtualAuthenticator with protocol: 'ctap2', transport: 'internal', hasResidentKey: true, hasUserVerification: true, isUserVerified: true, automaticPresenceSimulation: true;
    • WebAuthn.setUserVerified to switch it off.
    Each is a DevTools command whose reply ends the wait.
  • Turnstile in the browser: the page loads Turnstile's script from Cloudflare, which the test doesn't reach. The scenario intercepts that one script URL with Fetch.enable and answers it with Fetch.fulfillRequest. The answer is a stand-in that:
    • defines window.turnstile with render, reset and execute;
    • hands each execute a token the harness issued for passkey_sign_in (harness.turnstile.issueToken);
    • then calls onSignInTurnstileReady.
    The page's own widget code and the service's siteverify check run as written. Only Cloudflare's script is replaced.
  • The steps:
    1. sign in with Google over the controlled provider, as the test does today, and confirm with the app (codes computed at the controlled time);
    2. on the passkey page, click Add passkey; the virtual authenticator answers;
    3. sign out;
    4. on /sign-in, click Continue with Passkey;
    5. the page lands on /owner-ready and then the account page;
    6. invite a person from the page; the invitation is created with no confirmation step;
    7. document.cookie has no session token readable by script, and no response body seen by the page contains it.
  • The refusal run: the same steps 1 to 3, then WebAuthn.setUserVerified(false), then step 4. The page shows Better Auth UI's error notice, stays on /sign-in, and /api/auth/get-session returns no session.
  • Also read: at 400 px, the passkey button's left edge matches the Google and GitHub buttons'.
  • Fails on: today's build: there's no button at step 4, and both routes answer 404.
  • Unverified:
    • physical authenticators;
    • real Turnstile;
    • staging, which covers journey 5 from adding the passkey onward, in BG's run (R65).
