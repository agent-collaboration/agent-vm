What the host checks share

V2 to V6 are cases in one new host test, packages/sign-in-test-support/src/people-passkey-sign-in.host.e2e.test.ts. It reuses what the existing passkey tests use:

  • startLocalAuthHarness(), with the controlled clock and the Turnstile stand-in (harness.turnstile.issueToken({ action, hostname, verdict }));

  • a passkey registered with user verification by the software authenticator (createSoftwarePasskeyAuthenticator, registerBrowserPasskey);
  • then sign out, so the browser has no session before the passkey sign-in.

Both hosts: the harness picks Cloudflare (local workerd with D1) by default and Node with better-sqlite3 when SIGN_IN_TEST_HOST=node (local-auth-harness.ts:219–221). Every host check runs twice: pnpm test:e2e:host <file> and SIGN_IN_TEST_HOST=node pnpm test:e2e:host <file>.

On today's build, every case in this file fails at its first passkey sign-in request, which answers 404.

V7 · The sign-in page's pieces (S7)

  • Host test: the served /sign-in page has:
    • an island root with state { kind: 'passkey-sign-in', continueLocation: '/owner-ready' }, or with ?authorize=… when the page was opened from the CLI;
    • the #sign-in-passkey-captcha container with data-action="passkey_sign_in";
    • the island script, carrying the page's nonce.
    The page's security policy is unchanged (served-page-csp.host.e2e.test.ts passes as it is).
  • Unit tests, in the unit lane with Vitest's DOM environment as the existing island tests use:
    • attachPasskeySignInTurnstile leaves other requests unchanged;
    • for the challenge request, it calls reset then execute on a fake window.turnstile, and sets x-captcha-response to the token the fake's callback gives;
    • two challenge requests get two different tokens;
    • overlap: two token requests started together, with the fake's first callback held. The second doesn't call execute until the first settles. Releasing the callbacks in order settles each request with its own token. When the first gets error-callback, it rejects and the second still gets a token. A helper that overwrites the first resolver, or gives both requests one token, fails this case;
    • each of error-callback, expired-callback and timeout-callback rejects the pending attempt, and the next call starts a new one;
    • onSignInTurnstileReady sets ready and dispatches sign-in-turnstile-ready;
    • a script load failure: an error event on #sign-in-turnstile-script sets failed and dispatches sign-in-turnstile-failed. A token request pending at that moment rejects, and so does every later one, at once.
  • Hegel family for the token queue (owner rule, 15 Nov):
    • The test: packages/sign-in-core/src/pages/islands/passkey-sign-in-turnstile-queue.hegel.unit.test.ts, in the unit lane. @hegeldev/hegel 0.4.10, the version sign-in-test-support already pins, is added as a dev dependency of sign-in-core, because the island module isn't exported and there are no test-only exports. Settings: derandomize: true, hegel.Database.disabled.
    • Starting state and protocol: exactly as the Program Design defines them. Every run starts at { script: 'loading', executing: null, waiting: [] }. Every event is valid in every state, with the defined no-op where it applies, so nothing is filtered out.
    • Generators: sequences of 0 to 40 events drawn from all five kinds, in any order and any state. Request ids are fresh and increasing. Tokens are distinct strings. scriptReady and scriptFailed may appear any number of times, including after each other, to exercise the no-ops and terminal failure. Stray widget events with nothing executing are generated too.
    • Drain: after the generated prefix, the test appends a deterministic tail that brings the run to a drained end. That's scriptReady if still loading, then one widgetToken per remaining started or waiting request. In a second variant, the tail is a single scriptFailed. Completion is asserted only after the drain, so a run that never ends can't count as proof.
    • The model: written in the test from the protocol, independently of the code, as three plain values: a script flag, an executing id or null, and a waiting array. After each event, the transition's next state and effect list equal the model's.
    • Checks: the safety invariants after every step, and the completion property at the drained end (both listed on the Program Design).
    • The execution effect pair: every execution the model starts emits ensureWidget, then resetAndExecute, from idle, from scriptReady or in a handoff. The model holds no "rendered" fact, so scriptReady on its own and scriptReady, request, token reach the same state and give the same effects for the next request.
    • Render-once is the runner's, checked separately: a unit test drives the DOM runner with a fake window.turnstile through two executions. render is called once, and reset and execute once per execution.
    • Every branch is reached. The family records which protocol branch each step took, and fails if any of these was never hit:
      • a request while loading;
      • scriptReady with and without waiting work;
      • a request while ready and idle, and while ready and busy;
      • a token or failure with and without a waiting head;
      • scriptFailed while loading, while idle, and while executing with waiters;
      • a request after failure;
      • each no-op.
    • Wrong builds the family must catch, each run by the Verifier on its own, then reverted. Each one is defined by what it changes. The pass condition is that Hegel reports a counterexample of that class; the actual shrunk trace and the first state or effect that differs from the model are recorded in the evidence, with no particular exact shrink required.
      • Premature start: tokenRequested while busy executes at once instead of queueing. The class is ready, then a request, then a second request: the second request's effects differ from the model at once, and the safety rule "a new execution never starts while another is live" fails.
      • Lost rejection: scriptFailed rejects the executing request but not the waiting ones. The class is two or more requests, then scriptFailed: the effect list differs, and completion fails after the drain.
      • LIFO: the next execution starts from the back of waiting. The class is ready, then three requests, then a token: the handoff starts the wrong id, and arrival order fails.
  • Click only, your 15 Nov choice: V8 counts the browser's network events while the sign-in page loads, on Chrome, which supports autofill. With passkeyPlugin({ autoFill: false }), loading sends no challenge request. This runs through the real island and Better Auth UI's own hook, not a fake.
    • Fails on: a deliberate break that leaves the plugin at its default (passkeyPlugin()): loading sends one challenge request.
  • Fails on: today's page (no root, no container); a deliberate break that sets the same token twice; and one that ignores the script's load error. The DOM case starts a token request, dispatches the error event, lets pending promise callbacks run, then asserts the request is settled as rejected. On the broken build it's still pending, so the assertion fails at once; nothing waits.

V8 · Journey 5 in real Chrome, on both hosts (S3, S4, S7, S10)

Proven by: the existing real-browser test driving journey 5 with Chrome's virtual authenticator, on both hosts, and failing on today's build.

  • Where: sign-in-native-browser.host.e2e.test.ts, which already runs observeNativeSignInBrowser(host) for 'node' and 'cloudflare'. A new scenario step list, passkey-journey, in test-fixtures/native-browser-scenario.ts.
  • A localhost address: Chrome refuses WebAuthn on an IP-address origin, and today's harness serves http://127.0.0.1:<port>. The scenario starts the harness with issuerHostname: 'localhost', and Chrome is launched with --host-resolver-rules=MAP localhost 127.0.0.1 (Program Design). The evidence records the Chrome version and the origin. On the unchanged harness, step 2 fails in the browser before any request reaches the service.
  • The virtual authenticator: new calls through native-browser-protocol.ts's existing call:
    • WebAuthn.enable;
    • WebAuthn.addVirtualAuthenticator with protocol: 'ctap2', transport: 'internal', hasResidentKey: true, hasUserVerification: true, isUserVerified: true, automaticPresenceSimulation: true;
    • WebAuthn.setResponseOverrideBits({authenticatorId, isBadUV: true}) for the refusal run: the authenticator still signs a real assertion with its credential key, but with the user-verified bit cleared, so the server, not the browser, must refuse it. (setUserVerified(false) was wrong: Chrome's virtual device then refuses before any assertion is sent, so the server is never asked; pinned Chrome source virtual_ctap2_device.cc:1046–1050 versus :1750–1772.)
    Each is a DevTools command whose reply ends the wait.
  • Turnstile in the browser: the page loads Turnstile's script from Cloudflare, which the test doesn't reach. The scenario intercepts that one script URL with Fetch.enable and answers it with Fetch.fulfillRequest. The answer is a stand-in that:
    • defines window.turnstile with render, reset and execute;
    • hands each execute a token the harness issued for passkey_sign_in (harness.turnstile.issueToken);
    • then calls onSignInTurnstileReady.
    The page's own widget code and the service's siteverify check run as written. Only Cloudflare's script is replaced.
  • The steps:
    1. sign in with Google over the controlled provider, as the test does today, and confirm with the app (codes computed at the controlled time);
    2. on the passkey page, click Add passkey; the virtual authenticator answers;
    3. sign out: clear the browser's cookies (the native sign-out route is closed by B1-A, session-read-public-routes.unit.test.ts), so the browser has no session;
    4. on /sign-in, click Continue with Passkey;
    5. the page lands on /owner-ready and then the account page;
    6. invite a person from the signed-in page: the page's own context posts POST /api/auth/organization/invite-member with its cookie (no invite button exists until B1-C's People page, whose journey will click it). The invitation is created with no confirmation step, checked in the stored invitations;
    7. document.cookie has no session token readable by script, and no response body seen by the page contains it.
  • The refusal run: the same steps 1 to 3, then WebAuthn.setResponseOverrideBits({isBadUV: true}), then step 4. The verify request reaches the service and is refused with 401 and its error code. The page shows Better Auth UI's error notice and stays on /sign-in, and /api/auth/get-session returns no session. The override is then reset (isBadUV: false) before any positive or CLI step.
  • The command-line run: after steps 1 to 3, the scenario starts the real owner CLI with loginThroughNativeOwnerCli({ target, repositoryRoot, browser }) (native-cli-proof.ts:92). Its browser callback navigates Chrome to the CLI's own sign-in?authorize=… address and clicks Continue with Passkey.
    • Passes when: Chrome follows the real continuation through /owner-ready?authorize=…; the CLI's loopback receives its code; the CLI exits 0 with the person's token in its private cache.
    • Fails on: a deliberate break where the button navigates to /owner-ready without its query. The plain run still passes, but this one fails: the CLI never gets its code.
  • The Turnstile-failure run: the scenario answers Turnstile's script URL with a failed load (Fetch.failRequest), then clicks Continue with Passkey.
    • The error notice "Sign-in verification is unavailable. Reload the page to try again." appears.
    • The button is enabled again.
    • No challenge request is sent, and no session exists.
  • Also read: at 400 px, the passkey button's left edge matches the Google and GitHub buttons'.
  • Fails on: today's build: there's no button at step 4, and both routes answer 404. Every run is on both hosts.
