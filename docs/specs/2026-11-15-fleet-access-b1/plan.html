B1 · Plan: verification, acceptance, review

This page explains the process, not the design. It covers three things. First, how every B1 obligation gets verified, and what exactly is checked. Second, how acceptance happens, with the map from your outcomes to evidence. Third, what the reviewer gets, and how they check the work against your words and your design so the old mistakes don't repeat.

1. The yardstick is your approved design. It's never my workstream goal. 2. An outcome is accepted only when all of it is proven, at the boundary your Verification Design names. A PR that proves part of it is "partial", never "done". 3. The reviewer gets your design, your first-hand decisions, the PRs and the evidence. They get nothing I wrote except as claims to check.

1. How verification fully happens

Who: the paired Verifier, a Sol session that didn't write the code (the Implementer is Opus). It observes; it never repairs product code. Where: both builds your design names. Those are local workerd with D1, and Node with SQLite. Both run on a controlled clock with no real time anywhere in tests or helpers. Heavy runs go to Sunclaw. What it records: the build pin (switchboard commit, plus central's commit where central is involved), Node and Chrome versions, the command, the counts and exit codes, and file hashes. All of it goes into one evidence folder per run.

What counts: each case names the wrong build that must make it fail. A case that would still pass on the wrong build proves nothing and is rewritten. A success message or exit code alone never counts. The Verifier reads the effect: the row in the database, the page served, the refusal with nothing changed.

2. How acceptance happens, and the map

The Lead's five checks before accepting:

  1. The requirement is met: every case for the outcome passes.
  2. Tests: the repository's gates pass, with commands, counts and exit codes.
  3. Real path: the Verifier's observation ran at the boundary the design names.
  4. No drift: the code matches the Program Design.
  5. What isn't verified is named.

I open the decisive code and evidence myself; a tidy summary isn't enough. A PR can merge only after this, the reviewer's READY and green CI, and only once your stop lifts.

3. The packets: what each role gets, from whom, and where

B1's remaining work is cut into seven deliverable items. Each is something tangible the roles can finish in 2–4 hours, and each has a gate that must pass before the next one starts. Every item gets one folder, and everything for it lives there: the brief, what the Implementer hands back, what the Verifier saw, my check, the reviewer's report and my acceptance. Open the folder and you see exactly what each role was given and what it returned.

The folder: docs/specs/2026-11-15-fleet-access-b1/work/<item>/, for example work/b1-1-honest-tests/. None is created yet: your stop holds.

Key: amber is the Lead, teal the Implementer, violet the Verifier, blue the independent reviewer, green you and the gate.

Who: the Implementer (Opus high), on one item at a time.

Gets exactly:

Never gets: the Implementer's own results as proof. It runs every check itself.

Never gets: my plan, summaries or rulings as a standard.

Before review: I open the code and the evidence myself and write work/<item>/lead-check.html. It runs the five checks from section 2, each citing a file and line. The reviewer gets it as a claim.

To accept, I hold:

  • the acceptance map: obligation → check → evidence → accepted;
  • the Verifier's observation and evidence;
  • the reviewer's report, with each finding disposed of at its anchor.

Writes: work/<item>/lead-acceptance.html, with the map and each reviewer finding fixed, rejected with evidence, or brought to you.

The rule: anything not delivered comes to you before I accept. Then the gate passes and the next item starts.

How the reviewer validates

  1. Answer the first question: list what the change drops against your words, the earlier designs and the old tests.
  2. For each obligation, read your design row and any linked words of yours first, and write down what "done" means before opening the code.
  3. Read the code at the pinned commit, not the PR description.
  4. Open the evidence and check that it ran on that build, at the boundary the design names, and fails on the base commit.
  5. Any place my records narrow, defer or reinterpret an obligation is a finding. Never adopt it.
  6. A decision counts as yours only with a link to your own words. A relay stays "relayed, unconfirmed".

  • pnpm check, pnpm test:unit and pnpm test:e2e:host are green;
  • CI is green;
  • the reviewer says READY;
  • anything not delivered has been brought to you.
