B1 · Plan: verification, acceptance, review

This page explains the process, not the design. It covers three things. First, how every B1 obligation gets verified, and what exactly is checked. Second, how acceptance happens, with the map from your outcomes to evidence. Third, what the reviewer gets, and how they check the work against your words and your design so the old mistakes don't repeat.

1. The yardstick is your approved design. It's never my workstream goal. 2. An outcome is accepted only when all of it is proven, at the boundary your Verification Design names. A PR that proves part of it is "partial", never "done". 3. The reviewer gets your design, your first-hand decisions, the PRs and the evidence. They get nothing I wrote except as claims to check.

1. How verification fully happens

Who: the paired Verifier, a Sol session that didn't write the code (the Implementer is Opus). It observes; it never repairs product code. Where: both builds your design names. Those are local workerd with D1, and Node with SQLite. Both run on a controlled clock with no real time anywhere in tests or helpers. Heavy runs go to Sunclaw. What it records: the build pin (switchboard commit, plus central's commit where central is involved), Node and Chrome versions, the command, the counts and exit codes, and file hashes. All of it goes into one evidence folder per run.

What counts: each case names the wrong build that must make it fail. A case that would still pass on the wrong build proves nothing and is rewritten. A success message or exit code alone never counts. The Verifier reads the effect: the row in the database, the page served, the refusal with nothing changed.

2. How acceptance happens, and the map

The Lead's five checks before accepting:

  1. The requirement is met: every case for the outcome passes.
  2. Tests: the repository's gates pass, with commands, counts and exit codes.
  3. Real path: the Verifier's observation ran at the boundary the design names.
  4. No drift: the code matches the Program Design.
  5. What isn't verified is named.

I open the decisive code and evidence myself; a tidy summary isn't enough. A PR can merge only after this, the reviewer's READY and green CI, and only once your stop lifts.

3. What the reviewer gets, and how they check

Who: a fresh Sol xhigh session with no history of writing this work, using the role-checker and design-review skills and the principles verify-before-accepting, prove-it-works and write-tests-that-can-fail. It writes its report as an HTML page in the shared audit format.

How the reviewer validates

  1. For each obligation, read your design row and any linked words of yours first, then write down what "done" means before opening the code.
  2. Read the code at the pinned commit, not the PR description.
  3. Open the evidence and check it ran on that build, at the boundary the design names, and would fail on the wrong build.
  4. Any place my records narrow, defer or reinterpret an obligation is a finding. Never adopt it.
  5. A decision counts as yours only with a link to your own words. A relay stays "relayed, unconfirmed".
  6. Report every obligation: delivered, partial, missing or contradicted, with "fully fixed means".

Every page then gets a Terra medium check before it reaches you.
