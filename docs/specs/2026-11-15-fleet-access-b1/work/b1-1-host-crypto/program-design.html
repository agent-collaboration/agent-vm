B1-1 · The host supplies all cryptography: Program Design

How rules S1–S6 of the Specification are built, file by file, in switchboard at main f3b2b88b. In short: the host contract gets one new capability, crypto, shaped like the standard Web Crypto. Six call sites take it instead of the runtime global. The shared web capabilities builder hands it in for both hosts and the CLI, and the architecture check gains one rule.

The three things for you

The dependency picture (below): the core defines what it needs, and the hosts supply it. Nothing in the core points at a runtime. The new rule in the architecture check (below) rejects the runtime's crypto, clock and timers anywhere in the core.

None. The one structural choice, passing crypto explicitly rather than through a helper object, is mine within your rule, and is explained below.

It's the same pattern your approved design already uses for the clock, IDs and deadlines: an interface in the core, with each runtime injecting its own. Your words: "you inject stukff not pkul out engines" (U23). The trace table maps every rule to its owner and proof.

The parts and which way they depend

Arrows point from the package that depends to the package it depends on. The core depends on no runtime. Hosts depend on the core, never the reverse (R30). Only the shared web capabilities builder touches the runtime's globalThis.crypto.

Key: amber is the core, green is the only place the runtime's crypto is read, blue are the hosts, violet is test support. The edges are unchanged from today. B1-1 adds no package and no dependency.

The new capability

It's added to the host contract in packages/sign-in-core/src/contracts/sign-in-platform.ts, beside SignInClock, SignInIdSource and SignInDeadlines. It's a subset of the standard Web Crypto, so both runtimes satisfy it with their own globalThis.crypto, and a test can wrap it to record calls or return fixed bytes. The page nonce gets a branded type, so a page can't be built without one minted from the capability.

How a request reaches crypto, before and after

Serving a sign-in page (S1, the nonce)

Before: page-document.tsx:181 minted the nonce itself with crypto.randomUUID(). After: pageDocument requires a nonce: PageNonce prop and no longer mints anything. The two renderers that call it, renderOwnerPage and renderFactorPage, take nonce from their callers: minimalOwnerPage (called at sign-in-http-handler.ts:272) and renderFactorFormResponse (called at lines 346 and 391). Each caller already holds configuration.platform, and mints with mintPageNonce(configuration.platform.crypto). pageContentSecurityPolicy(nonce, challenge) is unchanged.

Forwarding an admin action to central (S1, S2)

obtainPersonFleetCredential widens its platform pick from 'clock' | 'ids' to 'clock' | 'ids' | 'crypto'. The line globalThis.crypto.getRandomValues(verifierBytes) (fleet-admin-forwarding.ts:156) becomes props.platform.crypto.getRandomValues(verifierBytes).

Reading a signed organization statement (S2)

readOrganizationStatementFacts(statement) becomes readOrganizationStatementFacts(crypto, statement). Its two callers in organization-stamp-renewal.ts (lines 306 and 346) already receive the platform's clock, so they also receive crypto from the same platform.

What each host does

  • packages/sign-in-platform-web/src/index.ts: createWebSignInCapabilities(clock?, deadlines?, crypto?) returns Pick<SignInPlatform, 'clock' | 'ids' | 'deadlines' | 'crypto'>. Its default crypto is the runtime's globalThis.crypto, typed as SignInCrypto. This file is the one place a production package reads it, and it adds no rule (S4). Its README line changes to say it also supplies crypto.
  • Cloudflare host (worker-configuration.ts:26) and Node host (sign-in-node-host.ts:75): no change of their own. They already spread createWebSignInCapabilities(...) into the platform, so crypto arrives with it.
  • Owner CLI (fleet-cli-commands.ts:61): it already builds createWebSignInCapabilities(). It passes capabilities.crypto to the proof-key store and the credential and admin commands.
  • Test support: a new fixture packages/sign-in-test-support/src/test-fixtures/recording-sign-in-crypto.ts wraps a real Web Crypto. It records each call (operation name and argument sizes, never key material) and can return fixed random bytes. Every place a test builds a SignInPlatform (for example storage-cases/storage-case-context.ts) adds crypto, using this fixture or the web default.

The architecture check's new rule

In scripts/audit-portal-architecture.ts, two changes, both limited to packages/sign-in-core/src/ as your proof row U23 asks:

  1. Read .tsx too: collectFilesUnderDirectory also returns .tsx files under packages/sign-in-core/src/. Other packages' file lists stay as they are, so no other check widens.
  2. Reject runtime globals: collectAuthCoreViolations adds a rule that walks the TypeScript syntax tree of each non-test core file and reports:
    • the identifier crypto used as a free global (not a property such as platform.crypto, and not a local binding or parameter);
    • globalThis.crypto;
    • Math.random, Date.now, performance.now, setTimeout and setInterval;
    • new Date() with no argument.
    String and template-literal contents are never walked, so browser scripts written as text aren't flagged. Test files (*.test.ts, *.test.tsx) are skipped here; their own time rule is B1-2's.

The rule applies inside better-auth/ too, which is stricter than proof row U23's wording ("outside the Better Auth boundary module"). That module's exemption exists so it can import Better Auth. Our own code in it, such as fleet-admin-forwarding.ts, still follows R30. On main today this rule reports exactly the six sites listed on the Requirements page.

Failure and concurrency

  • No new state, store or background work. Every capability call is a pure request-scoped computation, the same as the global it replaces.
  • A capability that throws propagates out of the page render or the admin forwarding, the same way a throwing global did. The existing handler turns it into its generic server-error response. Page rendering writes nothing, and admin forwarding writes nothing itself: it calls central and the sign-in service's own routes, so a throw before the call leaves no change.
  • Concurrent requests each call the capability independently. Web Crypto is safe to call concurrently on both runtimes, so there's no shared mutable state to guard.
