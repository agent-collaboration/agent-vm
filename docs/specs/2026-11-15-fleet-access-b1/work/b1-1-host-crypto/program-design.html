B1-1 · The host supplies all cryptography: Program Design

How rules S1–S6 of the Specification are built, file by file, in switchboard at main f3b2b88b. In short:

  • The host contract gets one new capability, crypto, shaped like the standard Web Crypto.
  • The six call sites take it instead of the runtime global.
  • The shared web capabilities builder hands it in for both hosts and the CLI.
  • The architecture check gains one rule.

The three things for you

The dependency picture (below): the core defines what it needs, and the hosts supply it. Nothing in the core points at a runtime.

The new rule in the architecture check (below) rejects the runtime's crypto, clock and timers anywhere in the core, including code inside ${…} in a template.

None for people. One decision for code outside this repository: the public exports of the two published packages (sign-in-core and sign-in-owner-cli) gain a required crypto. That's decision D1 on the Plan.

It's the same pattern your approved design already uses for the clock, IDs and deadlines: an interface in the core, with each runtime injecting its own. Your words (approved Requirements, line 174, U23): "you inject stukff not pkul out engines". The trace table maps every rule to its owner and proof.

The parts and which way they depend

Arrows point from the package that depends to the package it depends on. The core depends on no runtime. Hosts depend on the core, never the reverse (R30). Only the shared web capabilities builder reads the runtime's globalThis.crypto.

Key: amber is the core, green is the only place the runtime's crypto is read, blue are the hosts, violet is test support. These edges exist today. B1-1 adds no package and no dependency.

The new capability and the page nonce

It's added to the host contract in packages/sign-in-core/src/contracts/sign-in-platform.ts, beside SignInClock, SignInIdSource and SignInDeadlines. It's a subset of the standard Web Crypto, so both runtimes satisfy it with their own globalThis.crypto, and a test can wrap it to record calls or return fixed bytes.

The nonce helper lives in contracts/, not pages/, because the package's import map sends #sign-in-core/pages/* to .tsx files and #sign-in-core/* to .ts files (packages/sign-in-core/package.json, imports).

How a request reaches crypto, before and after

In the sequence diagrams, participants are coloured automatically. The colour carries no meaning.

Serving a sign-in page (S1, the nonce)

  • Before: page-document.tsx:181 minted the nonce itself with crypto.randomUUID().
  • After: pageDocument requires nonce: PageNonce and mints nothing. renderOwnerPage and renderFactorPage pass nonce through.
  • Who mints: the two response builders that decide whether to render HTML. minimalOwnerPage always renders, so it always mints. renderFactorFormResponse mints only on the branch that calls renderFactorPage. Its earlier returns (not a POST, not an offered path, the request isn't asking for HTML, or the 303 redirect) make no crypto call.
  • Who hands it in: the handler, at sign-in-http-handler.ts:272, :346 and :391, passes crypto: configuration.platform.crypto.
  • Unchanged: pageContentSecurityPolicy(nonce, challenge).

Forwarding an admin action to central (S1, S2)

Both platform picks in fleet-admin-forwarding.ts add 'crypto':

  • forwardFleetAdminRequest (lines 54–58), from 'centralClient' | 'clock' | 'ids'. It creates the key and signs central's proof itself (lines 82–106).
  • obtainPersonFleetCredential (lines 146–150), from 'clock' | 'ids'.

Line 156, globalThis.crypto.getRandomValues(verifierBytes), becomes props.platform.crypto.getRandomValues(verifierBytes). The verifier goes in the token request (code_verifier) and its S256 challenge in the authorization request (code_challenge), both sent through the self-call signIn.

What each host does

  • sign-in-platform-web: its default crypto is the runtime's globalThis.crypto, typed as SignInCrypto. This is the one production place that reads it, and it adds no rule (S4).
  • Cloudflare host (worker-configuration.ts:26) and Node host (sign-in-node-host.ts:75): no edits. They already spread createWebSignInCapabilities(...) into the platform, so crypto arrives with it.
  • Owner CLI: as in the CLI path.
  • Test support:
    • A new sign-in-test-support/src/test-fixtures/recording-sign-in-capabilities.ts wraps the real Web Crypto, clock, ID source and central client. It records each call: operation, algorithm and a SHA-256 of each input, never key material. It can return fixed random bytes.
    • Every place a test builds a SignInPlatform or renewal props adds crypto. That includes storage-cases/storage-case-context.ts, the stamp and central-recovery case files and test-fixtures/controlled-central-admin.ts.

The architecture check's new rule

In scripts/audit-portal-architecture.ts, two changes, both limited to packages/sign-in-core/src/, as your proof row U23 asks:

  1. Read .tsx too: collectFilesUnderDirectory (lines 1272–1288) also returns .tsx files when it walks packages/sign-in-core/src/. Other packages' file lists don't change, so no other check widens.
  2. Reject runtime globals: collectAuthCoreViolations (lines 1250–1270) adds a rule that walks the TypeScript syntax tree of each non-test core file. It reports:
    • the identifier crypto used as a free global (not a property such as platform.crypto, and not a local binding or parameter);
    • globalThis.crypto;
    • Math.random, Date.now, performance.now, setTimeout and setInterval;
    • new Date() with no argument;
    • globalThis[...] with a computed key.
    Templates: literal text of strings and templates is not code, so browser scripts written as text aren't flagged. The expressions inside a template's ${…} are code the service runs, so they are walked. `${crypto.randomUUID()}` is rejected. Test files (*.test.ts, *.test.tsx) are skipped here; their own time rule is B1-2's.

Scope: the rule applies inside better-auth/ too, which is stricter than proof row U23's wording ("outside the Better Auth boundary module"). That module's exemption exists so it can import Better Auth. Our own code in it, such as fleet-admin-forwarding.ts, still follows R30. Run over today's core source, the new rule reports exactly the six sites on the Requirements page.

Failure and concurrency

  • No new state, store or background work. Each capability call is request-scoped, the same as the global it replaces.
  • A throw while rendering a page (owner page or factor page) is caught by the handler's existing try/catch (sign-in-http-handler.ts:168–404). That catch:
    • attempts to delete the sessions issued in this request;
    • attempts to clean up people created without a linked account;
    • does both with Promise.allSettled, so a failed cleanup is ignored, as it is today;
    • replies 503 {"error":"sign-in-unavailable"}.
    Anything Better Auth already wrote earlier in the same request stands, as it would for any other error at that point today. For example, a factor that was just enabled, or a recorded sign-in.
  • A throw during admin forwarding stops the steps after it. Steps already completed stand: an earlier token exchange, or an earlier call to central. The admin page shows its existing failure.
  • A throw during stamp renewal's statement read ends that renewal attempt the same way a failed central read does today.
  • Concurrent requests call the capability independently. Web Crypto has no shared mutable state to guard.
