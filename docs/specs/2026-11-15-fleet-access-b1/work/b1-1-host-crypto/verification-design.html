B1-1 · The host supplies all cryptography: Verification Design

How each rule on the Specification will be shown to hold, and what stays unproven. This is a plan: nothing here has been run yet. The paired Verifier runs these checks on the pinned PR commit, and each must fail on its named wrong build.

The three things for you

Two checks carry the weight:

  • V2, the recording run: it watches every crypto call go through the host's capability. Your proof row U23 asks for exactly this.
  • V4, the architecture check: planted slips, including one in a .tsx page, must fail it.

The real Chrome pages and the admin journey also keep passing on both hosts (V5).

None. V3 checks against fixed reference values, including central's own shared vectors, that nothing anyone sees has changed.

Every check traces to your rule R30 and your proof row U23: "Run SO2 on both hosts; run the core with recording capabilities and a pinned process clock … every clock, identifier, crypto and central call is recorded; no platform global in the core outside the Better Auth boundary module, and a Node or Worker import placed in a sign-in-core source file makes the audit fail."

Where each check looks

Key: amber is what the check does, green is what it reads to decide.

The checks

V1 · The page nonce comes from the host (S1)

Proven by: rendering an owner page and a factor page with a crypto that returns the bytes 00 to 0f, and seeing that exact nonce in the page's security header and on every script tag.

  • Test: new focused tests in sign-in-core (pages/page-nonce.unit.test.ts, plus a case in better-auth/served-page-appearance.unit.test.ts), in the unit lane.
  • Passes when: the header contains 'nonce-000102030405060708090a0b0c0d0e0f' and every <script nonce> equals it. Two renders with a counting crypto get two different nonces.
  • Fails on: today's page-document.tsx, which mints its own nonce, so the header doesn't match the fixed bytes.
  • Reference: S1's format (16 bytes, 32 lowercase hex).
  • Unverified: nothing beyond V5's limits.

V2 · Every crypto call goes through the capability (S1, S2)

Proven by: running three real core paths with a recording crypto, and seeing each expected operation in the record.

  • The three paths:
    1. serving an owner page through sign-in-http-handler;
    2. forwarding an admin operation against the existing controlled central admin fixture (test-fixtures/controlled-central-admin.ts);
    3. reading a signed organization statement in stamp renewal.
  • Test: new packages/sign-in-test-support/src/host-crypto-recording.integration.test.ts, in the integration lane, using the new recording-sign-in-crypto.ts fixture.
  • Passes when:
    • path 1 records getRandomValues(16);
    • path 2 records generateKey(ECDSA P-256), exportKey(jwk), getRandomValues(32), digest(SHA-256) for the challenge, the thumbprint and the intent, and sign(ECDSA SHA-256);
    • path 3 records digest(SHA-256);
    • a crypto that throws makes path 1 return the handler's generic error response, with no row written.
  • Fails on: any of the six sites left on the runtime global, because its operation never appears in the record.
  • Reference: R30 and proof row U23's recording run.
  • Unverified: this runs on Node in the test process. It proves which code calls the capability, not how each runtime behaves, which is V5's job.

V4 · The check catches a slip, and the capability is required (S3, S6)

Proven by: planting slips in test sources and seeing the architecture check reject each one and accept the allowed look-alikes. Then running the check on the real tree.

  • Tests: new cases in scripts/audit-portal-architecture.unit.test.ts, run by pnpm test:unit:
    • Rejected: a .tsx core file using crypto.randomUUID(); a .ts core file using globalThis.crypto.subtle.digest; each of Date.now(), new Date(), performance.now(), setTimeout, setInterval and Math.random().
    • Accepted: platform.crypto.getRandomValues(…); a parameter named crypto; the same calls inside a template-string browser script; new Date(now) with an argument; a *.unit.test.ts file.
  • The real tree: pnpm test:portal-architecture reports exactly the six sites on main, and nothing on the PR.
  • Required capability (S3): a type-level case, a SignInPlatform literal without crypto marked @ts-expect-error, compiled by pnpm check. If crypto were optional, the marker would be unused and the type-check would fail.
  • Fails on: the check as it is today, which passes the planted .tsx and global slips.
  • Reference: proof row U23 and S6.
  • Unverified: an obscure aliasing trick, such as const c = globalThis; c['cry' + 'pto'], can evade a syntax check. The Verifier's source read of the changed files covers it.

V5 · Both hosts still work, unchanged (S4, S5)

Proven by: the existing real-path journeys passing on local workerd with D1 and on the Node host with better-sqlite3.

  • Served sign-in pages: real Chrome runs a page's scripts only when their nonce matches the page's security policy, so a wrong or missing nonce breaks the page.
  • Admin forwarding and relay: real proofs and digests are accepted by the controlled central.
  • Tests: reused as they are, in pnpm test:e2e:host:
    • sign-in-native-browser.host.e2e.test.ts: both storage hosts, headless Chrome;
    • fleet-admin-relay.host.e2e.test.ts;
    • fleet-cli.host.e2e.test.ts;
    • the verify-auth organization journey on local-workerd and local-node (journey read: .agents/skills/verify-auth/SKILL.md, "Organization statements"; lasting).
  • Passes when: every case passes on both hosts.
  • Fails on: a host that computes its own nonce format (Chrome blocks the scripts), or one that changes a proof (the relay refuses it). A host that doesn't hand in crypto doesn't compile.
  • Unverified:
    • deployed Cloudflare and Node hosts;
    • the real central, which the controlled central stands in for, as today;
    • the macOS Keychain CLI test, which runs only on a Mac.
    The browser test still carries B1-2's real-timer defect until B1-2 lands. That affects how it waits, not what it checks here.
