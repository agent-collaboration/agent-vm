Decisions

D1 · Open: release a breaking change to the published package?

@agent-collaboration/sign-in-core is published to npm (version 0.0.153, publishConfig public). Your rule R30 can only be met by handing crypto in, so eight of its exported functions gain a crypto parameter, and two exported types (SignInPlatform, OrganizationStampRenewalProps) gain a required crypto. Inside this repository, every caller is updated in the same PR. Outside it, I found no consumer: codex-router and agent-vm don't depend on the package.

Key: amber is the package, green is updated with it, blue is outside it.

OptionGainCost
A. Release it as a breaking change in the next 0.0.x version (recommended)R30 holds everywhere, with one way to call each function. Pre-1.0 versions allow breaking changes, and it matches your "no backward compatibility" rule.Any outside consumer, if one exists, must pass crypto when it upgrades.
B. Keep the old signatures as wrappers that read the runtime's cryptoOutside code keeps compiling.The wrappers break R30 inside the core and add a second path, which is the kind of compatibility shim you don't allow. The new check would also have to exempt them.

If you defer: B1-1 can't merge, because the PR changes the exported signatures. Nothing else in B1 waits on it.
