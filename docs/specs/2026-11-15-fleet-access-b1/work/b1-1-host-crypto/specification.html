B1-1 · The host supplies all cryptography: Specification

What must be observably true when B1-1 is done. Every rule here comes from your rule R30 (approved Specification, docs/specs/2026-11-02-fleet-access/specification.source.html:277), authorized by needs U23 and U16. How it's built is on the Program Design.

The three things for you

Rules S1–S3: every random value and every crypto operation the sign-in rules use comes from the host, and none is taken from the runtime. Rule S6: the architecture check fails if anyone puts the runtime's crypto, clock or timers back into the core, including in a page file.

None for people. Rule S5 requires every page, token, proof and digest to keep its exact format, so nothing a person or central sees changes. Exported function signatures change, but neither package is published, so nothing outside switchboard breaks (D1).

Your rule R30, word for word: "The core MUST reach storage, time, identifiers, cryptography and outbound requests only through capabilities its host supplies, and each capability is required. The Cloudflare host and the Node host MUST each supply them and add no sign-in rule."

Your proof row U23 adds: "every clock, identifier, crypto and central call is recorded; no platform global in the core outside the Better Auth boundary module." Both come from your approved design, which traces to your words on the Requirements page.

The rules

Key: blue is the host, green is the capability, amber is the core, teal is what outsiders see, rose is the check and what it rejects.

S1 · Random values come from the host

Every random value the core uses MUST come from the crypto capability. There are two today:

  • The page nonce: 16 random bytes, written as 32 lowercase hex characters.
  • The admin forwarding verifier: 32 random bytes, written in base64url without padding, used as the PKCE verifier when the sign-in service obtains a person's admin credential.

Edge cases:

  • Each rendered page asks the capability once, and its nonce is exactly the bytes it got back. Two pages getting different nonces depends on the host's randomness (each runtime's secure random source), not on a promise in the core.
  • A reply that isn't a rendered page (JSON, a redirect, a passed-through response) asks for no random bytes.
  • The nonce on every script tag of a page equals the nonce in that page's security policy header.

Wrong if: a page's nonce or the verifier comes from anywhere other than the capability. With a capability that returns fixed bytes, the nonce or verifier would then differ from those bytes.

S2 · Hashing, keys and signing go through the host

Every SHA-256 digest, and every key creation, export, import and signature the core performs, MUST go through the crypto capability. That covers:

  • the canonical-JSON digest;
  • the admin operation's intent digest;
  • the base64url SHA-256 used for PKCE challenges and the proof's token binding;
  • the organization statement digest;
  • the admin proof key: create (ES256, P-256), export, import and thumbprint;
  • the DPoP proof signature.

Edge case: a non-extractable key stays non-extractable. Only the owner CLI's Keychain custody asks for an extractable key, as today.

Wrong if: a recording capability doesn't see the operation when that code path runs.

S3 · The capability is required

The core MUST NOT fall back to the runtime's crypto when a host doesn't hand one in. Every function that needs it takes it explicitly, and a host that leaves it out does not build: it fails type-checking.

Wrong if: any core function has a default that reads the runtime's crypto.

Outside effect: this changes exported signatures of @agent-collaboration/sign-in-core and @agent-collaboration/sign-in-owner-cli. Neither is published (npm registry 404, 15 Nov), and every caller is in switchboard and updated in the same PR (D1).

S4 · Each host hands it in and adds no rule

The Cloudflare host, the Node host and the owner CLI MUST each hand in a crypto capability built from their runtime's standard Web Crypto. The host adds no sign-in rule while doing so: no extra checks, no format choices.

Wrong if: a host computes a digest, nonce or proof itself instead of handing in the capability.

S5 · Nothing outsiders see changes

For the same inputs, every output except the page nonce's value MUST be byte-for-byte what it is today. The nonce keeps its form, 32 lowercase hex characters, but its value and bit layout change (below):

  • Digests and thumbprints: SHA-256, base64url without padding or lowercase hex as today, and RFC 7638 for the thumbprint. Central computes the same digests.
  • Proofs: DPoP proofs (RFC 9449), with header typ: dpop+jwt, alg: ES256 and the public JWK, the same claims, and an IEEE P1363 signature.
  • Page security policy: the same policy text, with only the nonce value varying.
  • The nonce itself stays 32 lowercase hex characters. Today it's a version-4 UUID with the hyphens removed (122 random bits and fixed version bits). After B1-1 it's 16 random bytes (128 random bits). Only its value and internal bit layout change. It's used once and never parsed.

Wrong if: a fixed input gives a different digest or thumbprint than main at f3b2b88b, central refuses a proof it accepts today, or the page policy text changes.

S6 · The architecture check catches a slip

The architecture check (pnpm test:portal-architecture, part of pnpm check) MUST fail when any source file under packages/sign-in-core/src/, both .ts and .tsx, uses any of these as runtime globals:

  • crypto or globalThis.crypto;
  • Math.random;
  • Date.now, or new Date() with no argument;
  • performance.now;
  • setTimeout or setInterval.

Your proof row U23 already asks for this check to point at packages/sign-in-core/src/.

Edge cases:

  • A browser script written as text in a string is not code the service runs, so the check MUST NOT flag it.
  • A property or local name that happens to be called crypto, such as platform.crypto, MUST NOT be flagged.
  • Test files keep their own rules.

Wrong if: a planted crypto.randomUUID() in a .tsx page passes the check, or the check flags the admin page's browser script.

When something fails

  • The capability throws while a page is being rendered: the handler's existing error handling (sign-in-http-handler.ts:168–404) attempts to delete the sessions issued in this request and to clean up people created without a linked account. Both are best-effort, so a failed cleanup is ignored, as today. It replies 503 {"error":"sign-in-unavailable"}. No page is sent. Anything already written earlier in the same request stands, as it does today for any error at that point. For example, a factor just enabled, or a recorded sign-in.
  • The capability throws during admin forwarding: the steps after it don't happen. Steps already completed (an earlier token exchange or call to central) stand. The admin page shows its existing failure.
  • The capability throws during stamp renewal: that renewal attempt ends the way a failed central read ends today.
  • A host is built without the capability: it doesn't compile (S3). There's no runtime fallback to discover.
