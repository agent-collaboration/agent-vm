Deliverable 1 of B1. About 3–4 hours for the Implementer and Verifier pair. This page says why it exists and for whom. The Specification says what must be true. The Program Design says how, file by file, and the Verification Design says how each rule is proven.

What's wrong today

Your rule says the core reaches "storage, time, identifiers, cryptography and outbound requests only through capabilities its host supplies". Storage, time, IDs and outbound calls already work that way. Cryptography doesn't. The host contract (SignInPlatform) has no crypto capability at all, so six places in the core call the runtime's crypto directly. The independent audit found one of them (R1-X7). Reading the code found the other five.

Key: blue is the host, green is what it hands in, amber is the core, rose is what the core takes itself, which your rule forbids.

Why the check didn't catch it: scripts/audit-portal-architecture.ts blocks runtime imports and Cloudflare-only names. It doesn't block the standard globals both runtimes share (crypto, Date.now, setTimeout, Math.random), and it only reads .ts files (line 185), not .tsx.

Who needs this, and why

  • You, as the product owner: one sign-in design that runs the same on Cloudflare and on Node, with each runtime plugged in from outside (U23, U16).
  • Whoever adds a host later (another runtime, a test host): everything the core needs from a runtime is in one contract. Nothing is picked up silently.
  • The tests: a test can hand in fixed random bytes and record every crypto call. That's how your proof row U23 says this rule is checked: "a run with recording capabilities shows every clock, ID, crypto and outbound call went through them".
