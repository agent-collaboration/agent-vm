B1-A · One sign-in core, injected and honestly tested: Program Design

How rules S1–S12 of the Specification are built, file by file, in switchboard at main f3b2b88b.

  • Crypto through the host (S1–S6): the host contract gets one new capability, crypto, shaped like the standard Web Crypto. Six core sites take it instead of the runtime global. The shared web capabilities builder hands it in for both hosts and the CLI.
  • The architecture check gains one rule, covering the core and the sign-in tests.
  • No wall clock in tests (S7): the browser-test helper waits on events only, and one host test builds its rows from the controlled clock.
  • Hegel (S8): a new property-test family covers token-kind dispatch.
  • Flood limits (S9): the over-limit cases switch to Miniflare's real counter, which the harness already supports.
  • IDs (S10): a new test reads back every stored ID.
  • Agents (S11): the existing agent journey is re-run on the final build.

The three things for you

The dependency picture (below): the core defines what it needs, and the hosts supply it. Nothing in the core points at a runtime.

The new rule in the architecture check (below) rejects the runtime's crypto, clock and timers in the core, and real timers or clock reads in the sign-in tests, including code inside ${…} in a template.

The test changes (time, Hegel, flood, IDs) are each small and name their exact files.

None. Some exported signatures of sign-in-core and sign-in-owner-cli change. Neither is on the public npm registry, and every switchboard caller is updated in the same PR. Other consumers are unknown (Decisions).

It's the same pattern your approved design already uses for the clock, IDs and deadlines: an interface in the core, with each runtime injecting its own. Your words (approved Requirements, line 174, U23): "you inject stukff not pkul out engines". The trace table maps every rule to its owner and proof.

The parts and which way they depend

Arrows point from the package that depends to the package it depends on. The core depends on no runtime. Hosts depend on the core, never the reverse (R30). Only the shared web capabilities builder reads the runtime's globalThis.crypto.

Key: amber is the core, green is the only place the runtime's crypto is read, blue are the hosts, violet is test support. These edges exist today. B1-1 adds no package and no dependency.

The new capability and the page nonce

It's added to the host contract in packages/sign-in-core/src/contracts/sign-in-platform.ts, beside SignInClock, SignInIdSource and SignInDeadlines. It's a subset of the standard Web Crypto, so both runtimes satisfy it with their own globalThis.crypto, and a test can wrap it to record calls or return fixed bytes.

The nonce helper lives in contracts/, not pages/, because the package's import map sends #sign-in-core/pages/* to .tsx files and #sign-in-core/* to .ts files (packages/sign-in-core/package.json, imports).

The token-kind dispatch Hegel family (S8)

A new property test, packages/sign-in-test-support/src/core-tests/sign-in-response-release.hegel.unit.test.ts, sits beside the existing focused tests for the same function (core-tests/sign-in-response-release.unit.test.ts, which stay).

  • Why that package: it already depends on @hegeldev/hegel 0.4.10 (packages/sign-in-test-support/package.json:47–50) and already imports releaseSignInResponse from the core's public exports. So no manifest or lockfile changes.
  • Where it runs: its .unit.test.ts suffix puts it in Vitest's unit lane (vitest.config.ts:149–152).
  • What it generates: a grant (client_credentials, person, introspection, none); an audience (a registered workspace resource with a policy, central's admin audience, the management audience, an unknown one); a client (a registered agent, the owner fleet CLI client, another person client); whether the response carries a refresh credential; and whether the issued sessions are still active.
  • What it runs: releaseSignInResponse (response-release/sign-in-response-release.ts:53), with in-memory ports built from those choices.
  • The model is a pure function in the test, written independently of the code from the decision table and the two rules below. Its outcome is either a response (status, body, and which cleanups ran) or rejected (the release call's promise rejects, with which cleanups were attempted).

How the model walks:

  • Steps in order. The steps are taken in order, and the first whose condition holds decides. A step's condition reads the values the generated ports return.
  • Rule 1, a port throws. A port is consulted only when the walk reaches the step that reads it, so a throwing port matters only if it's reached. When the walk reaches a read that throws, that decides at once, ahead of every later step:
    • introspection gets {"active": false};
    • any other grant gets refused with invalid_client for client_credentials, otherwise invalid_grant.
    The reads that can throw:
    • the session check (step 0);
    • reading the body as JSON (steps 1 and 6);
    • the introspection body's shape check (step 1);
    • now;
    • the organization-session check (steps 3, 16 and 18);
    • inspectSignedToken, read just after step 6 and before step 7;
    • readAgent (step 10);
    • readWorkspaceResource (steps 11 and 15).
    This is sign-in-response-release.ts:73–209 inside one try, with its catch at lines 210–213.
  • Rule 2, what "refuse X" does.
    • Cleanup first: it starts deleting every session issued in this request at once. Only when all of those succeed does it clean up every person created in the request. Then it answers. The answer is 400 with {"error":"X"}, or 403 for not-allowed.
    • If cleanup rejects: if deleteSession or cleanupUnboundPerson rejects, there is no answer. The release call itself rejects. The code returns the refusal's promise without awaiting it inside the try (lines 60–80), so the rejection isn't caught. This holds for a refusal reached through rule 1 too.
    • What the caller does: the real caller already turns that rejection into 503 {"error":"sign-in-unavailable"} after its own best-effort cleanup (sign-in-http-handler.ts:338–344, 392–402). The model records "rejected"; it doesn't invent a response. B1-A doesn't change this behaviour (S5).
  • "Pass through" means the upstream response, unchanged.

The architecture check's new rule

In scripts/audit-portal-architecture.ts, four changes:

  • the first two are limited to packages/sign-in-core/src/, as your proof row U23 asks;
  • the third covers the sign-in tests, as your proof row U25 asks ("a scan finds no real-clock read, real-time wait or real timer in the sign-in tests, helpers or harness");
  • the fourth enforces UUIDv7 only across the sign-in packages, tests included (S12).
  1. Read .tsx too: collectFilesUnderDirectory (lines 1272–1288) also returns .tsx files under every packages/sign-in-*/src/ and scripts/verify-auth/. That way the test-time rule (S7) and the UUID rule (S12) see every sign-in helper and test file, not only the core's. This was corrected after the 16 Nov review (finding X3); the first version collected .tsx only under the core. Packages outside sign-in keep their file lists.
  2. Allow only listed runtime globals: collectAuthCoreViolations (lines 1250–1270) adds a rule over each non-test core file outside src/pages/islands/.
    • The program: a TypeScript program over those files (ts.createProgram, the typescript package the script already uses), with the core package's own compiler options from packages/sign-in-core/tsconfig.json: lib ES2024, DOM and DOM.Iterable; types: []; moduleResolution: "Bundler", so imports resolve.
    • How each name is classified: for every identifier in a value position (not a type, not a property name such as platform.crypto, not an object-literal or destructuring label), the checker's symbol decides, in this order:
      1. No symbol: the name doesn't resolve. Under types: [] that's a runtime-only name such as process or Bun. Reported.
      2. The compiler's own globalThis symbol (it has no declarations; typescript.js:51124–51126 creates it): reported, in every form, including globalThis.crypto and globalThis[…].
      3. The compiler's own undefined symbol (also without declarations): allowed. It's a language value, used about 90 times in today's core.
      4. A symbol with declarations, every one in a standard library file (lib.*.d.ts): a runtime global. It passes only if it's on the allowed list below, with the two narrowings.
      5. Anything else: one of our own declarations (a local, a parameter, an import, a module member). Never reported, even when it's named crypto, fetch or globalThis.
    • The allowed list, exactly what the core's server code uses at f3b2b88b: I measured it with the type checker over every non-test core file.
      • AbortController, Array, Boolean, Date, Error, Headers, JSON, Map, Math, Number, Object, Promise, RangeError, Request, Response, Set, String, SyntaxError;
      • TextEncoder, TypeError, URL, URLSearchParams, Uint8Array, atob, btoa, encodeURIComponent.
    • Two narrowings inside the list: Date only as new Date(value) with an argument (so Date.now() and a bare new Date() fail); Math but not Math.random.
    • Everything else fails with its file, line and name: crypto, globalThis (so globalThis.crypto and globalThis[…]), fetch, setTimeout, setInterval, performance, navigator, console, an unresolved process, and any name added later.
    • The list lives in the script as one named constant, signInCoreAllowedGlobals, with a comment giving each entry's reason. Widening it is a reviewed change.
    Templates: literal text of strings and templates is not code, so browser scripts written as text aren't flagged. The expressions inside a template's ${…} are code the service runs, so they are walked. `${crypto.randomUUID()}` is rejected. Test files are skipped by this core rule; the next rule covers them. A test file is any file Vitest runs as a test: *.test.ts, *.test.tsx and *.unit.spec.ts (vitest.config.ts:149–152).
  3. Reject real time in the sign-in tests: a new function, beside the core rule, walks:
    • every file under packages/sign-in-test-support/src/;
    • every test file (*.test.ts, *.test.tsx, *.unit.spec.ts) under packages/sign-in-*/src/;
    • scripts/verify-auth/.
    It reports:
    • setTimeout and setInterval, and typeof setTimeout in a type;
    • Date.now() and a zero-argument new Date();
    • any read of performance (performance.now(), performance.timeOrigin and the rest);
    • process.hrtime and process.uptime.
    new Date(x) with an argument is allowed, because the argument is where the time comes from. Every real-time source above is caught where it's read, so new Date(performance.timeOrigin) is reported for its performance read.
    • Allowed: calls on Vitest's vi object (vi.useFakeTimers, vi.setSystemTime, vi.advanceTimersByTime), and timer names written as strings (vi.spyOn(globalThis, 'setInterval'), toFake: ['setTimeout']), because strings aren't calls.
    • On main today it reports the five protocol-helper bounds, the authorization-fence rows, and the evidence folder's date in native-browser-scenario.ts:43. After the time changes, it reports nothing.
  4. UUIDv7 only (S12): a new function walks every file under packages/sign-in-*/src/, tests included, and scripts/verify-auth/. It reports:
    • a call to, or import of, randomUUID, from node:crypto or as crypto.randomUUID;
    • an import from uuid of anything but v7;
    • an import of any other UUID package.
    Literal text in strings isn't code, as above. On main today it reports page-document.tsx:181 and macos-keychain-proof-key-store.host.e2e.test.ts:1, 17; after the changes, nothing.

That module's exemption exists so it can import Better Auth. Our own code in it, such as fleet-admin-forwarding.ts, still follows R30. Run over today's core source, the allowed-globals rule reports exactly the six sites listed on the Audit page: the bare crypto in page-document.tsx:181, and globalThis in the other five files (nine lines). Every other global the core uses is on the list.

Failure and concurrency

  • No new state, store or background work. Each capability call is request-scoped, the same as the global it replaces.
  • A throw while rendering a page (owner page or factor page) is caught by the handler's existing try/catch (sign-in-http-handler.ts:168–404). That catch:
    • attempts to delete the sessions issued in this request;
    • attempts to clean up people created without a linked account;
    • does both with Promise.allSettled, so a failed cleanup is ignored, as it is today;
    • replies 503 {"error":"sign-in-unavailable"}.
    Anything Better Auth already wrote earlier in the same request stands, as it would for any other error at that point today. For example, a factor that was just enabled, or a recorded sign-in.
  • A throw during admin forwarding stops the steps after it. Steps already completed stand: an earlier token exchange, or an earlier call to central. The admin page shows its existing failure.
  • A throw during stamp renewal's statement read ends that renewal attempt the same way a failed central read does today.
  • Concurrent requests call the capability independently. Web Crypto has no shared mutable state to guard.
