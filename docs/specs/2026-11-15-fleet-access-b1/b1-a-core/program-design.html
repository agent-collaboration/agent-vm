B1-A · One sign-in core, injected and honestly tested: Program Design

How rules S1–S11 of the Specification are built, file by file, in switchboard at main f3b2b88b.

  • Crypto through the host (S1–S6): the host contract gets one new capability, crypto, shaped like the standard Web Crypto. Six core sites take it instead of the runtime global. The shared web capabilities builder hands it in for both hosts and the CLI.
  • The architecture check gains one rule, covering the core and the sign-in tests.
  • No wall clock in tests (S7): the browser-test helper waits on events only, and one host test builds its rows from the controlled clock.
  • Hegel (S8): a new property-test family covers token-kind dispatch.
  • Flood limits (S9): the over-limit cases switch to Miniflare's real counter, which the harness already supports.
  • IDs (S10): a new test reads back every stored ID.
  • Agents (S11): the existing agent journey is re-run on the final build.

The three things for you

The dependency picture (below): the core defines what it needs, and the hosts supply it. Nothing in the core points at a runtime.

The new rule in the architecture check (below) rejects the runtime's crypto, clock and timers in the core, and real timers or clock reads in the sign-in tests, including code inside ${…} in a template.

The test changes (time, Hegel, flood, IDs) are each small and name their exact files.

None. Some exported signatures of sign-in-core and sign-in-owner-cli change. Neither is on the public npm registry, and every switchboard caller is updated in the same PR. Other consumers are unknown (Decisions).

It's the same pattern your approved design already uses for the clock, IDs and deadlines: an interface in the core, with each runtime injecting its own. Your words (approved Requirements, line 174, U23): "you inject stukff not pkul out engines". The trace table maps every rule to its owner and proof.

The parts and which way they depend

Arrows point from the package that depends to the package it depends on. The core depends on no runtime. Hosts depend on the core, never the reverse (R30). Only the shared web capabilities builder reads the runtime's globalThis.crypto.

Key: amber is the core, green is the only place the runtime's crypto is read, blue are the hosts, violet is test support. These edges exist today. B1-1 adds no package and no dependency.

The new capability and the page nonce

It's added to the host contract in packages/sign-in-core/src/contracts/sign-in-platform.ts, beside SignInClock, SignInIdSource and SignInDeadlines. It's a subset of the standard Web Crypto, so both runtimes satisfy it with their own globalThis.crypto, and a test can wrap it to record calls or return fixed bytes.

The nonce helper lives in contracts/, not pages/, because the package's import map sends #sign-in-core/pages/* to .tsx files and #sign-in-core/* to .ts files (packages/sign-in-core/package.json, imports).

How a request reaches crypto, before and after

Serving a sign-in page (S1, the nonce)

  • Before: page-document.tsx:181 minted the nonce itself with crypto.randomUUID().
  • After: pageDocument requires nonce: PageNonce and mints nothing. renderOwnerPage and renderFactorPage pass nonce through.
  • Who mints: the two response builders that decide whether to render HTML. minimalOwnerPage always renders, so it always mints. renderFactorFormResponse mints only on the branch that calls renderFactorPage. Its earlier returns (not a POST, not an offered path, the request isn't asking for HTML, or the 303 redirect) make no crypto call.
  • Who hands it in: the handler, at sign-in-http-handler.ts:272, :346 and :391, passes crypto: configuration.platform.crypto.
  • Unchanged: pageContentSecurityPolicy(nonce, challenge).

No wall clock in tests (S7)

Two places break the rule today. Both are test code, so no product behaviour changes.

The browser-test protocol helper waits on events

packages/sign-in-test-support/src/test-fixtures/native-browser-protocol.ts drives Chrome over its DevTools socket. It has five real-time "bounds", and each becomes a wait on the event that ends it:

One host test builds rows from the controlled clock

packages/sign-in-test-support/src/authorization-fence.host.e2e.test.ts inserts rows with createdAt: new Date() (lines 538, 549, 560, 567, 678) and an invitation with expiresAt: new Date(Date.now() + 86_400_000) (line 548). Each becomes new Date(controlledSignInClock.now()), or now + 86_400_000, from the harness's controlled clock, the same clock Better Auth reads in that harness. The invitation's validity then no longer depends on the real date.

The token-kind dispatch Hegel family (S8)

A new property test, packages/sign-in-core/src/response-release/sign-in-response-release.unit.test.ts, uses @hegeldev/hegel (already a test-support dependency, 0.4.10).

  • What it generates: a grant (client_credentials, person, introspection, none); an audience (a registered workspace resource with a policy, central's admin audience, the management audience, an unknown one); a client (a registered agent, the owner fleet CLI client, another person client); whether the response carries a refresh credential; and whether the issued sessions are still active.
  • What it runs: releaseSignInResponse (response-release/sign-in-response-release.ts:53), with in-memory ports built from those choices.
  • The model is a pure function in the test, written independently of the code from the decision table below. Steps are taken in order, and the first that applies decides. Flood limits on Miniflare's real counter (S9)

The local harness already supports both counters. startLocalAuthHarness({ cloudflareOuterLimit }) takes 'real-binding' (the default) or 'controlled-stand-in' (test-fixtures/local-auth-harness.ts:145, 610, 754). The real binding reaches createBindingRequestLimiter in packages/sign-in-host-cloudflare/src/binding-request-limiter.ts, which asks Miniflare's RateLimiterObject.

  • The change: in people-request-limits.host.e2e.test.ts, the over-limit cases that pass 'controlled-stand-in' (lines 99 and 152) use the real binding instead, by passing nothing. Their assertions stay: 429 with Retry-After, every sign-in row fingerprint unchanged, and another address still passing.
  • The reset cases stay on the core's limiter with the controlled clock, as journey SO2 says.
  • The stand-in is removed. After this change no test uses 'controlled-stand-in'. The one failure case, "an unavailable outer backing call returns 503" (line 42), already runs on the real binding and arms the failure with harness.makeLimiterUnavailable(). So the option is deleted with the feature, as the old code it replaces:
    • its branch in test-fixtures/local-auth-harness.ts (lines 145, 610 and 754);
    • the AUTH_PROOF_RATE_LIMIT_MODE switch and the stand-in in test-fixtures/auth-proof-rate-limit-bindings.ts (lines 42–46).
  • Verified in Miniflare's source (miniflare 5.20260815.0-alpha, dist/src/workers/ratelimit/ratelimit-object.worker.js): the counter computes its window as Math.floor(Date.now() / (period * 1000)), with periods of 10 or 60 seconds. The test never reads that clock or waits on it, but a burst that crosses a window boundary resets the count. That's the residual risk on the Decisions page.

Every stored ID read back (S10)

A new host test, packages/sign-in-test-support/src/stored-identifier-readback.host.e2e.test.ts, runs on both databases:

  • The run: it starts the local harness, then runs the people journey: owner sign-in and organization, an invitation, accept, remove, a second factor, and an admin forwarding.
  • The scan: it reads, through Drizzle, the ten tables the journey fills, from the sign-in schema (signInSchema, storage/sign-in-schema.ts:589): user, session, account, organization, member, invitation, twoFactor, signInAudit, jwks and oauthClient. Each must have at least one row. Every value in a column named id, or ending in Id or _id, must parse as z.uuidv7().
  • Checking the table list: the Implementer confirms it against the first run. Any further table the journey fills joins the list; a table it can't fill is named as uncovered.
  • The derived key (oauthClientAssertion.id, a digest of the assertion's jti) and its replay refusal are already proven by storage-cases/provider-identifier-cases.ts:56–130. That case stays, and V9 names it.
  • Secrets and codes (token, secret, backupCodes, device and user codes) must not match the UUID shape.
  • No raw SQL: rows are read with Drizzle's query builder, as R29 requires.

The architecture check's new rule

In scripts/audit-portal-architecture.ts, three changes. The first two are limited to packages/sign-in-core/src/, as your proof row U23 asks. The third covers the sign-in tests, as your proof row U25 asks ("a scan finds no real-clock read, real-time wait or real timer in the sign-in tests, helpers or harness").

  1. Read .tsx too: collectFilesUnderDirectory (lines 1272–1288) also returns .tsx files when it walks packages/sign-in-core/src/. Other packages' file lists don't change, so no other check widens.
  2. Reject runtime globals: collectAuthCoreViolations (lines 1250–1270) adds a rule that walks the TypeScript syntax tree of each non-test core file. It reports:
    • the identifier crypto used as a free global (not a property such as platform.crypto, and not a local binding or parameter);
    • globalThis.crypto;
    • Math.random, Date.now, performance.now, setTimeout and setInterval;
    • new Date() with no argument;
    • globalThis[...] with a computed key.
    Templates: literal text of strings and templates is not code, so browser scripts written as text aren't flagged. The expressions inside a template's ${…} are code the service runs, so they are walked. `${crypto.randomUUID()}` is rejected. Test files (*.test.ts, *.test.tsx) are skipped by this core rule; the next rule covers them.
  3. Reject real time in the sign-in tests: a new function, beside the core rule, walks every file under packages/sign-in-test-support/src/, every *.test.ts under packages/sign-in-*/src/, and scripts/verify-auth/. It reports setTimeout, setInterval, Date.now(), performance.now(), a zero-argument new Date(), and typeof setTimeout in a type.
    • Allowed: calls on Vitest's vi object (vi.useFakeTimers, vi.setSystemTime, vi.advanceTimersByTime), and timer names written as strings (vi.spyOn(globalThis, 'setInterval'), toFake: ['setTimeout']), because strings aren't calls.
    • On main today it reports the five protocol-helper bounds and the authorization-fence rows. After the time changes, it reports nothing.

Scope: the rule applies inside better-auth/ too, which is stricter than proof row U23's wording ("outside the Better Auth boundary module"). That module's exemption exists so it can import Better Auth. Our own code in it, such as fleet-admin-forwarding.ts, still follows R30. Run over today's core source, the new rule reports exactly the six sites listed on the Audit page.

Failure and concurrency

  • No new state, store or background work. Each capability call is request-scoped, the same as the global it replaces.
  • A throw while rendering a page (owner page or factor page) is caught by the handler's existing try/catch (sign-in-http-handler.ts:168–404). That catch:
    • attempts to delete the sessions issued in this request;
    • attempts to clean up people created without a linked account;
    • does both with Promise.allSettled, so a failed cleanup is ignored, as it is today;
    • replies 503 {"error":"sign-in-unavailable"}.
    Anything Better Auth already wrote earlier in the same request stands, as it would for any other error at that point today. For example, a factor that was just enabled, or a recorded sign-in.
  • A throw during admin forwarding stops the steps after it. Steps already completed stand: an earlier token exchange, or an earlier call to central. The admin page shows its existing failure.
  • A throw during stamp renewal's statement read ends that renewal attempt the same way a failed central read does today.
  • Concurrent requests call the capability independently. Web Crypto has no shared mutable state to guard.
