The rules

Key: blue is the host, green is the capability, amber is the core, teal is what outsiders see, rose is the check and what it rejects.

S1 · Random values come from the host

Every random value the core uses MUST come from the crypto capability. There are two today:

  • The page nonce: 16 random bytes, written as 32 lowercase hex characters.
  • The admin forwarding verifier: 32 random bytes, written in base64url without padding, used as the PKCE verifier when the sign-in service obtains a person's admin credential.

Edge cases:

  • Each rendered page asks the capability once, and its nonce is exactly the bytes it got back. Two pages getting different nonces depends on the host's randomness (each runtime's secure random source), not on a promise in the core.
  • A reply that isn't a rendered page (JSON, a redirect, a passed-through response) asks for no random bytes.
  • The nonce on every script tag of a page equals the nonce in that page's security policy header.

Wrong if: a page's nonce or the verifier comes from anywhere other than the capability. With a capability that returns fixed bytes, the nonce or verifier would then differ from those bytes.

S2 · Hashing, keys and signing go through the host

Every SHA-256 digest, and every key creation, export, import and signature the core performs, MUST go through the crypto capability. That covers:

  • the canonical-JSON digest;
  • the admin operation's intent digest;
  • the base64url SHA-256 used for PKCE challenges and the proof's token binding;
  • the organization statement digest;
  • the admin proof key: create (ES256, P-256), export, import and thumbprint;
  • the DPoP proof signature.

Edge case: a non-extractable key stays non-extractable. Only the owner CLI's Keychain custody asks for an extractable key, as today.

Wrong if: a recording capability doesn't see the operation when that code path runs.

S3 · The capability is required

The core MUST NOT fall back to the runtime's crypto when a host doesn't hand one in. Every function that needs it takes it explicitly, and a host that leaves it out does not build: it fails type-checking.

Wrong if: any core function has a default that reads the runtime's crypto.

Outside effect: this changes exported signatures of @agent-collaboration/sign-in-core and @agent-collaboration/sign-in-owner-cli. Neither is on the public npm registry (404, 15 Nov), and every switchboard caller is updated in the same PR. Other consumers are unknown (Decisions).

S4 · Each host hands it in and adds no rule

The Cloudflare host, the Node host and the owner CLI MUST each hand in a crypto capability built from their runtime's standard Web Crypto. The host adds no sign-in rule while doing so: no extra checks, no format choices.

Wrong if: a host computes a digest, nonce or proof itself instead of handing in the capability.

S5 · Nothing outsiders see changes

For the same inputs, every output except the page nonce's value MUST be byte-for-byte what it is today. The nonce keeps its form, 32 lowercase hex characters, but its value and bit layout change (below):

  • Digests and thumbprints: SHA-256, base64url without padding or lowercase hex as today, and RFC 7638 for the thumbprint. Central computes the same digests.
  • Proofs: DPoP proofs (RFC 9449), with header typ: dpop+jwt, alg: ES256 and the public JWK, the same claims, and an IEEE P1363 signature.
  • Page security policy: the same policy text, with only the nonce value varying.
  • The nonce itself stays 32 lowercase hex characters. Today it's a version-4 UUID with the hyphens removed (122 random bits and fixed version bits). After B1-1 it's 16 random bytes (128 random bits). Only its value and internal bit layout change. It's used once and never parsed.

Wrong if: a fixed input gives a different digest or thumbprint than main at f3b2b88b, central refuses a proof it accepts today, or the page policy text changes.

S6 · The architecture check catches a slip

The architecture check (pnpm test:portal-architecture, part of pnpm check) MUST fail when any source file under packages/sign-in-core/src/, both .ts and .tsx, uses any of these as runtime globals:

  • crypto or globalThis.crypto;
  • Math.random;
  • Date.now, or new Date() with no argument;
  • performance.now;
  • setTimeout or setInterval.

Your proof row U23 already asks for this check to point at packages/sign-in-core/src/.

Edge cases:

  • A browser script written as text in a string is not code the service runs, so the check MUST NOT flag it.
  • A property or local name that happens to be called crypto, such as platform.crypto, MUST NOT be flagged.
  • Test files keep their own rules.

Wrong if: a planted crypto.randomUUID() in a .tsx page passes the check, or the check flags the admin page's browser script.

S7 · No sign-in test reads the real clock or waits on real time

From R33. This covers every test, test helper and harness of the sign-in packages:

  • every file Vitest runs as a test under packages/sign-in-*/src/ (*.test.ts, *.test.tsx and *.unit.spec.ts);
  • all of packages/sign-in-test-support/src/;
  • scripts/verify-auth/.
  • Waits are on events only. A DevTools reply arrives, a socket opens, errors or closes, a process exits, a readiness line arrives, a promise settles.
  • Time comes from a controlled clock. Every timer runs on a controlled clock or on Vitest's fake timers. Any fixture value that depends on time, such as an invitation's expiry, is computed from the controlled clock, never from Date.now() or new Date().
  • There's no real-time watchdog or "bound". If a browser or process hangs without an event, the test hangs. The test runner's own job limit, outside test code, ends the run. This follows from R33 itself: tests "wait only on events … and every timer runs on a controlled clock", so a real-time bound in a helper isn't allowed.
  • A scan enforces it: the same architecture check fails on setTimeout, setInterval, Date.now(), a zero-argument new Date() or performance.now() in those files. Vitest's own fake-timer APIs (vi.useFakeTimers, vi.setSystemTime, vi.advanceTimersByTime) and the names of timers passed as strings to them are allowed.

Wrong if: a planted setTimeout in a test helper passes the scan, or a fixture built with Date.now() passes.

S8 · The Hegel families exist

From R33: "The tests MUST include Hegel property tests of at least: the token-kind dispatch over every client kind, grant and resource; the device code's single use under concurrent redemption; and the token claims' parse round trip."

  • Token-kind dispatch (new): generated combinations of grant (client_credentials, person, introspection, none), audience (a workspace resource, central's admin audience, the management audience, anything else), client (a registered agent, the owner fleet CLI, any other person client), and whether a refresh credential is present. Each combination's decision from releaseSignInResponse must equal a model written from the approved rules: released, passed through, or refused with its exact error.
  • Claims parse round trip (exists): person-identity-contracts.unit.test.ts:118 stays.
  • Device code single use: belongs to machine login (B3) and isn't in this feature.

Each family is deterministic: Hegel's derandomize setting, no stored example database.

Wrong if: a dispatch that admits a combination outside the model, such as a refresh credential released to a client other than the owner fleet CLI, still passes the family.

S9 · "Limited" is proven on Miniflare's real counter

From R52 and your journey SO2: "Miniflare's binding keeps its own clock: locally it proves 'limited', the window reset is proven through the core's limiter on a controlled clock, and the binding's reset is checked once on the private stack."

  • On local workerd: the over-limit cases run against Miniflare's real rate-limit binding, not a stand-in. From one address, past the limit, the next request gets 429 with Retry-After, and every sign-in row reads back unchanged. Another address still passes. A forged x-forwarded-for is ignored.
  • The window reset is proven on the layers that run on a controlled clock. The core itself has no counter: it hands each request to the host's limiter (request-limits/sign-in-request-admission.ts:23–34). So the layers are:
    • Better Auth's own provider-layer limit, inside the service: after the limit, moving the harness's controlled clock past the window lets the next request through (the existing recovery-code case, people-request-limits.host.e2e.test.ts:173–232);
    • the Node host's fixed-window counter, which reopens exactly at expiry on the injected clock (fixed-window-request-limiter.unit.test.ts).
    That's how SO2's "the core's limiter on a controlled clock" maps onto the real code (Decisions).
  • The binding's reset and counting across Cloudflare locations are checked on the private stack, not here.
  • The real counter's own clock: it counts in windows aligned to its real clock, which the test never reads or waits on. A burst sent across a window boundary would let one extra request through. That's the residual risk recorded on the Decisions page.

Wrong if: the binding is unbound or removed from the Worker, and the "limited" case still passes.

S10 · Every stored ID is a UUIDv7

From R32: "No UUID other than version 7 MAY be minted or stored by the sign-in service."

  • Every UUID the service stores is version 7, wherever it sits. That means any column, including UUIDs inside JSON or URLs, not just columns named as IDs. It holds after the people journey on each database (D1 and better-sqlite3), checked twice:
    • before the member's removal, so rows that the removal deletes are seen;
    • at the end.
    It already holds for the owner-and-agent journey, which the existing inventory covers.
  • Coverage: before the first check, user, session, account, organization, member, invitation, twoFactor and signInAudit must each hold at least one row, so an empty table can't pass by having nothing to check.
  • Derived keys stay derived. The client-assertion record's key (oauthClientAssertion.id) is a digest of the assertion's jti, which is what makes its replay refusable. It must stay that digest, not become a UUID, and a replay must be refused. The existing case in storage-cases/provider-identifier-cases.ts (lines 56–130) already proves this, and it stays.
  • Secrets and codes are never UUIDs: session tokens, client secrets, PKCE verifiers, signing keys, backup codes, device codes and user codes.
  • Not reached by this journey: passkey (B1-B), deviceCode (machine login, B3), and the agent-path tables oauthResource and oauthClientResource. They're listed as uncovered, not claimed.

Wrong if: a version-4 UUID anywhere in a stored row passes, including in JSON or in a row later deleted; an expected table is empty and the check still passes; a secret is UUID-shaped; or the client-assertion key stops being the jti digest.

S11 · People get no tool credential, and today's agents still work

From R38. On the final build of this feature:

  • today's agent client gets a token for its linked workspace with its release checks, and makes one allowed tool call;
  • a person asking for a tool credential is refused.

Wrong if: either breaks on that build.

When something fails

  • The capability throws while a page is being rendered: the handler's existing error handling (sign-in-http-handler.ts:168–404) attempts to delete the sessions issued in this request and to clean up people created without a linked account. Both are best-effort, so a failed cleanup is ignored, as today. It replies 503 {"error":"sign-in-unavailable"}. No page is sent. Anything already written earlier in the same request stands, as it does today for any error at that point. For example, a factor just enabled, or a recorded sign-in.
  • The capability throws during admin forwarding: the steps after it don't happen. Steps already completed (an earlier token exchange or call to central) stand. The admin page shows its existing failure.
  • The capability throws during stamp renewal: that renewal attempt ends the way a failed central read ends today.
  • A host is built without the capability: it doesn't compile (S3). There's no runtime fallback to discover.
