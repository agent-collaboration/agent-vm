B1-A · One sign-in core, injected and honestly tested: Requirements

The feature: the sign-in rules run in one core that takes everything runtime-specific from its host (storage, time, IDs, crypto, outbound calls). Its tests prove that honestly: no wall clock, the flood limit on Cloudflare's real counter, every stored ID checked, and today's agents still working. It's the first B1 deliverable in the Fleet access sequence, and the Audit says what was built and what's wrong today.

The three things for you

  • The core never reaches for the runtime itself. Its crypto comes from the host, like its clock and IDs already do, and the architecture check catches a slip.
  • No sign-in test reads the real clock or waits on real time, and a scan enforces it.
  • The flood limit is proven the way your design says: "limited" on Miniflare's real counter, the window reset on a controlled clock.
  • Every identifier the service generates is a UUIDv7, checked across the eight tables a full people journey fills, on both databases. Derived keys, such as the client-assertion key, stay derived.
  • Today's agents still get their token and make one allowed call, and people still can't get a tool credential.

None. Pages, tokens, limits and the agent path behave exactly as today. This feature makes the existing behaviour structurally sound and honestly proven.

Who needs this, and why

Key: blue is you, teal the hosts, amber the core, green the proof, violet today's agents.

  • You: one sign-in design that runs the same on Cloudflare and on Node, with each runtime plugged in from outside (U23, U16). Tests you can trust because they can't pass by luck or by timing (U25).
  • Whoever adds a host later: everything the core needs from a runtime is in one contract, so nothing is picked up silently.
  • Today's agents: their tokens and tool calls keep working while all this changes underneath (R38).
