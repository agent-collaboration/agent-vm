Recorded risk: Miniflare's counter keeps its own real-clock window

Your journey SO2 accepted that "Miniflare's binding keeps its own clock". I read its source (miniflare 5.20260815.0-alpha, ratelimit-object.worker.js): it counts in windows of Math.floor(Date.now() / (period * 1000)), 10 or 60 seconds, aligned to the real clock. The test never reads that clock or waits on it.

The risk: if the requests in a "limited" case happen to cross a window boundary, the count resets and the case can't reach its 429 when expected. It would then fail: a false alarm, never a false pass.

How likely: roughly the case's duration divided by 60 seconds.

  • The social-sign-in case sends about 13 requests (outer limit 10 per 60 s), taking milliseconds, so it's very rare.
  • The page case sends up to about 301 requests (outer limit 300 per 60 s), one after another. If it takes a second or two, that's about one run in 30 to 60.

The Verifier records how long each case takes, so the real figure is known after the first run.

If it ever happens: the failure says the request wasn't limited. A rerun decides it. Nothing is waited on, and nothing passes wrongly.
