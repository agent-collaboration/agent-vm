The signature change: not on public npm; other consumers unknown

Meeting R30 changes some exported signatures:

  • @agent-collaboration/sign-in-core: eight functions gain a crypto parameter, and SignInPlatform and OrganizationStampRenewalProps gain a required crypto.
  • @agent-collaboration/sign-in-owner-cli: FleetCliIo and its three key-store constructors gain a required crypto.

Both packages have publishConfig set to public, but neither is on the public npm registry: on 15 Nov it returned 404 for both. codex-router and agent-vm don't depend on them. Every caller inside switchboard is updated in the same PR.

Consumers that use a git, tarball or private-registry dependency weren't checked, so they're unknown. If one exists, it would need to pass crypto when it upgrades.

If you publish later, these become the published signatures. Your deferred repository-visibility decision is where that gets settled.

Recorded risk: Miniflare's counter keeps its own real-clock window

Your journey SO2 accepted that "Miniflare's binding keeps its own clock". I read its source (miniflare 5.20260815.0-alpha, ratelimit-object.worker.js): it counts in windows of Math.floor(Date.now() / (period * 1000)), 10 or 60 seconds, aligned to the real clock. The test never reads that clock or waits on it.

The risk: if the burst of requests in the "limited" case happens to cross a window boundary, the count resets and one request too many gets through. The case would then fail, a false alarm, not a false pass. A burst takes milliseconds against a 60-second window, so this is rare.

If it ever happens: the failure says the request wasn't limited. A rerun decides it. Nothing is waited on, and nothing passes wrongly.
