B1-A · One sign-in core, injected and honestly tested: Verification Design

How each rule on the Specification will be shown to hold, and what stays unproven. This is a plan: nothing here has been run.

  • Who runs it: the paired Verifier, on the pinned PR commit.
  • Must fail on a named wrong build: V1–V4 and V6–V9.
  • Regression checks: V5 and V10, on the hosts and targets they name.

The three things for you

V2, the recording run, does what your proof row U23 asks. It drives each of the six crypto sites with known inputs and checks that each one's exact operation and input appears in the record. So any one site left on the runtime's crypto fails it. The same run also records clock, ID and central calls.

V4 and V6: planted slips must fail the architecture check. They include one inside a .tsx page, one hidden in a ${…} template expression, and a real timer in a test helper.

V8: removing Miniflare's counter from the Worker must make the "limited" case fail. V9: a planted version-4 ID must fail the readback.

None for people. V3 checks against fixed known values, including central's own shared vectors, that nothing anyone sees has changed.

Every check traces to your rule R30 and your proof row U23 (approved Verification Design, line 278): "Run SO2 on both hosts; run the core with recording capabilities and a pinned process clock … every clock, identifier, crypto and central call is recorded; no platform global in the core outside the Better Auth boundary module, and a Node or Worker import placed in a sign-in-core source file makes the audit fail; the device-code approval rule is in the core."

What this deliverable proves of that row, and what it leaves to others, is in the U23 split at the end.

The other checks trace to your proof rows in the same file:

  • U25 (line 280): "A scan finds no real-clock read, real-time wait or real timer in the sign-in tests, helpers or harness".
  • U24 (line 279).
  • U42 and journey SO2's flood paragraph: "Miniflare's binding keeps its own clock: locally it proves 'limited', the window reset is proven through the core's limiter on a controlled clock".
  • SO2's "today's agent path still works".

Where each check looks

Key: amber is what the check does, green is what it reads to decide.

The checks

V1 · The page nonce is the host's bytes, and only rendered pages ask (S1)

Proven by: rendering pages with a crypto that returns known bytes, and seeing exactly those bytes as the nonce. A reply that isn't a rendered page must ask for none.

  • Tests:
    • new packages/sign-in-core/src/contracts/page-nonce.unit.test.ts;
    • new cases in better-auth/served-page-appearance.unit.test.ts (owner page) and better-auth/factor-enrollment-page.unit.test.ts (factor page and pass-through).
    All run in the unit lane (pnpm test:unit).
  • Passes when:
    • with bytes 00…0f, the security header contains 'nonce-000102030405060708090a0b0c0d0e0f', and every <script nonce> equals it;
    • with a counting crypto, each rendered page asks exactly once, and its nonce equals that call's bytes;
    • a factor POST that returns JSON, a 303 redirect, or a pass-through makes zero getRandomValues calls.
  • Fails on:
    • today's page-document.tsx, whose nonce isn't the fixed bytes;
    • a build that mints in the handler before it knows HTML is needed, which makes a call on the JSON path.
  • Reference: S1 (16 bytes as 32 lowercase hex; a draw only for a rendered page).

V2 · Every crypto call goes through the capability (S1, S2), and so do clock, IDs and central (U23)

Proven by: driving each of the six sites with known inputs on recording capabilities, and finding each site's own operation and input in the record. Several calls are SHA-256, so the check matches the input digested, not just the operation name.

  • Test: new packages/sign-in-test-support/src/host-crypto-recording.integration.test.ts, in the integration lane (pnpm test:integration). It uses the new recording-sign-in-capabilities.ts fixture.
  • Pinned process clock: the whole file runs with the process clock pinned (Vitest fake timers with a fixed system time, far from the injected clock's time). Any output carrying the pinned process time shows a real-clock read. Your proof row U23 asks for this "pinned process clock".

V4 · The check catches a slip, and the capability is required (S3, S6)

Proven by: planting slips in test sources and seeing the architecture check reject each one and accept the allowed look-alikes. Then running the new check over today's core source, and a deliberate type mutation.

  • Tests: new cases in scripts/audit-portal-architecture.unit.test.ts (unit lane):
    • Rejected:
      • a .tsx core file using crypto.randomUUID();
      • a .ts core file using globalThis.crypto.subtle.digest;
      • `${crypto.randomUUID()}` inside a template;
      • each of Date.now(), new Date(), performance.now(), setTimeout, setInterval and Math.random();
      • globalThis['crypto'];
      • a Node import (import 'node:fs') in a core file, the mutant your proof row U23 names.
    • Accepted: platform.crypto.getRandomValues(…); a parameter named crypto; the same calls as literal text inside a browser-script template; new Date(now); a *.unit.test.ts file.
  • The base tree: the PR's checker, run over the base commit's packages/sign-in-core/src/, reports exactly the six sites. Run over the PR's tree, it reports none. (Today's checker on main doesn't have the rule, so it reports nothing either way.)
    • How to run it on the base: the script scans the tree it sits in (audit-portal-architecture.ts:1298–1309, 1332–1340 fix the root from the script's own location), and it has no root argument. So the Verifier makes a scratch worktree at the base commit (git worktree add <scratch> f3b2b88b), copies the PR's scripts/audit-portal-architecture.ts into it, and runs pnpm test:portal-architecture there.
    • Clean-up: the scratch worktree is removed afterwards. Nothing in the PR changes for this.
  • Capability required (S3): two deliberate mutations, run by the Verifier and then reverted:
    • removing crypto from createWebSignInCapabilities' return must make pnpm typecheck fail in the hosts;
    • making SignInPlatform.crypto optional must make the core's call sites fail to type-check.
    The core's test files aren't type-checked by pnpm typecheck (the package excludes src/**/*.test.ts), so this proof is a mutation, not a test file.
  • Fails on: today's checker, which passes the planted slips.
  • Unverified: exotic aliasing (for example const g = globalThis; g[name] built at run time) can evade a syntax check. The Verifier's and the reviewer's source reads cover it.

V6 · No sign-in test reads the real clock or waits on real time (S7)

Proven by: planting real-time calls in test sources and seeing the scan reject them, then running the scan over the real tree, plus the browser journey passing with event waits only.

  • Tests: new cases in scripts/audit-portal-architecture.unit.test.ts:
    • Rejected: setTimeout in a file under packages/sign-in-test-support/src/; Date.now() in a *.host.e2e.test.ts; new Date() in scripts/verify-auth/; performance.now(); setInterval; typeof setTimeout in a type.
    • Accepted: vi.useFakeTimers(), vi.setSystemTime(…), vi.spyOn(globalThis, 'setInterval'), toFake: ['setTimeout'], new Date(controlledSignInClock.now()).
  • The real tree: the PR's checker, run over the base commit's sign-in tests, reports the five native-browser-protocol.ts bounds (lines 84, 115, 148, 218, 274) and the authorization-fence.host.e2e.test.ts rows (lines 538, 548, 549, 560, 567, 678). Run over the PR's tree, it reports nothing. It's run on the base the same way as V4: the PR's script copied into a scratch worktree at f3b2b88b.
  • Behaviour: sign-in-native-browser.host.e2e.test.ts passes on both storage hosts with the event-only protocol helper.
  • The fixture's validity: authorization-fence.host.e2e.test.ts passes with its invitation's expiry taken from the controlled clock.
  • Fails on: a test helper that keeps a setTimeout bound, or a fixture built with Date.now().
  • Reference: R33 and proof row U25.
  • Unverified: how a genuinely hung Chrome is ended. That's the test runner's job limit, configuration outside test code, and it isn't exercised here.

V7 · The Hegel families (S8)

Proven by: the new token-kind dispatch family agreeing with its model on every generated case, and failing when the code admits a combination the model refuses.

  • Test: new packages/sign-in-core/src/response-release/sign-in-response-release.unit.test.ts (unit lane), with Hegel derandomize: true and no stored example database.
  • Passes when: for every generated case, the status, the error code or body, and whether cleanup ran, all equal the model's. The model is the 20-step decision table on the Program Design, covering introspection (passed through, {"active": false}, or the body with checkedAt), client_credentials, person tokens for central's admin audience and for the management audience, refresh credentials, and thrown ports.
  • Fails on: a deliberate mutation, run by the Verifier and then reverted, that removes the owner-fleet-CLI check on refresh credentials (sign-in-response-release.ts, the ownerFleetCliClientId comparison). Hegel must find a case where a refresh credential is released to another client.
  • The existing family (claims round trip, person-identity-contracts.unit.test.ts:118) keeps passing.
  • Reference: R33 and journey SO2's dispatch rows.
  • Unverified: the device-code family (B3).

V8 · "Limited" on Miniflare's real counter; reset on the controlled clock (S9)

Proven by: the over-limit cases passing on Miniflare's real binding, and failing when the binding is taken out.

  • Tests: people-request-limits.host.e2e.test.ts, the cases at lines 96 and 149, now on the real binding, in pnpm test:e2e:host. The existing reset cases run on the core's limiter with the controlled clock.
  • Passes when: from one address, past the limit, the next request gets 429 with Retry-After, and every sign-in row fingerprint reads back unchanged. Another address still passes. A forged x-forwarded-for is ignored.
  • Fails on: a deliberate mutation, run by the Verifier and then reverted, where the Worker's limiter is built without the binding (createBindingRequestLimiter answering allowed). The "limited" case must then fail.
  • Reference: R52 and journey SO2's flood paragraph.
  • Unverified:
    • the binding's own reset, and counting across Cloudflare locations, which are checked on the private stack;
    • the rare case of a burst crossing Miniflare's real-clock window (Decisions).

V9 · Every stored ID is a UUIDv7 (S10)

Proven by: reading back every ID column of every sign-in table after a full people journey, on both databases, and finding only version-7 UUIDs.

  • Test: new packages/sign-in-test-support/src/stored-identifier-readback.host.e2e.test.ts (host e2e lane), on D1 and on better-sqlite3.
  • Passes when:
    • each of the ten tables the journey fills (S10) has at least one row;
    • every value in their id, …Id and …_id columns parses as z.uuidv7();
    • no token, secret, backup code, device code or user code is UUID-shaped;
    • the existing provider-identifier-cases.ts case (the client-assertion key is the jti digest, and a replay is refused) still passes.
  • Fails on: a deliberate mutation, run by the Verifier and then reverted, that inserts one row with a version-4 ID through the normal store. The test must name its table and column.
  • Reference: R32 and proof row U24.
  • Unverified: IDs stored only by flows this journey doesn't reach. Machine login is B3's.
