Open: your four choices

1 · How long is a lost create reply recoverable?

What you see

A retry within a day gets the exact original answer. Later, a retry that hits “name in use” checks whether it was your own workspace and says so.

What changes

Nothing on Central; one lookup on the page.

What it costs

After a day, the exact original answer is gone; the lookup covers the common case.

Picture

What you see

A retry at any time gets the exact original answer.

What changes

Lead A keeps Central's request ledger indefinitely. Today it keeps CreateWorkspace answers for 24 hours, so this changes stored data on Central. Lead A would design that change with you before B2 builds.

What it costs

Unbounded ledger growth on Central; Lead A's work before B2 can build.

Picture

Cost: exact answer gone after a day.

Cost: unbounded ledger.

It's how Central works today and covers lost replies in practice. The approved text said “original answer” without a time limit, so this narrows it; that's why it's yours.

Create works as today; the after-24-hours behaviour isn't marked delivered.

2 · May key retirement pause sign-in?

What you see

During the window, new sign-ins wait and existing work drains. Then re-sign and withdraw, wait at least 5 minutes for Central to drop the old key, check, and reopen.

What changes

The maintenance entry and its steps; a pause setting; and one small stored fact, a single-row maintenance_pause table every ordinary stamp write checks, so work admitted before the pause can't commit after it.

What it costs

Minutes of no new sign-ins, plus waiting out outstanding token lifetimes before withdrawal. One new table (choosing A approves it).

Picture

What you see

Nothing; sign-in keeps working throughout.

What changes

A stored key epoch; every signer fenced on it; a matching Central contract.

What it costs

New machinery beyond approved B2, in both sign-in and Central, designed before build.

Picture

Cost: minutes without new sign-ins; one new one-row table.

Cost: epoch storage, fences, Central contract.

Key changes are rare and run by you; a short window is far less machinery.

Everything but the retirement procedure builds; rule 6 stays unproven.

4 · How do you run production maintenance?

Key retirement and the digest roll need Better Auth's keys and the sign-in store, so they must run inside the sign-in service. Today there is no way to invoke such an operation (the Node host has no CLI; the Cloudflare host has only the gateway's management binding).

What you do

Sign in as the deployment owner, confirm a second factor, open the maintenance page, run a phase, read the report.

What changes

One project Better Auth endpoint and page, same code on both hosts; everyone but the configured owner gets 404.

What it costs

A deployment-wide operation reachable on the public sign-in origin, guarded by owner identity and a fresh factor.

Picture

What you do

Deploy a small maintenance Worker bound to a private sign-in entrypoint for the window, call it, then delete it; on Node, run a new host command on the server.

What changes

A private WorkerEntrypoint, a maintenance Worker config, and a new Node host command.

What it costs

Two invocation paths and a deploy-and-delete step each time; nothing on the public origin.

Picture

One path on both hosts, behind the strongest identity you have (deployment owner plus fresh factor). Choose B if you want nothing deployment-wide on the public origin.

B, the private entry, stays the design and nothing public is built. B2 can't start until you answer, because the Plan builds one entry only.
