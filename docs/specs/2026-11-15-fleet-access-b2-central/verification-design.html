B2 · Central organizations: Verification Design

How each rule is shown to hold, on the real sign-in hosts paired with the real current Central. Every row names a wrong build that must fail. Nothing has run.

The three things for you

V4 creates 101+ workspaces and 101+ records and requires every one to appear. V6 moves the clock past a statement's expiry while its send is held, then delivers each kind of answer. V7 withdraws a real key and cold-starts Central with an idle organization present.

V3's 24-hour case and V7's window follow your answers to S5 and S12.

Each row traces to Specification. The earlier joint runs were on an older Central; all of these run against Central at the merged directory-read slice.

Where proof runs

The joint fixture sign-in-test-support/src/test-fixtures/b2e/ starts real Central on both pairings; its pins move to Central's final artifacts. Faults use the existing link fault proxy (b2e/link-fault-proxy.ts: hold, drop a reply) and Lead A's two test-only controls (fail the next change-record insert; corrupt a stored column). Heavy runs on Sunclaw.

V1 · Setup (S1)

Create an organization; Central answers provisioned; the row is ready and the stamp record is seeded from Central's facts. Drop the reply: still setting up; Try again sends exactly one request and becomes ready. Reload the page five times: zero sends. Wrong builds: mark ready before the answer; send on page load. Kept: people-organization-provisioning.host.e2e.test.ts cases, now against real Central.

V2 · Authority and atomic create (S2, S3)

  • As a member, another organization's owner, and with a body naming another organization: refused, no rows changed in either Central store.
  • Fail the next change-record insert: create refused or unavailable, and no workspace exists afterwards.
  • Name taken by another workspace: nameInUse; name and description at their byte limits accepted; one byte over refused.

Wrong builds: commit the workspace before the record; skip the body-organization check.

V3 · Operation IDs and lost replies (S4, S5)

  • Drop the create reply after Central applied it; resubmit from the page: the same operation ID is sent and the original answer comes back; one workspace.
  • After nameInUse, the next attempt uses the server's nextOperationId (a UUIDv7 from the injected source in the test's ID sequence); no browser-made ID appears in any request.
  • S5 A (recommended): at 24 hours on the controlled clock, the replay ends; on nameInUse the one lookup at workspaceId = operationId shows created for this caller's own workspace and duplicate for someone else's. S5 B: the original answer still returns at 24 hours and after a Central restart.

Wrong builds: mint a new ID after an unknown outcome (duplicate workspace); keep freshOperationId (source and request check).

V4 · Complete directory and history (S6, S7)

  • Create 130 workspaces and enough activity for 230 records. Page both lists to the end through the real page: every workspace and record appears once, in order.
  • Produce each of the seven record kinds and three origins on the real Central (machine records through the test fixture's enrollment path); all render.
  • Corrupt one stored workspace column with Lead A's control: the directory shows incomplete with that row's ID and column, and nothing is skipped. Fail one history page: incomplete, retryable.
  • Client unit cases: unknown kind, unknown origin, extra field, disorder, duplicates, wrong cursor, oversize page, each rejected.

Wrong builds: build the list from creation records (workspace 101+ missing); keep the three-kind parser (machine record breaks history); skip corrupt rows.

V5 · The page and status (S8, S9)

  • Real Chrome, both pairings: create with a fresh factor; with a stale factor the shipped confirmation appears, confirming retries once and creates; cancelling sends nothing; a second refusal shows an error with no loop. CSP has no violations.
  • Status: for a confirmed organization, an awaiting-answer statement, an expired pending statement, and a refused one, the card shows the right facts; the status reply contains no statement bytes (searched for the compact statement and its digest of bytes). Loading status makes no Central call.
  • 400 px dark layout; keyboard reachable.

Wrong builds: loop on repeated step-up; include the statement in the status reply.

V6 · Renew on use, including late answers (S10)

The existing proxy holds requests before forwarding and drops replies (b2e/link-fault-proxy.ts:55–77,150–201); a request held past expiry would be refused by Central (fleet_statement.rs:67–74). So the proxy gains a test-only holdNextReply: Central processes A while valid, the proxy keeps its reply, the sign-in clock alone moves past expiry (the joint fixture's clocks are separated for this case), then the same reply bytes are released. The guard's deadline is controlled so it doesn't time out first. For each answer while A has expired in flight: provisioned → confirmed; unknown → A kept, unanswered +1; non-stale refusal → A cleared, refused +1; stale with differing expired facts → adopted, then the next pass replaces them, and no Fleet call runs under expired facts. A late answer for A after A was replaced by B: the write loses; B untouched. Two callers at once: one statement in doubt. Kept: organization-statement.host.e2e.test.ts:339–622, the R29 joint case.

Wrong builds: check expiry in settlement (late answers dropped); settle without the bytes condition.

V7 · Key retirement (S11, S12)

  1. Organizations: one active, one idle and not due, one ready with its local record deleted, one setting up.
  2. Run retirement with real native keys: setting up blocks; the record-less one is seeded from Central and re-signed; idle is re-signed. Try Again on the setting-up one, run again: ready to withdraw.
  3. Withdraw the old key from the published key set; cold-start each Central over preserved data; an authorized read succeeds for every organization.
  4. Lose one confirmation answer mid-run: that organization is unfinished and withdrawal is refused.
  5. Three real keys: old A, requested new B, and a different default C. Every replacement statement's header names B.
  6. Equal keys, an unknown key and an expired new key are refused before any work.
  7. Interrupt and invoke the same phase again: before the sent-slot claim, after Central committed, after source confirmation, after withdrawal and before the restart check, after the restart. Each re-invocation reaches the same end; check-after-withdrawal completes only after the preserved Central stores really cold-started and served reads.
  8. Through the chosen entry on both pairings (B: the private entrypoint through a test maintenance Worker and the Node binary; A: the endpoint). Public fetch and the gateway's management binding can't reach it; under A, a member, another owner and a stale factor get 404.
  9. Key facts: after withdrawal (old row expired, still retained), check-after-withdrawal in a fresh process accepts the state; prepare refuses it; a key with no retained row is refused in both phases.
  10. Drain barrier, both pairings: hold a real ordinary renewal after it signed with the old key and before its sent-slot claim (barrier in the stamp store seam); turn the pause on and run prepare; release the held writer: its claim matches no row (the pause row exists), nothing is sent, and prepare reports ready only after its pause row commit and clean re-read. Repeat with a held seed and a held after-create markFleetReady. Hold an already authorized organization creation immediately before its native-create batch; commit the pause row and finish the inventory; release: zero new organization and fence rows, zero setup sends, inventory unchanged. Wrong builds: check only the setting and the final rows (the held writer commits an old-key claim); guard the stamp writes but not the create batch (a new organization appears).
  11. Pause coverage: with an owner browser session open and the pause on, attempt organization creation, setup retry, a Fleet admin call (renewal) and a held deferred write while prepare runs; none commits an old-key stamp; after withdrawal and restart every organization reads. Wrong build: pause only token, sign-in and device endpoints (a new organization signed with the old key fails the check).

Wrong builds: count the outer loop finishing as success; skip ready organizations with no record; ignore setting-up ones; sign with the default key instead of the requested one.

V8 · Engine permission (S15)

  • Unit: the owner holds organization:repairWork, the member nothing; the digest equals the expected value computed from the map.
  • Run the digest roll on both pairings: each organization's revision rises by one with the new digest; a second run changes nothing; deleted organizations are untouched.
  • Before Central's ACK: a new token (revision N+1) gets AuthorizationSyncRequired; after: admitted. An old token (revision N) after the ACK: RefreshRequired. An old process (old loaded digest) refuses issuance with policy-mismatch.
  • Same revision with different content is Conflict, and no ACK is recorded; drop the ACK, then the next invocation or Fleet call pushes the pending revision.
  • Admission order cases on Central: token above a stopped floor → AuthorizationSyncRequired; deleted floor → NotPermitted.

V10 · The machines (S16)

Hegel families in packages/sign-in-test-support/src/core-tests/: organization-setup-transitions.hegel.unit.test.ts, organization-stamp-transitions.hegel.unit.test.ts, key-retirement-transitions.hegel.unit.test.ts, organization-admin-create.hegel.unit.test.ts. Settings { testCases: 1000, derandomize: true, database: hegel.Database.disabled }. Sequences of 0–40 events from a finite catalogue; clock offsets around expiry; retries and duplicated answers. Each family's reference model is written in the test; after every prefix compare next state and proposed effects in full. Besides random sequences, each family includes one fixed witness sequence per legal transition in its table, so every transition is reached by construction. The M4 page path is also driven in real Chrome on both pairings for success after step-up, retry after an unknown reply, and the 24-hour reconciliation (the existing b2e-joint-journey.host.e2e.test.ts:1021–1063 case, retargeted).
