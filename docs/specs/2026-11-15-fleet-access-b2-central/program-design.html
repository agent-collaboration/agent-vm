B2 · Central organizations: Program Design

Keep the existing authority and renewal path; finish its consumers and operator entry. B2 changes sign-in, its page and the producer mirrors. Central implements the directory read and retired-contract cleanup in the named Lead A slice. This design builds on B1-A's merged crypto/clock/ID contract.

The three things for you

The page reads the authoritative directory, and history has its own cursor. Status is a sanitized authorized projection. Definite refusals supply replacement IDs from the server. Actual native key preparation is server-only, with per-organization confirmation and state-preserving cold restart proof.

Three choices remain open: retry, key retirement and engine-console scope. Key maintenance is conditional on selecting it; a live fence or whole console here needs its additional complete design. P9 includes required native engine compatibility and policy rollout either way. Accepted directory/corruption implementation remains a named dependency.

Approved B2's setup, renew-on-use and key-change outcomes remain the yardstick. The Lead approved Stage 1 on 15 Nov and confirmed the private maintenance capability, production owner step and exact dependency name. The owner's 4 Nov approval and later backup/unique-name answers are quoted on Requirements. New paths below are proposed code, not source already on main.

P2 · An authorized, sanitized status snapshot

The stored pending statement stays inside the service. Its bytes are used only to derive expiry; they never enter the browser DTO.

Add organizations/organization-stamp-status.ts for pure derivation, and better-auth/organization-admin-state-plugin.ts for a server-only readOrganizationAdminState endpoint. It accepts the selected organization ID from the handler plus request headers, verifies the cookie-bound live session with caching disabled, and performs a coherent primary Drizzle join of session/person/membership/organization and stamp fields. The read proves the session still belongs to the selected organization and has not expired. Use hasPermission with the joined live role, organization:view and useMemoryCache:false, as organization-permission-check.ts:24–55 does. No permission engine is added.

The existing stamp store gains a joined-facts read under its current injected database boundary. Extend its own parsed row schema rather than duplicate stamp columns in another schema. Authorization is taken from that one fresh read; the handler rechecks session expiry on its injected clock before response release. A missing/ended session is 401, missing permission 403 with no status, unavailable storage 503. The page does not read status first and check permission later. Ordinary GET to the server-only endpoint is 404.

StampAttemptView contains only the stored last attempt time/outcome and separate unanswered/refused counts. Use the existing outcome enum, not a new list of guessed errors. Implement the DTO as strict Zod discriminated unions and derive its type; the display above explains its states, not a parallel interface to maintain.

Derivation samples the injected clock once. Setting-up takes precedence; an absent confirmed digest yields unconfirmed. For a known stamp, compare confirmed expiry to now; derive pending expiry from the locally stored statement's parsed claims, treating invalid pending bytes as expired-pending. No signature or secret bytes enter the DTO. Last refusal remains a historical attempt even if the confirmed stamp is valid; show “Stamp valid until …; last renewal refused …”. The page says “Central work is unavailable” only when current readiness requires it. It must not claim the stamp alone proves the separate revision fence is synchronized.

Units: confirmed and pending expiresAt are Unix seconds, as the signed exp claim is. renewedAt and lastAttempt.at are Unix milliseconds. Derive validity with Math.floor(clock.now() / 1000); render expiry through new Date(expiresAt * 1000), with the UTC label. Strict schemas require safe nonnegative integer times and the existing last-outcome enum. Do not compare an exp value directly with the millisecond clock.

The server initial page state contains organization ID/name, sanitized status and platform.ids.nextId(). Status refresh uses a cookie-only same-origin read endpoint POST /api/auth/organization-admin/status, whose implementation calls the same native authorized read; it performs no Fleet call or renewal. This endpoint returns only the same DTO, with cache-control:no-store. Its public allowlist entry is exact POST only. History and directory continue to authorize at Central as well.

P3 · Replace browser ID minting at the existing forwarder

A delivery attempt and an operation have different lifetimes. Fresh proof for a retry does not change the operation it is trying to settle.

After a definite Central create refusal of nameInUse or conflict, the cookie-only forwarder returns that existing answer plus nextOperationId, minted once from platform.ids.nextId(). The private Central answer and CLI relay remain byte/shape unchanged. Define the browser's strict create-response schema by extending the existing refusal variants for these two reasons; other refusal variants and applied answers remain their current shapes. nextOperationId is required and UUIDv7 only on those two cookie response variants.

A name refusal first triggers one lookup at the old operation's workspace ID. If it finds that ID with the exact requested name, report created and refresh. A null/different-name result displays duplicate-name and installs the supplied next ID for the next submit. An unavailable/malformed lookup displays unavailable and keeps the old operation/content. Conflict displays its own message and installs the supplied next ID. Missing/malformed replacement ID fails closed as unavailable and keeps the old ID. No ID is minted for a transport uncertainty or second-factor refusal. Remove freshOperationId entirely.

An explicit retry reuses its captured submitted body and operation. Editing fields under an uncertain operation follows the existing changed-body conflict contract; it never silently mints another operation. No new field-locking policy or durable browser storage is added. A reload starts a newly rendered operation; it is not claimed to recover an abandoned tab's ID. Branch A's durable original-answer lookup is Central's obligation; Branch B follows the described 24-hour fallback.

P6 · The trusted maintenance capability

This is the conditional window branch. The native RPC handles serializable key operations; the trusted runner owns admission and restart controls. Green is verified completion, rose an explicit stop. Choice B needs its separate live-fence design.

Conditional A design, pending the owner's retirement choice. Add organizations/organization-key-maintenance.ts for the operation/report and better-auth/organization-key-maintenance-plugin.ts for native context. These are composed only by a new private maintenance factory. Node exports the factory for the owner's trusted deployment runner; Cloudflare exposes a distinct named OrganizationKeyMaintenance entrypoint with no public fetch route and no binding to the ordinary gateway. Existing AgentClientManagement is unchanged. Access to that named entrypoint is a deployment credential/capability, not a browser-supplied token or boolean.

The public Better Auth seams were opened in installed 1.7.11: dist/plugins/jwt/index.mjs:214 exports createJwk/resolveSigningKey/signJWT; utils.mjs:43–61 creates and encrypts the native key; adapter.mjs:9–13,52–53 selects live keys by creation time. index.mjs:124–129 filters published expiry plus its default 30-day grace. native-jwt-options.ts:6–10 currently sets EdDSA only, with no rotation interval. Server-only endpoints are native supported API (@better-auth/core/dist/api/index.mjs:86–106). No private adapter import, custom signing format or library patch is needed.

runOrganizationKeyMaintenance is the runtime-free orchestration in the same new organization module. Its ports are OrganizationNativeKeyMaintenance and QuiescedMaintenanceControl. The native capability above has serializable requests/results and is what the separate Worker entrypoint exposes. Host-control callbacks never cross Worker RPC as JSON or function arguments. Node supplies the same native capability in process.

QuiescedMaintenanceControl belongs to the owner's trusted runner, outside ordinary sign-in. It checks current admission/drain state and the inventoried credential-safety deadline, then drives preserving-state restart/read probes. Results are quiesced | not-quiesced | unavailable, and each restart/read is verified with compared identities or failed with a bounded reason. Locally the runner controls actual harness admission/processes. Production's owner must supply the deployment controls and original observations before invoking the native capability; a caller's boolean is not proof. The private capability grants native key power to that trusted runner, so it must never be exposed to the gateway or public route.

Drain includes deferred after-response signing and renewal work, including Worker waitUntil work and Node's tracked deferred tasks. A completed HTTP response is not proof its signing work settled. A held request or deferred signer keeps the trusted runner not-quiesced; no native key mutation is invoked while that state holds.

The window is exclusive to one maintenance runner for this deployment, including its private key operations. Native withdrawal rejects identical old/current IDs, an absent old row, a nonlive replacement or a current-key mismatch before writing. The trusted runner must keep other maintenance invocations out of the window; this procedure does not claim the live multi-writer guarantee that choice B would add.

The composed runner returns blocked with its failing precondition before withdrawal, unknown for an unsettled native result, withdrawn-unverified after a failed post-withdrawal probe, or withdrawn-verified with the compared key/org/directory identities. Each is a strict schema-derived variant. Only the trusted runner reopens admission after a verified result.

  1. Prepare: while maintenance traffic is quiesced, check the expected current key. Call native createJwk; Better Auth's existing injected generateId supplies its UUIDv7 (provider-configuration.ts:152–153). Resolve again and require the returned new ID to be current and both public keys visible. Same-time ordering that leaves the old key selected is unfinished, not success. A lost create result returns unknown: inspect current key metadata and explicitly resume using that ID; never mint another key automatically.
  2. Re-sign: inventory every organization's ID/fleetState through injected Drizzle, without a ready-only filter. The current helper filters ready rows (membership store:48–57); a settingUp organization may already hold an old Central stamp after a lost reply. Setting-up blocks retirement and requires its existing explicit setup retry; maintenance sends it no setup. A ready organization with no local confirmed stamp instead enters M2's key-change seed path, then bounded re-sign under the new key. Ready + setup retry returns immediately and is not its repair path (organization-provisioning.ts:76,94–107). Retain the existing empty-record key-change behavior (organization-statement.host.e2e.test.ts:624–654). Require the expected new key still current, use existing deadlines/pending rules, then independently read every Central digest/expiry/key. Withdrawal waits for agreement and no pending/unseeded row. An outer complete with an unfinished item is blocked. Re-read inventory/current key; any set/state/key change needs another pass.
  3. Credential-safety gate: the trusted runner inventories all key-dependent credential families and their maximum expiry. Record the last possible old-key issue after traffic drains. Withdrawal must not precede that expiry. Current configured person/m2m access tokens are at most 300 seconds (deployment-configuration.ts:76; provider-configuration.ts:366–377). That is not a bound for every future client, ID token or machine profile. An unknown family blocks withdrawal; no invented grace interval.
  4. Withdraw and recheck: reassert quiescence, credential safety, new current key, unchanged all-organization inventory with no setting-up/unconfirmed row, and Central agreement. Retire only the explicit old native key through its existing public adapter model's expiry field; use the same explicit grace-period value as native JWT options, preserving today's default of 30 days, so expiresAt + gracePeriod is at or before the current injected instant. The native JWKS endpoint must actually omit the old key, and key selection must keep the new one. The native provider retains its encryption/serialization; B2 never writes raw key bytes.
  5. Cold proof before reopen: restart Central preserving each organization's existing store and clearing runtime/key caches. Read the stored stamp facts and authorized directory again, with only the new key available from the actual JWKS endpoint. Compare organization/directory identities before and after. Failure after withdrawal returns withdrawn-unverified; keep maintenance closed and hand control to the owner. No automatic rollback or false completed report. Success is withdrawn-verified, with nonsecret per-org facts and target identity.

The native expiry write is isolated in the Better Auth boundary through its supported adapter; all backing storage still uses the injected Drizzle adapter. A current-key/old-key mismatch or absent key is a typed refusal before mutation. Repeating an already-withdrawn old key rechecks public JWKS and the cold proof; it does not create a key or repeat stamp effects. This is an operator flow with explicit preparation, verification and withdrawal, not a scheduled key manager.

Choice B: a live issuer key epoch would fence every sign/release and stamp writer and require Central to reject stale epochs after handover. It needs a persisted issuer epoch and a compatible closed stamp/admission format, plus race proof for all credential paths. Those contracts are not approved here. If selected, hold this operation's implementation, return to Program/Verification Design and obtain the schema/contract approval before any code depends on it.
