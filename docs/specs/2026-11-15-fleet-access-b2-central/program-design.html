B2 · Central organizations: Program Design

How B2 is built in Switchboard's sign-in core (packages/sign-in-core/src/ unless stated), against Central's private link. Most parts exist; this design adds the directory and status reads, moves the page onto the shell, makes operation IDs server-side, formalizes the four lifecycles as pure machines, adds the trusted maintenance entry, and rolls out the engine permission.

The three things for you

M2: the answer to a send is settled by one pure function whatever the clock says, so a late answer is never dropped. M3: retirement finishes only when every organization names the new key. The policy rollout is one conditional write per organization.

The detail follows the recommendations (24-hour recovery, maintenance window, console later). Branch notes list what each alternative changes.

Built on S1–S16; source at Switchboard f3b2b88b and codex-router e7b709f6a; Lead A's engine P8 at 066ea560.

The four machines

Common shape: closed Zod unions for state, event and effect; transition(state, event, context) → { kind: 'next'; state; effects: readonly Effect[] } | { kind: 'refused'; reason }; an inline x satisfies never as the default branch of every switch over state, event and effect. Runners are injected, perform effects only after the state write that proposed them committed, and turn results into events. A conditional write that loses runs none of its effects.

M2 · Stamp renewal

State is the stored OrganizationStampRecord (organization-stamp-renewal.ts), parsed strictly. Two pure functions:

  • decideOrganizationStampStep(record, sentExpiresAt, now, currentKeyId), unchanged in meaning: not-ready | seed | current | resend(statement) | sent-expired | sign(replaces). Each maps to one effect: none, read-central-facts, none, send(statement), none, sign(replaces) then claim-sent.
  • settleStampAnswer(record, sentStatement, answer, centralFacts?) → the conditional write to make: confirm(stamp) for provisioned; record-try(outcome, keep-sent) for unknown; record-try(refused-…, clear-sent) for a non-stale refusal; for stale, needs centralFacts: same digest → confirm; different → record-try(refused-stale, adopt-central); none → record-try(refused-stale, forget-central) then reprovision; timeout → keep-sent.

The clock never enters settleStampAnswer. It depends only on the bytes that were sent, the answer and Central's facts. Every write it returns is conditional on the record still holding those bytes, so a late answer for replaced bytes simply loses. Expiry only affects decideOrganizationStampStep, which won't start a new send for an expired statement. A ready organization with no confirmed facts decides seed, which reads Central and seeds; that is how key retirement reaches ready-but-unseeded organizations.

Key binding. An invocation takes { oldKeyId, newKeyId }. Before any work it refuses same-key if they're equal, unknown-key if either isn't in Better Auth's JWKS, and new-key-unusable if the new key is expired or its algorithm differs. For the whole invocation the runner passes signingKeyId: newKeyId to Better Auth's native signJWT (supported in 1.7.11, dist/plugins/jwt/sign.mjs:17–33), through signOrganizationStatement (organization-statement-signing.ts, which today passes no key override), and uses newKeyId as the currentSigningKeyId for M2's decision. So the replacement statement names the requested key even when Better Auth's default is a third key.

Two key facts, kept apart. Better Auth keeps every key as a row in its jwks table (read by ID through its adapter, dist/plugins/jwt/adapter.mjs:5–8,24–32) and publishes only the rows not past their expiry and grace (dist/plugins/jwt/index.mjs:118–140). Retained means the row exists; published means it appears in the public key set. Withdrawal means making the old key unpublished (its row expires) while its row stays; republishing is therefore possible if the check fails. Validation is per phase: prepare needs both keys retained, the old key published and the new key usable; check-after-withdrawal needs the old key retained but not published.

Phases and reconstruction. Closed phases: prepare (re-sign and verify; ends in ready-to-withdraw or blocked), withdraw (re-verifies read-only and ends publication; ends in withdrawn, or refused not-ready with no re-signing), and check-after-withdrawal (ends in done or failed). Nothing about a run is stored. Each invocation rebuilds its state from facts: the two key facts above, every organization's fleet state and stamp record, and Central's facts read for each. prepare with the old key already unpublished is refused (already-withdrawn); check-after-withdrawal with the old key still published is refused (not-withdrawn). The check re-enumerates every organization, including any created since prepare; any organization not confirmed on the new key fails the check, and the owner republishes the old key, runs prepare again, and withdraws again. A crash at any point is handled by invoking the same phase again: re-signing repeats safely through M2's conditional writes, and the check repeats its reads.

Withdrawal time is never earlier than the truth. Publication stops when the write that unpublishes the key commits, not when a clock was read before it. So withdraw makes two writes to the old row, both through Better Auth's database adapter (update on the jwks model), and the row stays retained throughout.

  1. Unpublish. Set expiresAt to a fixed sentinel far in the past (the Unix epoch). The write is conditional on the key still being published. The publication filter (jwt/index.mjs:118–140) drops the key from the commit moment C onward.
  2. Record. Only after the adapter acknowledges the first write, read now from the injected clock. Because the acknowledgement comes after the commit, now ≥ C. Then set expiresAt to now − grace, conditional on the row still holding the sentinel. That cutoff is already in the past, so the key stays unpublished.

After step 2, the row's expiresAt + grace is withdrawnAt, a clock reading taken after C: an upper bound on the real end of publication. Reconstruction from the row:

  • Sentinel present: step 1 committed and step 2 didn't. check-after-withdrawal refuses withdraw-incomplete. Invoking withdraw again sees the sentinel, which proves the commit already happened, and performs step 2 with a fresh now (still ≥ C).
  • Past cutoff, not the sentinel: the row holds step 2's reading, or the key's own natural expiry, where publication really did end at that cutoff. withdrawnAt is that cutoff. withdraw is refused already-withdrawn.
  • Still published: check-after-withdrawal is refused not-withdrawn.

No step ever writes a cutoff from a clock read before the unpublishing commit.

When Central can no longer trust the old key. Central holds sign-in's keys only in memory (IssuerKeyCache, a Mutex<Option<…>>, issuer_key_cache.rs:148–157 at Central e7b709f6a). Each response is kept for its max-age, capped at MAXIMUM_KEY_AGE_SECONDS = 300, counted from when the response arrives (issuer_key_cache.rs:9,174–203; issuer_key_resolution.rs:49–59; test cache_lifetime_is_measured_from_the_key_response_receipt). A statement signed with the new key uses a fresh cached set without refetching (issuer_key_resolution.rs:31–34). So a response requested just before W and delivered late can keep the old key trusted past W + 300 s, and a successful read proves nothing. The fetch itself is bounded at 10 seconds, covering both the send and the body: natively today (collaboration-central-tokio/src/sign_in_trust.rs:28–31); on Cloudflare by Lead A's central slice: bounded Cloudflare key fetch (10 s), where today's collaboration-central-cloudflare/src/sign_in_trust.rs:84–109 is unbounded. A fetch past the bound fails as Unreachable and caches nothing. Any response containing the old key was requested before W, arrives by W + 10 s and expires by W + 310 s. check-after-withdrawal refuses central-key-cache-window before withdrawnAt + 310 s. Every value involved is a duration after the same real moment, so a clock offset between sign-in and Central doesn't matter. Both inputs are facts already present, so nothing about the run is stored. The window makes the check correct without depending on a restart. Approved rule 6 still requires each Central to pass a cold restart, so the procedure restarts each Central after the window and before the check: Tokio by a process restart, Cloudflare by a Central deploy. That is your step. The report records that the check ran after it. The runner reuses renewOrganizationStampForUse for each renew(id), with the key override. In production, the owner invokes withdraw between the other two phases.

The engine permission rollout

Add 'organization:repairWork' to fleetPermissionSchema and to the owner's native role and permission maps; the member role gets nothing. Accept Central's new closed refusals in fleetAdminRefusalReasonSchema. Recompute the version-1 digest from the actual map with injected crypto; the expected value with only this addition is aa2fc571158408fdcdcf1d8d0319f0a0886f5570bc60cc52f85a45005fc75f91 (from 2d31b5d72716e64e255d8858c231f593155289fb03ed354c4b762890667a3c22), checked by a test.

organizations/policy-digest-roll.ts, run from the maintenance entry right after deploy: for each organization, one Drizzle update on organization_authorization_revisions setting permission_policy_digest = new and revision = revision + 1, conditional on permission_policy_digest = old and the state being active or stopped (deleted untouched). The existing delivery path pushes the new revision. Between deploy and the run, issuance refuses with policy-mismatch (person-fleet-issuance.ts:76–78). After the run, a new token names revision N+1 while Central's floor is still N, so Central answers AuthorizationSyncRequired (token above the floor, request_admission.rs:182–196) until the floor push is acknowledged; then it admits. Old tokens at N get RefreshRequired once the floor is N+1. Nothing is admitted on a mismatch.

State is rebuilt from the fence row (digest, revision, state) and its delivery ACK; nothing new is stored. A crash after the write is recovered by the next invocation or the next Fleet call's drain, which push the pending revision. The roll's report counts acknowledged, pending (with reasons) and skipped per organization; it finishes only when every non-deleted organization is acknowledged.

The maintenance entry

better-auth/sign-in-maintenance.ts defines two operations over the injected configuration: retireSigningKey({ oldKeyId, newKeyId, phase: 'prepare' | 'withdraw' | 'check-after-withdrawal' }) (M3) and rollPolicyDigest() (M5), each returning a closed nonsecret report.

Invocation depends on your fourth choice; until you choose, the private entry (B) governs and no public route is built. Correcting the earlier draft: sign-in-host-node has no CLI today.

  • B, private entry (default until chosen). Cloudflare: a SignInMaintenance WorkerEntrypoint exported from the sign-in Worker beside the existing management entrypoint (sign-in-host-cloudflare/src/index.ts:14–25 shows the pattern), built from the same configuration so it has the keys and store. No public route or gateway binding reaches it. For a maintenance window the owner deploys a small maintenance Worker whose only binding is { service: sign-in, entrypoint: SignInMaintenance }, calls it with a secret held in the owner's vault, then deletes it. Node: a new binary sign-in-maintenance in sign-in-host-node that composes the same configuration from the host's environment, as the listener does, and runs one operation on the server. Both print the closed report.
  • A, owner-only endpoint (if you choose it). A project Better Auth plugin endpoint POST /api/auth/maintenance/{operation} and a small page, same on both hosts, admitting only the configured owner (configuration.ownerEmail, verified) with a second factor from the last 15 minutes; everyone else gets 404; the gateway has no path to it. This puts a deployment-wide operation on the public origin, which is why it's yours to choose.

The maintenance window (S12 A) needs a pause control; none exists. Add a deployment setting SIGN_IN_MAINTENANCE_PAUSE. When true, every ordinary writer that can sign or commit an organization stamp, or issue a credential, answers 503 maintenance: Better Auth's token, sign-in and device endpoints; /api/auth/organization/create and its after-create provisioning (organization-provider-options.ts:95–96,119–121,154–162); the explicit setup retry (organization-provisioning-plugin.ts:33–64); and every Fleet admin call (whose guard runs renewal). After-response deferred work checks the setting before writing. Only the maintenance operation writes, and it signs only with the new key. Pausing and reopening are owner deploys.

The drain barrier. The setting stops new requests but can't stop a writer admitted earlier (for example one paused between signing with the old key and claiming the sent slot, organization-stamp-renewal.ts:236–253). So option A also needs one small stored fact: a single-row maintenance_pause table in the sign-in database, written by prepare as its first step. Every ordinary stamp write (claimSentStamp, confirmSentStamp, recordStampTry, seedConfirmedStamp, recordUnsentTry, forgetConfirmedStamp, markFleetReady, in storage/organization-stamp-store.ts and the provisioning store) adds the condition that no pause row exists, in the same conditional Drizzle update it already makes. Organization creation is guarded too: the batch that inserts the native organization and its fence (storage/authorization-fence-mutations.ts:303–325) inserts both with INSERT … SELECT … WHERE NOT EXISTS (maintenance_pause), as one batch; if the guard matches nothing, neither row exists, the create fails with maintenance, and after-create provisioning never runs; maintenance's own writes carry its invocation and skip that condition. Once the row is committed, no earlier-admitted ordinary writer can commit anything, on any instance, old deployment or new; the barrier is the commit, not a wait. An ordinary send only follows a successful claim, so no old-key statement reaches Central after the row either; a creation that had already sent leaves its organization setting up, which blocks retirement until handled. prepare reports ready-to-withdraw only after the row is committed and its final re-read is clean; reopening deletes the row. This adds a table, so choosing A approves it (Decisions).
