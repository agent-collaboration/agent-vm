B2 · Central organizations: Specification

One organization can be administered from sign-in through its real Central: confirmed setup, safe workspace creation, complete directory/history, honest renewal status and a safe signing-key handover. The Requirements own why this is needed. The rules below define the observable result.

The three things for you

Every directory workspace and history page is reachable; every current record variant is readable; an unknown answer preserves the operation ID; pending or expired renewal is visible without credentials; and key retirement cannot strand an idle organization after a cold restart.

Three answers remain open on Decisions: the late-retry promise, maintenance versus a live key-epoch fence, and whether the whole engine-operations console belongs here or in its named later feature. S5, S12 and S15 preserve the branches; no recommendation is selected. Production maintenance remains owner-run.

The sources are approved B2, U15/U21/U27/U43/U45 and R29–R34/R53/R55 in the approved design, plus the later owner answers quoted in Requirements. The 4 Nov approval is the owner's “yes you need anytnhign?” (Fleet transcript lines 71226/71230). These are future obligations; current source and historical proof are distinguished on the Audit. No implementation success is claimed.

The things these rules describe

Each organization is isolated. The operation and its record refer to one creation; a retry does not create another operation merely because a reply was lost. A stamp replacement changes the signed assertion, not the organization.

The observable rules

S1 · Setup becomes ready only on confirmation

Creating an organization MUST need no per-organization deployment. It starts setting up. A valid confirmed provisioning answer makes it ready; unavailable, lost, malformed and refused answers do not. Repeated provisioning of the same organization changes no existing stamp or duplicate setup record. A permitted explicit Try again sends one request for that ID; reading or refreshing the setup page sends none. The existing setup page is BG's surface; B2 supplies its real private-link behavior.

Reference: approved B2 setup flow and OD22/OD23. Wrong if: a stand-in success, lost answer or page reload can declare setup complete.

S2 · Organization and permission checks precede disclosure

Every B2 request MUST remain bound to its authenticated person, current organization, required permission and actual operation. A member, another organization's owner, wrong body organization, wrong reached store, stale authority, invalid proof or wrong token audience/kind MUST reveal and change nothing outside its authority. Public requests MUST have no route to internal provisioning or maintenance. Central independently rechecks the reached organization's identity. The existing person-fleet token/revision fence remains mandatory; S15 changes the native role map through that existing fence.

Reference: U15/U21/U27/U45, R34/R55 and the already-landed authorization contract. A status read uses organization:view, directory reads the same, history organization:readAudit, creation workspace:create; all already exist in fleet-permission.ts:4–13.

S3 · A workspace and its record commit together

An allowed create MUST produce one workspace with the requested valid name/description and one person-origin creation record naming the checked permission. If the record write fails, neither effect commits. A different workspace using the unique name is nameInUse. A conflict or unknown answer is never called “Workspace created.” without a valid original answer or the selected S5 reconciliation. Current name/description bounds stay unchanged: 1–256 UTF-8 bytes with no surrounding whitespace, and description up to 2,048 UTF-8 bytes (fleet-admin-operation.ts:19–40).

S4 · Operation IDs come from the injected source

The initial and replacement operation IDs MUST be UUIDv7 values from the server's injected source. Unknown transport/result outcomes keep the same operation and content. A definite nameInUse or conflict permits a fresh operation for the next corrected attempt. An uncertain reconciliation lookup keeps the original operation and says unavailable. No browser time/randomness UUID formatter remains. A new token/proof on a retry does not change the operation ID.

S5 · The owner chooses the late-retry promise

Open: retry choice. Common obligations: no duplicate effect, no cross-person/organization answer, and no false success after a lost reply. A changed request cannot rewrite a retained answer.

S6 · Directory and history are complete, separately

Every workspace in the authoritative organization directory MUST be reachable without reconstructing existence from creation records. Directory traversal orders workspace IDs ascending, with an exclusive cursor and pages of 1–100, using the accepted shared contract below. History uses its existing ascending record-ID cursor. A stable collection is traversed without omission or duplication, including beyond 100 earlier records. Each page is a current read; no cross-page snapshot is promised. Refresh restarts at the first page to include concurrent changes. A failed page remains visibly incomplete and retryable; it cannot become a complete empty list. A corrupt stored workspace row fails the whole page with the authorized diagnostic below; it is never skipped or coerced.

Dependency: Lead A: central workspace directory read, scheduled after the engine's deliverable 1 merge. This slice also removes the retired people-command contracts and supplies the accepted test-only record-insert failure/stored-column controls. The request/response and corruption refinement were accepted by Lead A, 15 Nov, relayed by the Lead; implementation and final exported artifacts remain to land. B2's directory consumer follows that slice.

S7 · Every current record kind and origin is readable

The closed consumer MUST accept organizationProvisioned, stampRenewed, workspaceCreated, machineEnrolled, machineRevoked, machineExpired and allowanceChanged. Origins are signInProvisioning, automatic and person; only person carries person/permission fields. These are Central's current variants:15–23,59–66. B2 only displays machine events; B3 owns their effects.

A genuinely unknown kind/origin or extra field MUST retain today's closed-parser malformed-reply outcome and show history unavailable; never skip the record or coerce it to another kind. This preserves the existing parser's failure policy (fleet-admin-client.ts:158–160). All known and unknown cases need producer fixtures and actual consumer proof.

S8 · The page uses the existing sign-in design and factor behavior

The served page MUST use the existing page shell, stylesheet, nonce policy and shared controls. The owner can create, page directory/history and refresh status. Creation requires a second factor no older than 15 minutes; reads require none. On secondFactorRequired, use the shipped confirmation component, then retry the same action once with fresh server-side authority. Cancellation/failed confirmation sends no retried create. A second refusal settles with a visible error rather than looping. At 400 px every control, status and paging action remains usable; names/descriptions render as text. Credentials stay out of page state, responses and script-readable cookies.

S9 · Renewal status tells the truth without releasing the statement

The authorized owner MUST see setup/unconfirmed, confirmed expiry, a statement awaiting an answer, its expired-pending condition, last renewal time and the distinct unanswered/refused outcomes already retained. A valid confirmed stamp may coexist with a failed renewal: show both facts rather than calling the organization blocked. An expired confirmed stamp blocks dependent work. Status loading does not itself renew or provision. Storage failure shows unavailable. The response MUST contain no compact signed statement, session/access token, proof or private key.

S10 · Preserve renew-on-use, recovery and the fence

The statement lasts 120 days and renews when 60 days or less remain, before a Fleet call. At most one unanswered statement is saved; all resends use exactly its bytes, including after restart/concurrent callers. Unknown/refused counts stay distinct. Expiry prevents starting a new send, but every result of an already-started send MUST still settle in pending or sent-expired while its exact bytes match: success confirms, unknown retains/counts unanswered, a nonstale refusal clears/counts refused, and stale starts the existing facts reconciliation. That reconciliation may adopt differing verified facts even when expired, then replace them; expired facts authorize no work. A late result for superseded bytes loses the conditional settlement. A valid stamp permits a call despite renewal failure only if the existing revision fence also allows it. Expired pending bytes are retained as the recovery limit until a matching in-flight result settles them. No cron, timer, notifications or reset service is added. Existing bounded deadlines and empty-Central recovery stay unchanged.

S11 · Trusted key preparation covers every organization

A server-only maintenance capability MUST use Better Auth's native keys and signing helpers, never a public HTTP path or the gateway's ordinary agent-management binding. It identifies explicit old/new keys and inventories all known organizations. A setting-up organization may already hold a Central stamp after a lost reply: it blocks retirement until the existing explicit setup retry confirms it, with no automatic setup send. A ready organization with absent local confirmed facts is different: maintenance MUST enter the existing authoritative seed/re-sign path directly, without an ordinary admin call or setup retry. Every ready organization, including idle/not-due and ready-but-unseeded ones, uses the conditional renewal/re-sign rules and an independent Central facts read. Withdrawal waits until all are ready, source and Central agree on the new key, and none has pending bytes. Any unfinished organization blocks retirement. Each real Central must cold-start over preserved data with the old key unavailable and serve an authorized read using the replacement.

The report contains IDs/digests/status only. Native key creation, pending sends, failed checks and a lost answer remain explicit outcomes; they never become permission to delete a key. If key selection or the organization set changes, recheck. Existing credential verification lifetimes also constrain withdrawal; B2 does not shorten them.

S12 · The owner chooses the interruption cost of retirement

Open: key-retirement choice. A requires a trusted maintenance window: stop new sign-in issuance, drain in-flight requests and deferred after-response signing/renewal work, re-sign/verify, honor outstanding credential lifetimes, withdraw the old key, perform preserving-state cold restarts and recheck before reopening. Failure before withdrawal keeps the old key. Failure after withdrawal remains a maintenance failure; no success or automatic rollback is claimed.

B requires uninterrupted operation and a live key-epoch fence that prevents a paused old-key signer from committing or releasing after the handover. That adds a persisted issuer epoch, fencing of every relevant native release/stamp writer and a compatible Central admission contract. This is new machinery outside approved B2; selecting B returns its affected Program/Verification design for completion and approval before implementation. It never silently selects A.

S14 · Keep the core and its proof honest

B2 builds after B1-A merges and consumes its injected crypto/clock/ID/deadline contracts. New service code reads no runtime globals, uses injected Drizzle and closed discriminated types, and follows existing architecture/UUID checks. Tests use controlled clocks/events and preserve property coverage. Both real local sign-in/Central pairings and the actual browser journey must cover the final pinned build. Heavy runs go to Sunclaw. Inventory/skips, historical runs, local pairings, hosted bindings and production execution keep their own evidence names. No new CI gate is authorized.

S15 · Engine compatibility and a safe permission-policy rollout

Dependency: Lead A deliverable 1, the Central engine, specifically its Program Design P8. This is separate from the directory-read slice. The new organization:repairWork permission MUST be mapped to the native owner role only, with member empty, in the closed Fleet schema, native actions/role map and native permission-check request map. Shared closed refusals gain notFound, notRetired, discardUnsupported and stale; unknown values remain malformed. EngineHealth/EngineListRetired use existing organization:readAudit; EngineRetry/EngineDiscard use repairWork and a recent factor. Until the role mapping is available, Central changes refuse NotPermitted.

The native-derived version-1 canonical policy digest changes from 2d31b5d72716e64e255d8858c231f593155289fb03ed354c4b762890667a3c22 to aa2fc571158408fdcdcf1d8d0319f0a0886f5570bc60cc52f85a45005fc75f91 when repairWork is the sole addition. Recompute it from the actual map using injected crypto; the ten owner permissions and exact artifact are specified in P9. Person-fleet permissions/digest change. Organization stamp claims contain no policy digest and MUST NOT acquire one or be re-signed solely for this policy change.

A small private conditional writer MUST use the existing organization fence state/revision/digest/ACK/delivery fields, with no migration or new attempt table. Stop increments N to N+1 while retaining the old digest. Resume is permitted only after that stopped floor is ACKed and the compatible map is loaded; it increments again to N+2 with the new digest. Resuming derives from active source with ACK below N+2, never a new stored string. Failed compare-and-set writes return a typed refusal and execute none of the candidate's proposed effects; deleted/overflow never resets a revision.

The trusted rollout runner MUST hold a target-specific issuance pause from stopped N+1 until the ACK of active N+2; its deployment control fails closed on runner failure/restart. Normal issuance before floor ACK remains allowed by r3:128; do not add a global ACK condition to decidePersonFleetIssuance. Unknown ACK stays pending and retries the identical payload. Delivery keeps its separate rules: higher revision is stored unless the floor is Deleted; identical same-revision state/digest is Acknowledged, changed is Conflict, and lower is Acknowledged unchanged.

Request admission has this precedence after valid proof/time and a present floor (person_request/request_admission.rs:182–196, Central e7b709f6a): Deleted → NotPermitted; otherwise token revision above floor → AuthorizationSyncRequired; otherwise Stopped → NotPermitted; otherwise Active with older token revision → RefreshRequired; otherwise Active with mismatched digest → RefreshRequired; otherwise this organization-floor check passes. In particular, a token at N+2 against stopped N+1 is AuthorizationSyncRequired. A deleted floor is NotPermitted even for an ahead token. This preserves Central's contract; later admission checks still apply. Production pause/deployment/resume are owner actions.

Open scope: engine choice. A maps permission/refusals and delivers the safe policy rollout here, exposing none of the four engine routes through sign-in; the whole console is named Engine operations: inspect and repair retired work. B adds all four forwarded routes, typed results, health/list paging, guarded repair UI and CLI as a whole feature; its complete consumer/UI/verification revision must be approved before implementation. No partial repair console or unchosen branch is authorized.

S16 · Explicit pure machines and effects for every B2 lifecycle

Setup, stamp renewal, key retirement and policy rollout MUST each have the closed state/event/effect inventory in P8–P9, a pure transition with injected facts/time and inline value satisfies never at each narrowed state/event/effect switch boundary. Add no shared exhaustiveness helper. Stored variants are strictly parsed; unknown state strings fail loudly through runtime validation, not through the erased TypeScript expression. Every effect is closed proposed data, interpreted exhaustively by an injected runner only after the corresponding state commit; a result becomes a new event. A losing conditional write may discard proposed effects but MUST execute none and leave no half-write. Retarget setup/renewal through these machines and remove competing imperative paths; keep Better Auth internals as shipped.

Key-run phases remain ephemeral. Restart reconstructs from actual native keys and pending/confirmed stamps; policy resuming reconstructs from the existing fence and ACK plus observed deployment pause/map. No B2 run/attempt table or lifecycle columns are added. Hegel compares complete next state and effect data against independent models, with deterministic generators, time moves, retries, concurrent pairs and crash points. H1–H4 name the permanent files, invariants and required shrinking wrong builds. Real conditional-write races on D1 and better-sqlite3 remain required alongside pure proof.

The accepted directory contract B2 needs from Central

Accepted by Lead A, 15 Nov: ListWorkspaces uses POST /organization-admin/v1/workspaces over the existing private link and organization:view. It reuses the current WorkspaceView, including description and state. It adds no permission and changes no role-policy digest. Accepted source: Lead relays 01a1e125-7a0a and 01a1e12a-7ec5; these are interface agreements, not implementation receipts.

after is null or a lowercase workspace UUIDv7, exclusive. limit is an integer 1–100. All directory states are eligible. Results are strictly ascending by workspace ID, bounded by limit. Central looks ahead one row and returns the last emitted ID as next only when more exist; an empty or final page has null. The consumer rejects nonprogress, duplicates, out-of-order rows, excess size and inconsistent cursors. The history result shape stays unchanged; a short history page terminates traversal, and a full final page requires one subsequent empty read.

Exactly one row identity variant is present. rawKey is used only when the stored workspace ID cannot parse, is bounded to 128 Unicode code points (the JSON Schema character count), and requires column workspace_id. A valid lowercase UUIDv7 relabelled as rawKey, unknown error/column, extra fields, both identities or an invalid parsed ID are malformed replies. Render the identity as text; disclose it only after the existing admin authorization. Other 503s retain today's bare unavailable answer. An unknown nonempty 503 body is malformed, not a fabricated diagnosis.
