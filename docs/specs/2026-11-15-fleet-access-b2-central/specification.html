Setup

S1 · Ready only on confirmation

Creating an organization MUST need no deploy and starts setting up. Only a confirmed provisioning answer makes it ready; unknown, lost, malformed and refused answers don't. Try again sends one request for that ID; reading or refreshing the page sends none. Repeating provisioning never creates a second stamp or setup record.

Administration

S2 · Checks before anything is shown

Every request MUST be bound to its person, current organization, permission and operation. A member, another organization's owner, a wrong body organization, a wrong reached store, stale authority, an invalid proof or the wrong token kind reveals and changes nothing. Permissions are the existing ones (organizations/fleet-permission.ts:4–13): status and directory organization:view; history organization:readAudit; create workspace:create. No public route reaches provisioning. Maintenance is one hidden owner-only endpoint and page on the sign-in origin. It MUST be linked from nowhere. For everyone except the configured owner with a live session and a second factor from the last 15 minutes, it MUST answer exactly the response an unknown path gets, whatever the method, body, content type, query or origin; no parsing or validation response may come first. The gateway MUST have no path to it. Each run MUST record an intent before any effect and an outcome after. A failed intent record means nothing runs; a missing outcome means the run is reported as unconfirmed.

S3 · A workspace and its record commit together

An allowed create MUST make one workspace with the valid name and description and one person-origin record naming the checked permission; if the record write fails, neither exists. A name already used by another workspace is nameInUse. Bounds stay as today: name 1–256 UTF-8 bytes with no outer whitespace, description up to 2,048 bytes (organizations/fleet-admin-operation.ts:19–40).

S4 · Operation IDs come from the server

Initial and replacement operation IDs MUST be UUIDv7 from the server's injected source. An unknown outcome keeps the same operation and content. Only a definite nameInUse or conflict earns a new ID for the next attempt. The browser makes no IDs.

S5 · How long a lost create reply is recoverable (your choice)

Common to both: no duplicate workspace, no answer for another person or organization, no false success. A (recommended): today's behaviour: the original answer for 24 hours (organization_workspace_plans.rs:103–135); after that, on nameInUse, one lookup at workspaceId = operationId may establish it was this caller's own workspace, otherwise duplicate or unavailable. B: the same operation, person and content always get Central's original answer, byte for byte, even after restarts and after 24 hours; Lead A's retention must cover it before build.

S6 · Complete directory and history, separately

Every workspace in Central's directory MUST be reachable through ListWorkspaces (contract below), never reconstructed from history. History uses its existing ascending record-ID cursor. Both page beyond 100 without loss or duplication for a stable collection; each page is a fresh read. A failed page shows “incomplete” and can be retried; it is never an empty complete list. A corrupt stored workspace row fails the page with the closed diagnostic below.

S7 · Every current record kind and origin reads

The consumer MUST accept kinds organizationProvisioned, stampRenewed, workspaceCreated, machineEnrolled, machineRevoked, machineExpired, allowanceChanged and origins signInProvisioning, automatic, person (organization_change_rows.rs:15–23,59–66). An unknown kind, origin or extra field stays a malformed reply and history shows unavailable; nothing is skipped or recast.

S8 · The page is on the design system

The admin page MUST use the shared page shell, stylesheet, nonce policy and controls. Creating needs a second factor from the last 15 minutes; reading needs none. On secondFactorRequired it shows Better Auth UI's shipped ConfirmSecondFactorStep, then retries the same action once. Cancel or failure sends no retry; a second refusal ends with a visible error. At 400 px everything is usable; names and descriptions render as text; no credential reaches page state.

Keeping it running

S9 · Renewal status, without the statement

The owner MUST see: setting up or confirmed; the confirmed stamp's expiry; a statement awaiting an answer and whether it has expired; the last renewal time; and the unanswered and refused counts with the last outcome. A valid confirmed stamp with a failed renewal shows both facts. Loading status renews and provisions nothing. The reply never contains the signed statement, tokens, proofs or keys.

S10 · Renew on use, including late answers

The statement lasts 120 days and renews when 60 days or less remain, before a Fleet call. At most one statement awaits an answer and every resend uses exactly its bytes. Expiry stops a new send from starting; it MUST NOT discard the answer to a send that already started. That answer settles while the record still holds the same bytes: provisioned confirms; unknown keeps it and counts unanswered; a non-stale refusal clears it and counts refused; stale reads Central's facts and may adopt them even if expired (your R29 change), with no work allowed under expired facts. A late answer for replaced bytes loses its conditional write. A valid stamp allows a call despite renewal failure only if the revision fence also allows it. No timers.

S11 · A trusted key retirement covers every organization

A maintenance operation reachable only through the entry you choose on Decisions (private by default) MUST take explicit old and new key IDs, refuse equal keys and keys with no retained record, check per phase whether the old key is still published, sign every replacement with exactly the new key, and inventory every organization. A crash anywhere is handled by invoking the same phase again. Setting up: blocks retirement until its explicit Try again confirms it; no automatic setup send. Ready with no local confirmed record: the existing seed path reads Central's facts and re-signs, without a setup retry. Every ready organization, idle or not due, is re-signed on the new key and confirmed. Withdrawal is allowed only when every organization's confirmed stamp names the new key, none has a statement awaiting an answer, and source and Central agree. Withdrawal MUST go through the operation's own withdraw step. That step re-checks those conditions and ends the old key's publication. The withdrawal time W it records MUST be a clock reading taken after the unpublishing write has committed, so W is never earlier than the real end of publication. This holds even across a crash between the write and the record. Then, once no Central can still trust the old key, each Central serves an authorized read for every organization. Central keeps a key set in memory for at most 300 seconds, counted from when the response arrives (issuer_key_cache.rs:9,174–203; issuer_key_resolution.rs:49–59 at Central e7b709f6a). Every key fetch is cut off at 10 seconds: natively today (collaboration-central-tokio/src/sign_in_trust.rs:28–31), and on Cloudflare through Lead A's central slice, bounded Cloudflare key fetch (10 s). So a response requested before W expires by W + 310 seconds at the latest. The check MUST NOT pass before W + 310 seconds; this rule is the same on both hosts. Approved rule 6 also requires that each Central “passes a cold restart”: after W + 310 seconds, each Central is restarted (Tokio: a process restart; Cloudflare: a Central deploy). That is your production step. The check then reads every organization. The check can't see the restart itself, so its report records that it ran after your restart step, and V7 proves the cold-start case. A key changed in any other way is outside this guarantee. The report holds IDs, digests and status only.

S12 · Rotation with no pause (your 16 Nov pick: “B is the best way”)

Sign-in MUST keep working throughout a key rotation: no maintenance window, no pause, no new table. Better Auth signs with its newest live key (dist/plugins/jwt/adapter.mjs:9–13), so creating the new key B makes every ordinary signer use it. The old key A stays published until every organization has moved.

The one write that commits to sending a new statement, the sent-slot claim, MUST succeed only if that statement was signed with the current key. A claim signed with A that lands after B became current fails its condition, saves and sends nothing, and the request signs again with B. Writes that record what Central already holds stay unconditional, so an A statement sent before B existed still settles normally and is then re-signed: confirmation, seeding from Central's facts, and recorded tries.

A new organization's setup statement is signed after the organization is created. If it was signed with A, it either is confirmed (and the re-sign loop moves it to B), or Central refuses it after A is withdrawn and the organization stays setting up until Try again signs with B. While an organization is still setting up, prepare reports blocked; invoking it again once setup finishes continues.

The rotation (S11) then re-signs every organization, repeating until every confirmed statement names B, none is awaiting an answer, and sign-in and Central agree. Only then is A withdrawn, followed by the W + 310 second window. Failure before withdrawal keeps A published, so nothing breaks. Central needs no change: it checks each statement against the published key set.

Waiting on your word: approved rule 6 also requires each Central to “pass a cold restart” (on Cloudflare, a deploy). The 310 second window already makes that unnecessary for correctness. It stays in the procedure until you say whether to drop it.

The engine permission

S15 · organization:repairWork, rolled out with one revision

Central's engine (Lead A's deliverable 1, P8) adds repair routes needing organization:repairWork. Sign-in MUST add it to the owner role only (members get none) in the closed permission schema, the native role map and the permission-check map, and accept Central's new closed refusals notFound, notRetired, discardUnsupported, stale, subjectUnreadable (Lead A's P8: a discard on a retired subject whose stored row won't decode; nothing changes, and retry still works). The role map's digest therefore changes. For each organization, one conditional fence write sets the new digest and raises the revision by one, then it is pushed as usual. Until Central acknowledges it, new tokens (revision N+1, above Central's floor N) get AuthorizationSyncRequired, never admitted (request_admission.rs:182–196); after it, old tokens at N get RefreshRequired; sign-in's own issuance refuses while its loaded digest and the fence disagree (person-fleet-issuance.ts:76–78). A token carrying repairWork is inert until the engine's routes exist (request_admission.rs:135–137). Lead A confirmed this is safe from Central's side. Organization stamps carry no policy digest and are not re-signed. Console scope: only this permission and its rollout are in B2. The console (health, the retired list, retry and discard, with UI and CLI) is its own later feature, my sequencing call under your 16 Nov rule.

For reference, Central's admission order after a valid proof and time with a floor present: Deleted → NotPermitted; token revision above the floor → AuthorizationSyncRequired; Stopped → NotPermitted; older revision → RefreshRequired; digest mismatch → RefreshRequired (request_admission.rs:182–196).

Code and proof

S13 · Old code removed

Remove the history-derived directory, the browser ID generator, the three-kind parser, the hand-written page and its custom dialog, and old joint pins. Retarget meaningful refusal and replay tests. No organization registry or workspace store in sign-in.

S14 · Honest core and proof

B2 builds after B1-A merges and uses its injected crypto, clock, IDs and deadline. New code passes the architecture and UUIDv7 checks, uses injected Drizzle and closed types. Tests use controlled clocks and events. Both real local pairings and the real browser cover the final build. Heavy runs on Sunclaw. No new CI gate.

S16 · Machines, effects as data, Hegel

Setup (M1), stamp renewal (M2), key retirement (M3), the page's create operation (M4) and the policy digest roll (M5) MUST each have closed state, event and effect unions, a pure transition with injected facts and time, an inline x satisfies never at each switch, and strict parsing of stored values. Effects are data run by an injected runner only after the state write commits; results return as events. A lost conditional write runs none of its proposed effects. Hegel compares full next state and proposed effects with independent models; separate runner tests check that nothing executes after a lost write. Real conditional-write races run on D1 and better-sqlite3.

The directory contract with Central (agreed with Lead A, 15 Nov)

POST /organization-admin/v1/workspaces on the private link, permission organization:view, reusing Central's current WorkspaceView.

after is null or a lowercase workspace UUIDv7 (exclusive); limit 1–100; all states listed; ascending by ID; next only when more exist. The consumer rejects non-progress, duplicates, disorder, oversize pages and inconsistent cursors.

Anything else in a 503 body is malformed. Other 503s keep today's bare unavailable. The diagnostic shows only after admin authorization, as text.
