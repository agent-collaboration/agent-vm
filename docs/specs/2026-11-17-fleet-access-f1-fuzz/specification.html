Obligations

S1 · Every reachable route has a request family (U1)

Every route in E1 MUST have one classification row. Handler-owned routes are discovered from the real handler source, not only from a hand-written list. Every row that isn't blocked or server-only MUST have exactly one request family. A coverage check MUST fail when:

  • a provider endpoint or a handler-owned route has no classification row;
  • a reachable row has no family;
  • a family names a route that doesn't exist.

The check covers a new handler-owned route as well as a new provider endpoint.

S2 · Generated requests get only documented answers (U1)

Each family MUST generate its route's real request parts:

  • query parameters for GET routes (no GET body);
  • URL-encoded form for the token route;
  • JSON for body routes, including malformed JSON and the wrong content type where the transport allows it;
  • valid, near-valid and boundary values of each part.

Sent through the real host entry on each host, as each caller in its classification row, every answer MUST:

  • be the documented success, or a documented refusal with its generic body;
  • never be 5xx (F1 injects no storage faults);
  • respect the route's disclosure rule: no credential of any class in body or headers (browser session tokens, access, refresh and ID tokens, client secrets, cookie values). The exceptions are each route's authorized success credential outputs, checked against its existing issuance and release contract: the session Set-Cookie on sign-in success, the token route's access_token, and a refresh credential only for the configured fleet CLI under sign-in-response-release.ts's release checks. Legitimate cookie deletion is also allowed. A credential in any error response, or issued outside the route and caller's entitlement, fails. No person's email or ID beyond what the caller is entitled to see. The owner may see their own organization's members and invitees; a member may not; nobody sees another organization's. The existing refusal-field list in credential-free-refusal.ts is the floor.
  • respect the route's permitted refusal effects: a refusal changes only what its row permits. Examples are consuming a passkey-confirm challenge before validation, recording a factor-change intent, clearing a cookie, and expired-session cleanup with its fence bump. Every other stored row stays unchanged, and a replay of a consumed challenge is refused.

S3 · Organization rules hold over any sequence (U2)

Over Hegel-generated sequences, run on each storage engine, each operation MUST go through its real entry, then be read back from storage. The operations are create organization, invite, accept, cancel, remove member, change role, choose current organization, create session, expire session and delete person. They run through the Better Auth provider routes and service operations the product uses; raw store writes would bypass the guards. Two kinds of rule MUST hold after every step, checked every step.

Provider policy:

  • removing an owner is refused (both enforcing guards: organization-role-hooks.ts:35 and Better Auth's last-owner check);
  • a refused operation changes nothing except its permitted effects.

Stored invariants:

  • R-owner: every organization has at least one owner.
  • R-choice: a stored current-organization choice is null or an organization the person belongs to.
  • R-removed: a removed member has no live session scoped to that organization.
  • R-fence, keyed on the (organization, person) pair:
    • role change bumps the affected pair;
    • member removal bumps the pair and marks it inactive;
    • rejoining bumps the retained pair, never resets it;
    • session deletion bumps every retained pair of that person;
    • person cleanup bumps and marks inactive every retained pair;
    • fence changes follow what the operation actually committed, not whether its HTTP answer was success or refusal. An operation that commits no authorized change bumps nothing. A refused read that legitimately cleans up an expired session bumps that person's retained pairs, as the existing expiry cleanup does (expired-session-cleanup-proof.ts:60).
    • a revision never decreases.
  • R-invite: invitation states move only along the documented lifecycle.

S4 · UI properties hold under exploration (U3)

Bombadil campaigns, each on both hosts:

  • the sign-in page signed out;
  • the owner and People pages signed in as an owner;
  • the People URL signed in as a plain member.

Every reachable state MUST satisfy:

  • no uncaught exceptions and no unhandled rejections;
  • no console errors outside an explicit allowlist (each entry with its reason);
  • no navigation failure except the route's documented refusal. On the member's People URL the expected answer is the 403 refusal with its generic content, and any other status ≥400 still fails.
  • the S2 disclosure rule applied to page text and attributes: the owner's People page may show its own organization's emails, the member's page shows none.
  • passkey click-only: in each document, every passkey-challenge request is initiated after a passkey-button click in that document, judged on one ordered witness of both events (see the Program Design). A click with no request is allowed, for example after navigation, cancel or a transport failure.

S5 · Findings are reproducible (U4)

Hegel: a finding records its printed values and seed.

Bombadil: a finding records its private trace plus a replay through the same driver. The replay recreates the host, fixtures, controlled clock and signed-in state, then runs Bombadil's reproduce with the live issuer, the spec and the cookies. It omits the time-limit and stop-on-violation options, which conflict with reproduce. Divergence on replay is reported as divergence.

A fixed finding MUST become an ordinary permanent regression test. Hegel runs derandomized in CI.

S6 · Limits are stated (all)

Results hold for:

  • the local hosts;
  • the software authenticator;
  • controlled providers;
  • the injected clock;
  • sequential operations only, not concurrent interleavings.

Bombadil traces may hold sensitive values; they stay private and are never committed or reported unredacted.
