F1 · Fuzz testing for sign-in: Program Design

How it's built, revision 2, after design review F1–F10. F1 is test code only: no product file changes and no CI gate changes. Pure tests go in the unit lane. Anything that needs a live Miniflare or Node host (the provider inventory, dual-engine storage, host requests) goes in the existing host e2e lane, which CI already requires (ci.yml:43), per Switchboard's AGENTS.md:35. Bombadil runs through an on-demand driver in scripts/.

Coverage (S1)

  • Handler route discovery: handler-route-discovery.unit.test.ts parses the real sign-in-request-handler.ts and sign-in-http-handler.ts source with the TypeScript compiler API. It collects every route literal the handlers branch on (pathname ===, startsWith prefixes, route tables) and fails when a discovered literal or prefix has no classification row. Adding a real handler branch therefore fails coverage with no test list edited. Comparisons against immutable literal constants (for example the imported organizationAdminPagePath, organization-admin-page.ts:4) are resolved through the TypeScript type checker to their literal value. The test fails on any comparison it can't resolve to a literal (computed or unresolvable), so that case can't pass silently. (Clarified 17 Nov on the Implementer's source read.)
  • route-classification.ts is the independent table (E2). Each row: method, path, exposure, request parts, documented answers, disclosure rule, permitted refusal effects. It's written from the specs and tests, not computed from the product allowlist.
  • route-coverage.host.e2e.test.ts builds the live provider inventory, then checks that provider rows plus handler routes equal the classification rows, and that the reachable rows equal the families.
  • The pure unit test checks the table's own consistency: every reachable row has request parts and answers.

Requests (S2)

  • Families: one module per reachable row, exporting { route, callers, generate }. generate draws:
    • the query map for GET routes;
    • the URL-encoded form for the token route;
    • the JSON body for body routes;
    • malformed JSON and the wrong content type where Fetch allows them (no GET body: Fetch rejects it before the host).
    Values come from Hegel generators per field: valid, near-valid, boundary.
  • route-requests.host.e2e.test.ts: per family, caller and SIGN_IN_TEST_HOST, it runs hegel.testAsync (200 cases default, derandomized in CI).
    • Each case: it sets up fresh fixture state for its caller, sends through the harness, then checks the S2 answer, disclosure and effect rules from the row.
    • Disclosure: it scans body and headers for every credential class (reusing credential-free-refusal.ts) and for identities beyond the caller's entitlement.
    • Effects: a stored-row snapshot diff before and after, allowing exactly the row's permitted effects.

Organization sequences (S3)

  • organization-model.ts (pure, unit-tested): people, organizations, memberships with roles, invitations, sessions, and fence pairs keyed on (organization, person) with an active flag. It's written from the domain rules and the fence contract (authorization-fence-mutations.ts:233–354, person-session-store.ts:239).
  • organization-sequences.host.e2e.test.ts: a hegel.stateful.StateMachine with runAsync, on each storage engine via the existing dual-storage host.
    • Each rule performs its operation through the real entry: the Better Auth organization routes or service operations through the harness, as the right caller. It applies the same operation to the model, then reads stored state back through the existing store readers.
    • Refused operations must be refused by both.
    • Invariants are S3's rules plus “model equals stored projection”, all with alwaysCheck: true.
    • Pools hold people, organizations and sessions. 50 steps per case; 100 cases per engine.

Bombadil (S4, S5)

  • Dependency: @antithesishq/bombadil, an exact-pinned dev dependency. The driver maps the existing CHROME_BIN to Bombadil's CHROME variable.
  • Specs: sign-in-signed-out.ts, owner-pages.ts and member-people-denied.ts. Each:
    • keeps noUncaughtExceptions and noUnhandledPromiseRejections;
    • replaces noConsoleErrors with an allowlisted version;
    • replaces noHttpErrorCodes with a navigation-status property that accepts only the route's documented refusal (403 plus generic content for the member campaign);
    • adds the S2 disclosure rule over page text and attributes, per campaign;
    • uses action generators that stay inside the page under test.
  • Passkey click-only witness, ordered: the driver launches Chrome itself (CHROME_BIN, headless, remote debugging on 127.0.0.1) and creates the page itself at about:blank. On that page, through its own CDP session, it arms both observers before any navigation or application script. Bombadil then attaches to that same existing page with bombadil browser test-external --remote-debugger <url>, without --create-target. Without that option Bombadil doesn't navigate; it captures the current state (browser.rs:410–435). So the driver navigates, with Page.navigate to the campaign URL on its own session. It does that only after an event-based readiness barrier: both observers armed, plus Bombadil attached with its first state captured. The Implementer takes Bombadil's exact readiness signal from its source or output stream. If no such signal exists, they report back: no sleep, no timeout guess. So an on-load challenge, and on-load console errors, can't escape either record. The observers:
    • enables Network, recording requestWillBeSent for the challenge path, which marks a request's initiation, not its response;
    • adds, through Page.addScriptToEvaluateOnNewDocument in an isolated world (test-side observer only, no product change), a capture-phase click listener on the passkey button that reports through a Runtime binding.
    Both events arrive on that one connection in order, tagged with the document's loader ID. The property: in each document, every challenge initiation comes after a passkey-button click in that document. Clicks without requests pass.
  • Driver, run mode, per host (Chrome launched by the driver, Bombadil attached with test-external):
    • start the harness;
    • seed the campaign's people, organization and sessions;
    • launch Chrome, create the about:blank page, and arm both observers;
    • start Bombadil attached to that page, wait on the readiness barrier, then navigate the page to <issuer>/<page> from the driver;
    • the Bombadil command is bombadil browser test-external --remote-debugger <url> --time-limit 5m --exit-on-violation --output-path <private> <issuer> <spec>, with one --cookie per cookie and no --create-target. The issuer origin bounds exploration; the driver supplies the navigation;
    • judge passkey click-only only from the ordered witness, with no counting. Record Bombadil's exit code, the witness verdict and event log, the trace path and campaign settings; tear down.
  • Driver, replay mode: recreate the same host, fixtures, controlled clock and signed-in state, then launch Chrome, create and arm the about:blank page exactly as in run mode, and run bombadil browser test-external --remote-debugger <url> --reproduce <trace> against the new issuer, with the same spec and cookies, without --time-limit or --exit-on-violation, and with no --create-target. As in the run, the driver navigates to the campaign URL after the readiness barrier, before Bombadil replays its recorded actions. The ordered witness decides the replay as it decides the run.
