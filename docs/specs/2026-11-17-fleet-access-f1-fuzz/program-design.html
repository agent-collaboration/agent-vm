F1 · Fuzz testing for sign-in: Program Design

How it's built. F1 is test code only. It adds no product behaviour, changes no product file, and adds no CI gate (CI already runs the unit, integration and host suites the Hegel tests join). Everything lives in packages/sign-in-test-support, plus one on-demand driver under scripts/, following the repo's rule that scripts/ holds drivers and tests live under packages.

Hegel: request bodies (S1, S2)

  • fuzz/body-families/: one module per fuzzed endpoint, exporting { method, path, callers, documentedAnswers, generate }. generate is a Hegel generator built with composite and oneOf, drawing:
    • a valid body from the endpoint's real Zod schema's shape (hand-written; Hegel has no Zod adapter);
    • near-valid bodies (one field mutated);
    • boundaries (empty, very long, Unicode, numbers at limits);
    • junk JSON, non-JSON and a wrong content type.
    The body is drawn as its own value, so failures shrink to it.
  • endpoint-coverage.unit.test.ts compares the family list with the reachable rows of installedProviderEndpointInventory, in both directions (S1).
  • endpoint-bodies.host.e2e.test.ts runs hegel.testAsync per family and per caller (signed out, member, owner), for each SIGN_IN_TEST_HOST, with its own testCases count (default 200 per family).
    • Each case: it sends the request through the existing harness entry, then asserts the answer is in documentedAnswers, there's no 5xx, and no forbidden values appear in the body (S2).
    • For a refusal: it compares stored-row snapshots before and after, using the existing recording database helpers.
    • Reset: each case starts from a fresh fixture state, so shrinking and replay are sound; Hegel reruns the body, and the harness gives each case its own state.
  • Settings: derandomize: true in CI, the database disabled in CI (Hegel's own CI default), and failing values printed through tc.note.

Hegel: storage sequences (S3)

  • organization-model.ts is a small independent model: maps of organizations, members with roles, invitations, sessions and fence revisions. It's written from the domain rules, not copied from product code.
  • organization-storage.hegel.integration.test.ts uses hegel.stateful.StateMachine with runAsync.
    • State: the model plus real stores, built through the existing injected Drizzle store factories for each engine: the D1 fixture and better-sqlite3.
    • Rules: one per operation in S3. Each applies the operation to both the model and the real stores; where the domain refuses, both must refuse and the stores must be unchanged.
    • Invariants: each S3 rule, plus “model equals stored projection”, all with alwaysCheck: true, because Hegel otherwise samples invariants between steps.
    • Pools hold created people, organizations and sessions.
    • Budget: 50 steps per case, 200 cases per engine.
  • Limit: Hegel runs steps one at a time, so this proves sequential rules, not concurrent interleavings. The existing fence and concurrency tests keep covering those.

Bombadil: UI exploration (S4)

  • Dependency: @antithesishq/bombadil as an exact-pinned dev dependency of sign-in-test-support. It gives the TypeScript types and a wrapper for the binary on darwin-arm64, linux-x64 and linux-arm64. The version is 0.7.10 (source); the Implementer confirms the npm release exists and is at least two weeks old, or uses the newest that is.
  • Specs (bombadil/specs/): one per campaign: sign-in-signed-out.ts, owner-pages.ts and member-people-denied.ts. They're written in Bombadil's spec runtime, so they can't import Node packages. Each spec:
    • re-exports the defaults except noConsoleErrors, which is replaced by an allowlisted version;
    • adds S4's properties as always(...) formulas over extractors: page text and attributes; performance resource entries for the passkey challenge path before the click; People-row presence;
    • adds action generators that keep exploration inside the page under test.
  • Driver (scripts/bombadil/run-sign-in-ui-fuzz.mts, on demand): for each host it:
    • starts the existing harness, which binds 127.0.0.1 port 0 and exposes its issuer;
    • creates the needed people and sessions through existing fixtures, then passes the session cookie with --cookie;
    • runs bombadil browser test --headless --time-limit 5m --exit-on-violation --output-path <private trace> <issuer>/<page> <spec>, using the existing CHROME_BIN;
    • records the exit code (0 clean, 2 violation, 1 error), the trace path and the reproduce command;
    • tears the harness down.
    Traces stay in a private folder outside git (S6).
  • Limits: Bombadil exposes no seed, its replay can diverge, and its shrinking is experimental. A violation is a finding to reproduce and turn into an ordinary test, not a gate on its own.

Who owns what

All F1 files are new test or support files in sign-in-test-support and scripts/bombadil/, plus one dev dependency. No product file changes. When a fuzz finding needs a product fix, that fix is a normal bug fix in the owning package, with the finding as its regression test.
