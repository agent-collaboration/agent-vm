BG · Getting in: Verification Design

The three things for you

V2 drives all six journeys in real Chrome on both hosts. V3 races Accept and Decline on both databases. V4 runs every journey on staging after a deploy and tries to enter production from staging.

Follows the 30 Oct assumptions (S08: Google only for the real release check; S09: virtual authenticator for passkeys).

Approved SO14–SO16. Nothing has run.

V1 · The page decision (S1)

Hegel family packages/sign-in-test-support/src/core-tests/decide-setup-page.hegel.unit.test.ts, { testCases: 1000, derandomize: true, database: hegel.Database.disabled }, over every combination of facts, destination and time around the deadline (−1, 0, +1 ms). Independent reference table in the test. Invariants: one page; a pending step always wins except the invitation-as-organization-step case; never a setup step for an enrolled person with memberships; at or past the deadline never continue. Wrong builds: route a stale confirmation to the factor step; continue at the deadline; skip the organization step when an invitation destination is for someone else.

V2 · Six journeys, local (S2–S6, S10)

New packages/sign-in-test-support/src/getting-in-journeys.host.e2e.test.ts, both hosts, real Chrome via the local auth harness with provider, Turnstile and Central test peers:

  1. First-time owner: clean database, CLI started first; app enrolment; codes shown until Finish (navigation blocked before); create organization (owner offered create); lands on account; CLI receives its code before the deadline.
  2. Returning person with an old confirmation: goes straight to account or CLI; a protected change asks for a factor.
  3. Command line with a member of two organizations: choose, then continue without an approve screen; bootstrap skipped for the member.
  4. Invited member: Join org as role; Accept → membership; reload → no invitation shown. A second invitee declines. A wrong account sees nothing and is offered sign-out.
  5. Add a passkey on the account page, sign out, sign in with it (CDP virtual authenticator).
  6. Lost factor: recovery code accepted; another code reused → refused.
  7. Deadline passed during a pending step: account page with the expired notice; the CLI gets nothing.
  8. At 400 px dark, keyboard only: one heading, “Switchboard”, no overflow.

Kept: the real-CLI continuation test, retargeted; the short-name test retargeted to R60 (stop following once edited). Wrong builds: leave /owner-ready; extend the deadline on a prompt; show a used invitation.

V3 · Decline against Accept (S6)

Both databases, barriers around the real native Accept claim and our Decline write: Decline first → Accept loses its claim; Accept first → Decline answers already-answered and the membership stands; Decline of an expired invitation → expired; by a non-recipient → not-found with no detail. Rows read back each time. Wrong build: Decline without the status = 'pending' condition overwrites an accepted invitation.

V4 · Staging and production (S7–S9)

  • After a staging deploy: reset, identities, all six journeys from signed-in test identities, TOTP from the shown key and server Date; staging rows read with Wrangler's remote D1 for the oracle.
  • Production: /__staging/test-identity → 404; a staging session cookie → signed out; the deployed bundle contains no testUtils string; the configured owner isn't .invalid.
  • Release: one real Google sign-in on staging by the dedicated test account, recorded with the git SHA and both Workers' version IDs.

Deadlines, factor windows and expiry are proven locally on controlled time (V2), not on staging.

V5 · Machines and gates (S11)

Hegel families for M2 (decline outcomes), M3 (continuation) and M4 (identity lifecycle: reset only removes the test domain). One added literal per union fails pnpm typecheck at its satisfies never. Gates on Plan.
