V1 · The page decision (S1)

Hegel family packages/sign-in-test-support/src/core-tests/decide-setup-page.hegel.unit.test.ts, { testCases: 1000, derandomize: true, database: hegel.Database.disabled }, over every combination of facts, destination and time around the deadline (−1, 0, +1 ms). Independent reference table in the test. Invariants: one page; a pending step always wins except the invitation-as-organization-step case; never a setup step for an enrolled person with memberships; at or past the deadline never continue. Wrong builds: route a stale confirmation to the factor step; continue at the deadline; skip the organization step when an invitation destination is for someone else.

V2 · Six journeys, local (S2–S6, S10)

New packages/sign-in-test-support/src/getting-in-journeys.host.e2e.test.ts, both hosts, real Chrome via the local auth harness with provider, Turnstile and Central test peers:

  1. First-time owner: clean database, CLI started first; QR and text key match; a wrong code then the right one on the same setup; codes shown until Finish (navigation blocked before); reload in a second tab: codes not shown again, the new-codes message shown; create organization (owner offered create, plus a pending invitation offered too); lands on account; CLI receives its code before the deadline.
  2. Returning person with an old confirmation: goes straight to account or CLI; a protected CLI change gets secondFactorRequired, the CLI opens /account/confirm, the person confirms, and the page continues the CLI's authorization. The CLI's new credential names the same session S0, and its single retry succeeds with the same operation identity.
    • Browser signed out: start with a real CLI credential on S0, and clear the browser's cookie without touching the CLI's stored credential. /account/confirm shows sign-in, which creates S1. The person confirms S1, and the page continues the authorization. The CLI's new credential names S1, its stored credential is replaced, and the retry succeeds.
    • S0 ended on the server: the old credential's refresh stays refused; the same confirm-and-authorize path gives a credential on S1, and the retry succeeds.
    • Another person in the browser: the CLI keeps its old credential, makes no retry, and reports “Signed in as a different person; nothing was changed”. Central saw one refused attempt only.
    • Never enrolled: a person who never enrolled a factor, opening /account/confirm, lands on the authenticator step.
    • No caller anywhere opens /owner-ready (it 404s).
    Wrong builds:
    • Today's confirm-then-refresh after confirming S1: the retry gets secondFactorRequired again, because of the session mismatch.
    • No person check: the other-person case runs the command as them.
    • /account/confirm without the signed-out case: the step-up dead-ends.
  3. Command line with a member of two organizations: choose, then continue without an approve screen; bootstrap skipped for the member.
  4. Invited member: Join org as role; Accept → membership; reload → no invitation shown. A second invitee declines. With a CLI carried inside the invitation destination, Accept (and separately Decline) continues the CLI before its deadline, and at the deadline lands on account with the expired notice. A wrong account, a used, an expired and a canceled invitation each show their message and action, with no organization or email shown. A person with two pending invitations and no destination is offered both.
  5. A sole member whose current choice was cleared through native set-active resumes a CLI: the page input says select-first; the script calls set-active before bootstrap or authorize; the CLI token names that membership, before the original deadline. Holding the set-active reply past the deadline means authorize is never reached. Wrong build: a continuation input without the selection field (the member navigates unselected and the token is refused).
  6. Signed-in visits to organization admin with no membership, and with memberships but no valid current choice, reach /setup and then the pending step or the chooser; never /owner-ready or the confirmation page.
  7. Add a passkey on the account page, sign out, sign in with it (CDP virtual authenticator).
  8. Lost factor: recovery code accepted; another code reused → refused.
  9. Deadline passed during a pending step: account page with the expired notice; the CLI gets nothing.
  10. At 400 px dark, keyboard only: one heading, “Switchboard”, no overflow.

Kept: the real-CLI continuation test, retargeted; the short-name test retargeted to R60 (stop following once edited). Wrong builds: leave /owner-ready; extend the deadline on a prompt; show a used invitation.

V3 · Decline against Accept (S6)

Both databases, barriers around the real native Accept claim and our Decline write: Decline first → Accept loses its claim; Accept first → Decline answers already-answered and the membership stands; Decline of an expired invitation → expired; by a non-recipient → not-found with no detail. Rows read back each time. Wrong build: Decline without the status = 'pending' condition overwrites an accepted invitation.

V4 · Staging and production (S7–S9)

  • After a staging deploy: reset (its report lists the test organizations; sign-in rows gone; Central residue listed as open), identities, all six journeys from signed-in test identities, TOTP from the shown key and server Date; staging rows read with Wrangler's remote D1 for the oracle.
  • Staging refusals, each with unchanged rows and nothing revealed: Chrome reports no CSP violation and each page carries the policy; a protected change without a recent factor is refused (R53); a member's owner-only action is refused (R13); a setup page reached while a step is pending shows the step (R57).
  • Production: /__staging/test-identity → 404; a staging session cookie → signed out; the configured owner isn't .invalid; the production build's metafile, bound to the deployed version, contains no module under the test-utils plugin, the staging folder or test support. Wrong build: include a renamed test-utils plugin; the metafile check fails.
  • Release: one real Google sign-in on staging with its real Turnstile check, by the dedicated test account, recorded with the git SHA, both Workers' version IDs and the Turnstile outcome.

Deadlines, factor windows and expiry are proven locally on controlled time (V2), not on staging.
