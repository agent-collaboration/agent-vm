Rules

S1 · One decision picks the page

From G1, G6. Every request to /sign-in, /setup, /invitation/:id or /account MUST get the page chosen by one pure decideSetupPage(facts, destination, now). Order: not signed in → sign-in; second factor never enrolled → authenticator step; no organization → organization step (everyone offered their pending invitations, the configured owner also offered create, otherwise told to ask); a live invitation destination for the person's verified email → invitation page; an invitation destination that isn't theirs, or is used, expired, canceled or unknown → a page explaining that without naming any organization or email, with one action; command line waiting with several memberships and no current organization → choose; with one membership and no current organization, the page selects it (by Better Auth's set-active POST) and continues; command line waiting, ready, before its deadline → continue; otherwise account. A pending step wins over every destination, except that when only the organization step is pending and the destination is an invitation for that person, the invitation page is the organization step. Readiness depends on enrolment, never on how recent a confirmation is; a stale confirmation only matters for protected changes. No GET writes anything.

S2 · Recovery codes stay until Finish

From G2, R59. The authenticator page shows the QR code and the same key as text; a wrong code keeps the same setup. After a correct first app code the page shows the recovery codes, and nothing navigates away until Finish. A reload or second tab is a fresh decision: the factor is set up, the codes are never shown again, and the page says new recovery codes need confirming with two factors.

S2a · Confirming again for a change

From G6, R53. When a protected change needs a recent second factor (from the CLI or a page), the person confirms at /account/confirm with an app or recovery code, then the change is retried once. A confirmation counts only for the browser session it was made in. So for the CLI, the confirmation page MUST continue to a CLI authorization, and the CLI MUST retry with the new credential from the confirmed session. If the browser had to sign in again, that session is a new one. The retry MUST be refused when that credential belongs to a different person. The CLI's step-up link and the factor forms, which pointed at /owner-ready, point here. The organization admin page's redirect for a visitor with no matching current membership, which also pointed there, goes to /setup instead.

S3 · Back to the command line, within its deadline

From G3. The CLI adds deadline (its own wait end, epoch milliseconds) to the URL it opens. It is fixed once, carried through every step and redirect, and never extended. Before the deadline, continue goes to authorize with skip-consent (owner first runs bootstrap; a member skips it) and the CLI receives its code. At or past the deadline the person lands on the account page with “Your command-line sign-in expired; run it again”. The continuation script checks the deadline again immediately before navigating.

S4 · The account page

From G5. Shows your second factors (manage, add a passkey), your organizations with one to choose (B1-C's surface), and a clear “done”. No admin actions.

S5 · The invitation page

From G4. Reads the invitation through Better Auth's get-invitation, which checks the signed-in recipient first; a wrong account learns nothing and is offered “sign out and use another account”. Shows “Join organization as role” with Accept and Decline. After either, a waiting command line carried inside the invitation destination becomes the destination, with its original deadline, and the page goes through /setup, so a used invitation is never shown again.

S6 · Decline is guarded

From G4. Our Decline endpoint MUST change the invitation only while it is pending and unexpired, for the signed-in recipient. If an Accept landed first, Decline answers “already answered”. Better Auth's own reject-invitation stays closed.

S7 · Staging without you

From G8. A separate staging build (same core factory and options plus Better Auth's testUtils) serves two routes behind a staging secret: create-or-find a test identity and sign it in; reset test-domain users and what they own (sessions, memberships, organizations owned only by test users, and their Central side). After each staging deploy the run resets, creates identities and drives every journey from a signed-in test identity, and checks the refusals R65 names: pages under their security policy, a protected change without a recent factor (R53), an action without permission (R13), and a page reached while a step is pending (R57), each changing and revealing nothing. The provider sign-in step itself is not part of these runs. Removing test organizations' Central stores waits on a Central operation that doesn't exist yet (Lead A, asked); until then they remain as unreferenced residue.

S8 · Production refuses the test path

From G8. Production MUST answer /__staging/* as unknown; refuse a cookie minted on staging; contain no test-utils plugin, staging module or local stand-in in its build (shown by module path in the build's own record, for the deployed version); and its configured owner is not under the test domain. Staging and production have separate databases and auth secrets.

S9 · One real sign-in per release

From G9. Once per release, one real Google sign-in on staging, including its real Turnstile check, by the dedicated test account or by you with a Verifier watching, recorded with the artifact identity.

S10 · Look and cutover

From G10. “Switchboard” on every page, one top heading, the shared dark design, 400 px and keyboard. /owner-ready and its Continue are removed with no redirect.

S11 · Machines and Hegel

The page decision (M1), Decline (M2), the continuation (M3) and a test identity (M4) MUST be closed unions with pure transitions, inline x satisfies never, effects as data where they call out, and Hegel families; Decline's conditional write races Accept on both databases.
