Confirming a factor again, after /owner-ready goes

Three live callers point at /owner-ready, with two different purposes. Organization recovery: the organization admin page redirects a signed-in visitor with no membership matching the session's current choice (sign-in-http-handler.ts:152–156); that redirect moves to /setup, so the page decision shows the pending step, the chooser or the account page. Confirmation: the Fleet CLI opens it when Central asks for a recent second factor (sign-in-owner-cli/src/fleet/fleet-cli-commands.ts:154–155), and the factor forms return to it (pages/factor-page.tsx:27–28 ownerReadyLocation, used by factor-enrollment-page.ts:57). Those two move to /account/confirm. Its handler reads the same facts as M1 and handles four cases:

  • Signed out (common, since the CLI's person token outlives the browser session): the sign-in page, returning to /account/confirm with its parameters after sign-in.
  • Unavailable: 503.
  • Second factor never enrolled: a redirect to /setup, because there is nothing to confirm yet.
  • Enrolled: a page with the app-code and recovery-code forms (the existing factor controls). On success it continues the authorize destination it carries, as S3 says.

Which session the confirmation lands on. A confirmation is stamped on the browser's current session only (second-factor-provider-plugin.ts:158–169, second-factor-store.ts:70–89). The CLI's credential is bound to the session it was issued from, and refresh keeps that session (fleet-credential.ts:132–150; @better-auth/oauth-provider 1.7.11 refresh issues with sessionId: refreshToken.sessionId). So if the browser had to sign in again (new session S1), confirming S1 does nothing for a CLI credential on S0. Today's sendConfirmingOnce (fleet-admin-command.ts:129–141) confirms, refreshes, and retries; in that case its retry would get secondFactorRequired again.

The CLI's step-up therefore uses its existing login flow, not refresh.

  1. On secondFactorRequired, the CLI starts the same loopback authorization as signInFleetCli (fleet-credential.ts:98–125), with PKCE, state and a deadline. It opens /account/confirm carrying that authorize destination.
  2. The page signs the person in if needed, confirms whichever browser session is current, then continues to authorize with skip-consent. The code is bound to that same, now-confirmed session.
  3. The CLI exchanges the code, as at login.
  4. The new credential's person must equal the old credential's person. If someone else is signed in to the browser, the CLI discards the new credential, keeps the old one, and stops with “Signed in as a different person; nothing was changed”.
  5. Otherwise it replaces the stored credential and retries the operation once, with the same operation identity.

This works the same whether the browser was on S0 (the new credential is on confirmed S0) or signed in again (the new credential is on confirmed S1). No confirmation is copied between sessions and Better Auth is unchanged. In fleet-admin-command.ts, sendConfirmingOnce's confirm-refresh pair becomes this confirm-and-authorize step, and confirmSecondFactor becomes the loopback authorization. At or past the deadline, the page lands on the account page with the expired notice, and the CLI reports the step-up as expired.

ownerReadyLocation becomes confirmLocation; its tests and people-organization-page.host.e2e.test.ts:170–201 (expired confirmation → confirm again) are retargeted, not dropped.

Each row is a case in a switch on the facts' kind with an inline x satisfies never. Readiness reads enrolment only; a stale confirmation never routes to a setup step. The handler reads facts once per request and renders the chosen page; GET never writes. setup-facts.ts reads the pending invitations for the verified email and the destination invitation by ID through injected Drizzle (not native get-invitation, which refuses non-pending rows before saying why, crud-invites.mjs:502–509); a failed read makes the facts unavailable, never “ask for an invitation”.

After Accept or Decline, the invitation controller promotes the destination's then (if any) to the top-level destination and navigates to /setup with it, keeping its original deadline; the answered invitation is gone from the URL, so it is never shown again, and M1 decides the next page from the remaining destination.

Authenticator step and recovery codes

The step page uses Better Auth's two-factor/enable and verify-totp. It shows the QR code and the same key as text (R59). A wrong code keeps the same setup and lets the person try again. After a correct code, the island holds the recovery codes from enable's reply in memory only and shows them with a Finish button; navigation away is disabled until Finish, which then GETs /setup. A reload or a second tab re-decides: the factor is enrolled, the codes are not shown again, and the next page says “To get new recovery codes, confirm with two factors on your account page” (R59).

M2 · Decline

States pending | accepted | rejected | canceled as Better Auth stores them; our only transition is pending → rejected. Endpoint (in invitation-decline-plugin.ts, beside passkey-confirmation-plugin.ts): require a verified current session whose email equals the invitation's; then one Drizzle update status = 'rejected' WHERE id = ? AND status = 'pending' AND expiresAt > now. One row changed → declined; zero rows → re-read: accepted or rejected → already-answered; expired → expired; not found or not the recipient → not-found (no detail). An intent record is written before and an outcome after, like the other people changes.

Staging

  • Entrypoint. sign-in-host-cloudflare/src/staging/index.ts builds the same configuration with the same core factory and options, plus Better Auth's testUtils plugin. Its own Worker, D1 and auth secret.
  • Routes, each requiring the staging secret (from agent-vault): POST /__staging/test-identity creates or finds a user under the .invalid test domain with verified email and signs it in through testUtils, returning its cookie; POST /__staging/reset first lists the organizations owned only by test users and returns their IDs in its report, then deletes test-domain users, their sessions and memberships, and those organizations' sign-in rows. Central cleanup is an open dependency: Central has no operation that removes an organization's store (organization_signin_http.rs:25–58), so their Central stores remain as unreferenced residue until Lead A's post-engine slice adds RemoveOrganizationStores (Lead A, push 01a1e1aa-6656): a private-link operation with a request ID, 1–50 organization IDs in, one result per ID out (removed | notFound | refused { reason } | unavailable, no all-or-nothing), and refused before any read unless Central's own deployment is configured as staging. The reset then passes its returned IDs and retries the unavailable ones. Lead A will show you that slice before it's built, since it deletes stores. The real test account outside the test domain keeps its factor.
  • M4 · test identity: absent → created → signed-in → reset; reset only matches the test domain.
  • Run. A script scripts/verify-auth/staging-journeys.mts resets, creates identities, drives the six journeys in headless Chrome from signed-in identities, and computes TOTP codes from the displayed key and the server's Date header.
  • Production checks in the same script against production: /__staging/* → 404; a staging cookie → refused; configured owner not under the test domain; and module exclusion from the build's own record: the production Worker build writes its bundler metafile, and the check requires it to contain no module under better-auth/dist/plugins/test-utils/, sign-in-host-cloudflare/src/staging/ or sign-in-test-support/, bound to the deployed Worker version ID. Module paths don't change when a symbol is renamed or minified.
