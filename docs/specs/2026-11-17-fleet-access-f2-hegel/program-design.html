F2 · Hegel on critical systems: Program Design

F2 is test code only: no product file changes, no new CI gate, no new dependency (@hegeldev/hegel 0.4.10 is already in the repo). Each test sits beside the package it tests, in the lane its boundary needs, per Switchboard's AGENTS.md:35:

  • pure functions in unit;
  • SQLite and process-local stores in integration;
  • Durable Object or live-host stores in the host lane.

Shape of each test

  • Generators are built from the target's real Zod input schema, hand-written (Hegel has no Zod adapter), drawing valid, near-valid and boundary values. Security targets add adversarial strings: .., encoded separators, Unicode lookalikes, case and port variants, overlong values.
  • Oracles are independent: P5's operation/group/scope/support model built from literal catalog cases, P2's per-entry decision table, P3's authored-policy table, round trips and frozen vectors for P1 and P8, the code's documented rules for P4 and P9, and small state models for M1–M5. Never the function under test.
  • State machines use hegel.stateful.StateMachine with runAsync. Invariants are alwaysCheck: true (Hegel otherwise samples between steps). Clocks are injected, and stores come from the package's own injected Drizzle/store factories. 50 steps per case.
  • Settings: 500 cases per pure property, 100 per state machine except M4 at 25 (Lead call, 17 Nov: see Decisions), derandomize and the database disabled in CI. Failures print values through tc.note.
  • A finding: the Implementer stops and reports it to the Lead with the minimal case. A product fix is a separate bug fix with that case as its regression test.
