Sign-in

  • Start from #11. Merge item2/b3a-device-grant forward onto current main (after B1-A, B1-C, B2, B2X), keeping its tests; bring #14's verification with it.
  • Approval rule in the core: machine-login/device-approval-rule.ts, a pure function over the code record, the approver's live permission, factor recency and now, returning approve | deny | refuse(reason); both endpoints call it. Deny now requires a recent second factor, like Approve.
  • The page keeps the chosen action through step-up. On #11, ConfirmSecondFactorStep.onConfirmed always calls decide('approve') (pages/islands/device-approval-island.tsx:144–172 on d60372cc). The island's state gains pendingDecision: 'approve' | 'deny', set when the person clicks, and onConfirmed retries exactly that decision once.
  • Workspace picker: the approval page calls B2's ListWorkspaces (permission organization:view, which owners hold) and sends the chosen IDs in DecideDeviceLogin.
  • Revoke: a “Machines” section on B2's admin page lists enrollments (from the machine lookup) with Revoke, Allow and Withdraw; each forwards the command with the person token and a recent factor; on revoke, the sign-in service disables that enrollment's client.
  • Carrying the connection is host-owned, because today's core link (central-link/central-transport.ts:1–4) is fetch-only. Public path GET /api/fleet/link/{organization} with Upgrade: websocket and the bearer machine token; Central path GET /v1/organizations/{organization}/link (4a's door, workspace_link.rs:50–54); the token header is passed unchanged and only Central verifies it.
    • Cloudflare: the Worker matches the path and returns env.CENTRAL.fetch(rewrittenRequest); Workers carry a 101 response with its WebSocket through a service binding, and Central's Worker entry (workspace_link_entry.rs:6–54) answers it.
    • Node: sign-in-http-listener.ts (today request-only, :76–107) adds an upgrade listener for that path. It opens a Unix-socket connection to Central (the path the existing central-unix-transport.ts uses), writes the rewritten upgrade request with the unchanged Authorization header, and reads Central's status line. On 101 it writes Central's 101 headers to the client, writes any bytes already read past the headers in each direction, and pipes the two sockets both ways until either closes. On any other status it writes that status and body to the client and closes both. The listener keeps a set of upgraded socket pairs and destroys them on shutdown.

Allowances: the machine_allowances table (your 9 Nov decision)

What changes. Today Central (#281) keeps a machine's current workspaces as a JSON list in machines.allowed_workspaces. B3 moves that truth into its own table, one row per machine and workspace, as you approved. Behaviour stays exactly as today: an approval adds: it makes the picked workspaces' rows active and leaves every other active row alone (device_login_decision.rs:75, “Approval adds allowances; it does not withdraw existing ones”, B3/R39). Allow and Withdraw change one row. Revoke withdraws every row, so an approval after a revoke starts from nothing; all in the same transaction as today, each with its change record. machine_approvals.allowed_workspaces stays as that approval's record of what was approved then. It's history, never read for admission.

SQL. These are edits to Central's 0001_workspace_requests.sql in place, per the owner's 17 Nov choice for Central migrations. They land with Lead A's 0001/0002 fixes in one change and one staging reset. Names follow Central's current tables; timestamps are TEXT like the rest of machines.

-- machines: allowed_workspaces removed; former_installation_id added (the re-key, set once)
CREATE TABLE machines (machine_id TEXT PRIMARY KEY, installation_id TEXT NOT NULL,
  former_installation_id TEXT UNIQUE, label TEXT NOT NULL, state TEXT NOT NULL,
  enrollment_generation INTEGER NOT NULL DEFAULT 0, created_at TEXT NOT NULL, updated_at TEXT NOT NULL);

-- new: which workspaces each machine may serve
CREATE TABLE machine_allowances (
  allowance_id TEXT PRIMARY KEY,                         -- UUIDv7 from the injected ID source
  machine_id   TEXT NOT NULL REFERENCES machines(machine_id),
  workspace_id TEXT NOT NULL,
  state        TEXT NOT NULL,                            -- active | withdrawn
  created_at   TEXT NOT NULL,
  updated_at   TEXT NOT NULL,
  UNIQUE (machine_id, workspace_id));

Admission read (workspace_admission.rs:16, Lead A's 4a). The query drops m.allowed_workspaces and instead reads this one workspace's row:

SELECT m.machine_id, m.state, c.expires_at, w.state AS workspace_state,
       (SELECT a.state FROM machine_allowances a
         WHERE a.machine_id = m.machine_id AND a.workspace_id = ?1) AS allowance_state
FROM machines m JOIN machine_credentials c ON c.machine_id = m.machine_id
LEFT JOIN workspaces w ON w.workspace_id = ?1
WHERE m.machine_id = ?2 AND c.token_hash = ?3

With a workspace: allowance_state = 'active' admits; 'withdrawn' or NULL refuses with WorkspaceNotAllowed; any other value is a corrupt row. Without a workspace, the allowance isn't read. Refusals are unchanged. The JSON decode at :33–36 goes away.

Router host

  • FleetLogin operator request with public inputs only; the device flow; polling with an injected wait.
  • M3 · Router login: requesting → waiting → redeemed → publishing (confirm credential, replace fleet_login, retire older) → one of four endings, kept distinct and bound to the existing F11 contract (codex-router-host/src/fleet_machine_login/login_contract.rs:97–122,152–161, login_publication.rs:20–44): loggedIn; refused { reason }; outcomeUnknown when a publication or retirement step can't be confirmed (the terminal frame says so, with public context); and, only in the attached CLI, “login interrupted, run it again” when the stream ends with no terminal frame (the Host died). Never resume an old code.
  • M4 · Renewal: connected → refreshing (before grant_expires_at) → renewing (RenewMachineToken) → connected; refused once → refreshing; refused twice or enrollmentNotActive → needs-new-code. Pinned 17 Nov to Lead A's seam (codex-router d23724feb):
    • Interface. B3's Router host implements MachineTokenSource (crates/collaboration-runtime/src/central_link_driver/link_transport.rs:50): availability() → TokenAvailability, which is Ready, RefreshPending or NeedsNewCode (:37); a cancel-safe changed() backed by a watch it owns; and report_renewal(&TokenRenewalResult). The link driver sends RenewMachineToken and passes every answer back.
    • Refusal handling. M4's switch is exhaustive over TokenRenewalRefusal (crates/central-link-protocol/src/link_renewal.rs:65), my call:
      • Renewed: back to connected.
      • TokenRejected and DifferentEnrollment: refresh once more. A second refusal leads to NeedsNewCode.
      • EnrollmentNotActive and DifferentMachine: straight to NeedsNewCode. An identity mismatch is never auto-healed.
      • CentralUnavailable: transient. It does not count toward NeedsNewCode; the token stays Ready and the next connection retries, so a Central outage never asks a person for a new code.
  • Secret store: the RefreshCredentialStore and DataKeySource traits; EncryptedEnvelopeStore, MemoryOnlyStore, MacKeychain; the composition root injects [MacKeychain] on macOS, [] elsewhere; today's cfg-selected access is removed. Classification generalizes the existing read-only classifier (codex-router-secret-store/src/classified_store_open.rs:54–73,91–131) to the injected list: it creates and overwrites nothing; only BackendAbsent moves to the next source; memory-only is chosen only when every source is absent and the store holds no encrypted, legacy or temporary credential data; existing data with no usable key is an error. Creating a fresh data key is a separate, explicit startup step.
  • Re-key and switch: send the former service ID with the login; on a new enrollment replacing an active one, run R10/R10a and call the link client's re-enrolled entry.
