1 · Approval replay

Main today: login/device_login_decision.rs:25–39, rule "N03". Once a request_id has an approval, every repeat for the same machine returns the first snapshot, and changed labels or workspaces are silently ignored. A different machine gets NotPermitted. The tests are device_login_decision_test.rs:153–204 and both host machine_login/approval.rs:8,48–81,112.

Meaning (Sign-in Lead proposal). The comparison is typed field equality, not raw bytes. It compares the decoded DecideDeviceLogin with the retained login_machine_approvals row on the fields an approval binds:

  • machine_id;
  • label;
  • allowed_workspaces, compared as a set;
  • code_expires_at;
  • the approver (approved_by_person_id).

The approver's factor time is not bound: it is admission evidence, not part of what was approved. Every bound field is already a column (0001:6–24), so no new column is needed, and existing rows carry over unchanged. JSON spelling cannot change the result.

Precedence:

  1. The organization mismatch and the SD8 freshness check, unchanged; both give NotPermitted.
  2. If an approval exists for this request_id:
    • a different machine gives NotPermitted, unchanged;
    • bound fields that are equal return the first Approved answer, with no write;
    • otherwise, a new DeviceLoginRefusal::RequestConflict {}, with no write.
  3. The new-approval path, unchanged.

After a crash or replay: the unique index on request_id (0001:24) and the guarded batch (machine_login_plans.rs:98–131) keep it to one approval and one effect. A replay after activation or reopen reads the same row.

2 · The global machine claim: options for the owner

The owner ruled "no it may not, but how we ensure this / only by the router righ?" and then "a machien cannot move to another organization". The claim is option A, simplified: a permanent claim in sign-in, with no transfer and no change to central. The design is on Machine claim. The options below are kept as the record of what was asked.

Each organization's central store is its own Durable Object, and machine_login_plans.rs:23–44 reads only self.organization. So no store sees another organization's machines. "One active claim per machine ID" needs a shared authority, which is a new storage boundary, and the owner decides storage. No option is chosen. In this section "option A" means the claim option below, not the 9 Nov SQL option A.

One fact frames them: machineId is the Router install's own UUIDv7, self-asserted (0001:3–5). A shared claim serialises claims made under the same ID. It says nothing about physical identity.

What option A or B must guarantee

The release protocol is designed only after the owner picks A or B. If he picks C or D, it isn't needed. Whichever option is picked has to meet these requirements, which came out of review:

  1. Ownership: the claim belongs to (machineId → organizationId), not to one enrollment. Inside the owning organization, replacing enrollment E1 with a pending E2 never drops it.
  2. An identity before forwarding: the authority mints a claim_id that travels with the approval and is stored on it. Central won't commit or activate an approval whose claim_id isn't current.
  3. The release is ordered against commits. Expiry alone isn't a fence, because central samples decision time before its guarded write. The "no live enrollment" observation must be taken under the owning organization's turn. It must be bound to that store's latest approval deadline and to a version that every approval or grant increments. The authority releases only if that version still matches. An approval made after the observation therefore blocks the release.
  4. Abandoned approvals: an Approved row whose code expired, and which never got a first-grant attempt, counts as ended for release purposes. Main writes Lapsed only when a first grant is attempted (login/machine_token_decision.rs:76–92), so the observation must treat Approved with now > code_expires_at as ended.
  5. Failure: an unreachable organization store keeps the claim, and the second organization is told to retry.
  6. Scope: one sign-in deployment (one issuer).

3 · Idle expiry: mint (carried) and live (new)

Mint, carried as is: login/machine_token_decision.rs:42–43 checks 30 days (decision_support.rs:10). At :177–224, it ends the enrollment as Expired, bumps the machine's generation, sets the machine to Revoked, clears its allowances, and writes MachineExpired plus one allowance record per row. The first answer is MachineTokenRefusal::IdleExpired {}. A replay then sees Expired and answers EnrollmentNotActive {}, with no new write (:57–65). The generation fence is observed through a pending older approval, which can no longer activate. An attachment carries enrollment and client IDs plus a deadline, not a generation.

Live, which changes main (Sign-in Lead proposal). Today machine_connection.rs:103–152 (validate_live) ignores last_grant_at. Under normal issuance this can't matter: every grant resets last_grant_at and lasts only 600 s (machine_token.rs:170–179), so token expiry always comes before idle expiry. The live check is defence in depth, for an attachment whose stored grant is older than 30 days while its token is still valid. That happens only with hand-made or clock-skewed state.

  • Decision: fleet-machine-login exposes the pure idle_expired(last_grant_at, now) → bool.
  • Where it runs: only at the under-turn re-read in core (machine_connection_admission.rs, the re-read after verification). Both hosts reach it, for connect and for renewal. The hosts' pre-restore before verification (workspace_machine_link.rs:491–518, workspace_link.rs:435–454) stays read-only and never writes.
  • The write and the close order: under the turn, core commits the existing idle_expiry batch and captures the expired enrollment ID. It returns the refusal together with an InvalidateEnrollment(enrollment_id) effect.
    • Renewal: the host sends the typed refusal on the triggering socket, then closes only the sockets whose attachment names that expired enrollment. A replacement enrollment that registered after the commit keeps its socket. If the send fails, the scoped close still runs.
    • Connect: the refusal comes before upgrade, so there's no socket. The host returns its existing HTTP refusal for EnrollmentNotActive, then runs the same scoped close for any older sockets of that enrollment.
    The existing machine-wide close is not reused for idle expiry. The expiry takes effect at the commit, so any socket of the expired enrollment is refused on its next request by validate_live even before it closes.
  • Typed results:
    • connect: the existing MachineConnectionRefusal::EnrollmentNotActive {};
    • renewal: the existing MachineTokenRenewalRefusal::EnrollmentNotActive (machine_connection_admission.rs:236–245). The Mac treats that as "stop, get a new code" (B3 M4).
    No new variants and no wire change.
  • When the store is unavailable: nothing is written, and the answer stays the existing retryable one.

Enrollment state machine (StoredEnrollmentState):

  • Approved → Enrolled at first grant.
  • Approved → Lapsed: the pending row ends, and the generation is not bumped.
  • Enrolled → Revoked{reason}, and Enrolled → Expired: both bump the generation.
  • Enrolled → Revoked{Superseded} on a re-login.

Every ended state is terminal.

4 · Allowances: the table

Owner decision, 20 Nov: "we want allwoance talbes". Earlier, 9 Nov, B3 SQL review: "Approve option A". The DDL below is a Sign-in Lead proposal for implementing that decision.

CREATE TABLE login_machine_allowances (
    allowance_id   TEXT PRIMARY KEY,   -- UUIDv7 from the injected ID source
    machine_id     TEXT NOT NULL REFERENCES login_machines(machine_id),
    workspace_id   TEXT NOT NULL,
    state          TEXT NOT NULL,      -- Rust AllowanceState { Active, Withdrawn } (organization_commands.rs:115)
    changed_by     TEXT NOT NULL,      -- Rust enum: Approval{approval_id} | Person{person_id} | Automatic | Backfill
    created_at     TEXT NOT NULL,
    updated_at     TEXT NOT NULL
);
CREATE UNIQUE INDEX login_machine_allowances_pair ON login_machine_allowances(machine_id, workspace_id);

There are no CHECK constraints. Kinds are Rust enums. changed_by replaces a required enrollment ID: an admin allow can happen while no enrollment is active, and the backfill has no person.

Store disposition: per the owner's workspace-storage record, central starts fresh at the identity cutover. So the table is created empty and no backfill is needed. Only if a populated post-cutover store must be migrated does this conditional backfill apply: each JSON entry in login_machines.allowed_workspaces becomes an Active row with changed_by = Backfill, then the column is dropped. The admitting S5 decision states which case applies. login_machine_approvals.allowed_workspaces stays as the immutable record of what each approval asked for.

State machine: an allowance moves Active ⇄ Withdrawn. It becomes Active only through approval or Allow.

5 · Permissions and factor (carried as is)

  • The issuer: Switchboard organization-access-control.ts:5–21 grants owner machine: enroll · revoke · setTokenLifetime and workspaceAdmin: allowMachine · withdrawMachine · removeSession.
  • Central signed admin: person_request/request_admission.rs:134–145 checks the route's permission. Then every state-changing signed admin route requires a fresh factor.
  • Revoke: answers Refused{FactorNotRecent} on the wire (organization_admin_contract.rs, MachineEnrollmentRevocationRefusal).
  • Device approval: login/device_login_decision.rs:50–60 requires a fresh factor when organization_has_enrollment. That is true once any approval row exists, including pending, lapsed or ended ones (machine_login_reads.rs:27–65). The answer is DeviceLoginRefusal::SecondFactorRequired { within_seconds }.
  • OD18 meaning (the owner's decision, "the first machine is exempt"; applied as my call on 18 Nov). Only the organization's very first approval is exempt. Main's stricter predicate is the meaning: it stops a run of factor-free pending approvals. The B3 spec S1 wording "already has an enrolled machine" will be corrected to "has any earlier machine approval".
  • Contract 1 line 111 says revoke is for those who "may enroll". The later clarification, my 20 Nov answer 5 and main, is machine:revoke. Downstream client disable on revoke stays an obligation, and session removal waits on central's session list.

6 · Key-set errors

Main today: the verifier machine_token::MachineTokenRefusal maps every KeySet(_) to Rejected (machine_token.rs:103–106). The variants are MalformedKeySet, UnknownKey and CacheUnavailable (issuer_key_cache.rs:138–145).

Meaning (Sign-in Lead proposal):

  • KeySet(MalformedKeySet) → Unavailable, retryable. It's the issuer's fault.
  • KeySet(CacheUnavailable) → Unavailable, retryable. It's the receiver's own cache.
  • KeySet(UnknownKey) → Rejected, unchanged. That's the answer after the one fetch on a cold cache, or the one forced refresh on a cached miss (issuer_key_resolution.rs:25–60).

On the hosts: connect and renewal give the existing retryable outcome at each host's boundary. A failed renewal never replaces the attachment. With valid keys and a still-valid enrollment and token, the retry succeeds.
