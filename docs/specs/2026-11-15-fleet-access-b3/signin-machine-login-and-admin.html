This is the Sign-in Lead's design input to the central Lead's FleetRuntime slice S5, which re-splits fleet-machine-login and fleet-admin out of central's single crate. It defines what the login tables and the issuer's answers mean. Central owns the checks, the commands and where they are mounted.

The global machine claim: options for the owner

Each organization's central store is its own Durable Object, so no single store sees every organization's machines. "One organization at a time" therefore needs an authority that sees all of them. That is a new storage boundary, and the owner decides storage. No option below is chosen.

One fact frames them all: machineId is the Router install's own UUIDv7 (migration 0001 comment, owner 18 Nov). It is self-asserted. A modified Router can pick any ID. So a server-side claim gives consistency for honest Routers; it is not a security boundary.

Allowances: the table

Owner decision, 20 Nov: "we want allwoance talbes". 9 Nov, B3 SQL review: "Approve option A".

CREATE TABLE login_machine_allowances (
    allowance_id     TEXT PRIMARY KEY,   -- UUIDv7 from the injected ID source
    machine_id       TEXT NOT NULL REFERENCES login_machines(machine_id),
    workspace_id     TEXT NOT NULL,
    state            TEXT NOT NULL,      -- Rust enum AllowanceState { Active, Withdrawn }
    enrollment_id    TEXT NOT NULL,      -- the enrollment that last changed it
    changed_by_person_id TEXT,           -- NULL when the change was automatic (expiry)
    created_at       TEXT NOT NULL,
    updated_at       TEXT NOT NULL
);
CREATE UNIQUE INDEX login_machine_allowances_pair
    ON login_machine_allowances(machine_id, workspace_id);

There are no CHECK constraints; state is the existing AllowanceState enum (organization_commands.rs:115). There is one row per machine and workspace, and its state moves between Active and Withdrawn. login_machines.allowed_workspaces is removed in the same migration, after its values are copied into rows.

The reader is workspace_admission, on every request. It admits only if a row (machine, workspace) is Active and the workspace is active. A missing row, a Withdrawn row or an archived workspace is refused with RefusalReason::WorkspaceNotAllowed, which matches today's refusals at workspace_admission.rs:41–48.

One live authority, one history: login_machine_allowances is the only live authority. login_machine_approvals.allowed_workspaces stays as an immutable record of what that approval asked for. Admission never reads it. The change records are the history.

State machine: an allowance is Active ⇄ Withdrawn. Withdrawn → Active happens only through Allow or a later approval.

The live idle check at connect and at renewal

Today: idle expiry is decided only when a token is minted (machine_token_decision.rs:42). machine_connection.rs:103–145 (validate_live) checks organization, effective deadline, identity, state and client, but it ignores last_grant_at (it matches Enrolled { client_id, .. }). With 600-second tokens the gap is small but real: a connection opened just before the 30-day boundary is admitted after it.

The decision (Sign-in Lead proposal, agreed with the central Lead as a central item): fleet-machine-login exposes one pure function, idle_expired(last_grant_at, now) → bool, using IDLE_EXPIRY_SECONDS. Access calls it inside validate_live at connect and at renewal, under the existing central turn, and calls it again after any wait for verification. When it returns true, admission calls the existing idle_expiry decision. That is the same guarded write: Expired, the generation bumped, allowances withdrawn and the record written, exactly once.

The refusal: MachineConnectionRefusal::EnrollmentNotActive {} at connect. At renewal it is MachineTokenRefusal::IdleExpired {}, the same answer the mint path gives.

An already-open connection is closed at the existing under-turn invalidation point, the same one revoke uses, because the generation changed. A retryable failure (store unavailable) writes nothing.

State machine (from StoredEnrollmentState): Approved → Enrolled (first grant); then Enrolled → Revoked{reason}, Enrolled → Expired, or Approved → Lapsed. Every ending state is terminal and bumps the generation on the machine.
