B3 · Machine login: Verification Design

The three things for you

V6 is the real journey: two Routers on macOS log in by device code through the sign-in page, connect through sign-in, against both Central builds; one is revoked and refused. V1 races two pollers on one code.

V3's allowance checks read machine_allowances rows (your 9 Nov decision). Cases:

  • active re-login adds: a machine with W1 and W2 active is approved again for W2 and W3; afterwards W1, W2 and W3 are active (W1 not withdrawn);
  • Withdraw is targeted: withdrawing W2 leaves W1 and W3 active;
  • revoke clears: after revoke none is active, and a fresh approval for W3 activates only W3 (W1 is not restored);
  • admission: a withdrawn or missing row refuses with WorkspaceNotAllowed.

Fails on: a build that replaces the set at approval (the W1 case); a build that restores old rows after revoke.

Approved B3 proof table; Lead A's 4a rows are observed here, built there.

V1 · Login and single use (S1, S2)

  • Kept: #11/#14's tests, merged forward, both hosts against real Central.
  • Two pollers redeem one approved code at once, barriers around the conditional write, on D1 and better-sqlite3: exactly one machine token.
  • Through the real page, Deny with an old confirmation: confirm the factor, and Deny is retried: the code is denied, no approval call is made, no machine token can be redeemed. Approve with an old confirmation, confirm, Approve: approved. Someone else denying: the code stays for the owner. Wrong build: #11's unconditional decide('approve') after confirmation.
  • Repeat approval with changed workspaces: the first stored approval returns; the page shows Central's stored values.
  • Hegel family device-approval-rule.hegel.unit.test.ts (M1) over code states, approvers, factor ages and time.
  • Redemption family (R33): device-redemption.hegel.host.e2e.test.ts on D1 and better-sqlite3, { testCases: 100, derandomize: true, database: hegel.Database.disabled }. Each case approves one code, then generates 2–5 pollers, a release order through barriers placed just before Better Auth's conditional consume (routes.mjs:289–379, consumeOne by code ID, owner and approved status), and optional pollers arriving after expiry on the controlled clock. Invariant: exactly one poller gets a machine-token response (access token, refresh credential, machine client ID, Central address, per machine-login-contracts.ts:167–172 on d60372cc), every other poller is refused, the device-code row is absent afterwards (native consumeOne deletes it, @better-auth/drizzle-adapter dist/index.mjs:473–496), and no person's sign-in session is issued. “Redeemed” is the model's logical state, not a stored status. Wrong build: a read-then-update redemption shrinks to two pollers both getting machine-token responses.

V2 · Connection and renewal (S3, S6)

  • A Router connects through the sign-in carrier on both pairings: on Node through the real listener's upgrade handler and the real Unix socket (not an in-process fetch), on workerd through the service binding. Messages flow both ways; closing either end closes the other; shutting the Node listener down closes upgraded sockets. A person token, a stale token, another installation's token and a superseded enrollment's token are refused by Central and that status reaches the Router (4a's check, observed).
  • On a controlled clock, a running machine renews many times on the open connection; a machine idle 30 days is refused idleExpired.
  • Token at grant_expires_at − 1 ms admitted, at equality refused.

V3 · Workspaces and revoke (S4, S5)

  • Approval with workspaces W1 and W3 picked from the live list: only those allowed. Withdraw W1, W3 stays; a non-owner's withdraw is refused.
  • Revoke: connection closed, client disabled, next renewal refused, Router asks for a new code. Drop the close at the fault proxy: the machine still gets nothing and ends at its token's expiry.
  • Re-login after revocation: nothing restored; workspaces chosen again.

V4 · BA1, re-key, switch (S7, S9)

  • BA1's six cases from approved B3, as Rust tests on both Central builds, plus a hegeltest family over M2 (enrollment). It draws approvals, first Grants, revocations, re-approvals and clock moves past 30 days, compares against an independent model, and checks after every step that a machine has at most one active enrollment and no approval activates after a generation change. Wrong builds: activate without comparing the generation (shrinks to approve, revoke, first Grant); no idle expiry (shrinks to Grant, clock + 30 days, Grant).
  • Re-key from three roots (pre-PR-A, post-PR-A, fresh): the machine ID is exactly the peer UUIDv7; sessions and allowances stay; a lost token answer then a retry with the same mapping is accepted; a different mapping is refused.
  • Link switch: hold a notice, a read and an install across the switch and kill the Router at each step; never a mix; same-central and other-central rules each hold after restart.

V5 · Secret store (S8)

  • The login code compiles against RefreshCredentialStore alone; the crate selects no platform.
  • Fake-source unit tests: absent then usable picks the second; a locked, denied or damaged first source stops with no later access; all absent with an empty store gives memory only; all absent with existing ciphertext, legacy data, temporary data, a missing key item, a wrong key or damaged metadata is an error, and the store's bytes are unchanged afterwards.
  • Kill between credential confirmation, metadata publication and retirement: no inconsistent pair is used. Separately, without killing the Host, make retirement fail after the public row committed: the terminal frame is outcomeUnknown (not “interrupted”), and the stored credential and metadata form a usable pair.
  • No plaintext on disk; memory-only restart needs a new code and comes back as the same machine. The Keychain case runs on your Mac with your yes.

V6 · The real journey and step switch (S10, S11)

  • Two Routers on macOS log in by device code through the sign-in page, connect through sign-in, against Central's Worker and Tokio builds; one is revoked and refused. Linux memory-only restart runs in the existing Ubuntu job.
  • Step 1 unchanged in production configuration; on a test deployment step 2 refuses the old credential and every bad machine token.
  • hegeltest families for the Router's two machines, in the codex-router host crate, each with an independent model, full comparison of next state and proposed effects after every step, and the settings fixed so runs repeat:
    • M3 (login): draws code replies, poll results, slow-downs, publication and retirement results, and a stream end with no terminal frame. Invariants: exactly one of the four endings; loggedIn only after the credential is confirmed and fleet_login replaced; an unconfirmable publication or retirement step is outcomeUnknown, never loggedIn; an old code is never resumed. Wrong builds: report loggedIn before retirement is confirmed; resume the old code after an interruption.
    • M4 (renewal): draws refresh results, renewal replies across 4a's closed refusal set, and clock moves around grant_expires_at. Invariants: a refresh always happens before grant_expires_at; one refusal leads to exactly one more refresh; a second refusal or enrollmentNotActive ends in needs-new-code. Wrong builds: retry forever after refusals; renew at or after grant_expires_at.
