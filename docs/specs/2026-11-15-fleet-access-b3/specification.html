B3 · Machine login: Specification

The three things for you

S2: one code, one machine, once. S5: revoke ends the connection and every later renewal. S7: a newer login always wins over a stale one (BA1). S8: the refresh credential is never written in plaintext.

S4's allowance storage (a machine_allowances table) and S7's enrollment storage (one row per login) are your 9 Nov decisions.

Approved B3 revision 2026-11-07.1; Lead A's 4a for Central's token, door and renewal.

Rules

S1 · Logging a machine in

From M1. codex-router fleet login --organization <id> --label <label> MUST print a code and an address. The owner, signed in with machine:enroll, opens it. A recent second factor is required when the organization already has an enrolled machine; the first machine is exempt (OD18). The owner sees the code beside the machine's label and organization, picks workspaces, and approves. The Router then gets a machine token and refresh credential and connects.

S2 · One code, one machine, once

From M2, M9. A code MUST be approvable once, redeemable once even when two pollers race, expire at its lifetime, and limit guesses (RFC 8628 §5). Approval logs in only the requesting machine, into only that organization. Someone else opening or denying the code leaves it for the owner. Deny also needs a recent second factor. A repeated approval returns the first one, unchanged. The approval rule is one pure function in the sign-in core.

S3 · Connect only through sign-in

From M4. The Router MUST connect to Central only through the sign-in service, which carries the WebSocket upgrade over the private link to Lead A's door. Every token but a valid machine token for that installation and active enrollment is refused (Lead A's check).

S4 · Workspaces

From M3. The approval page MUST list the organization's workspaces (from B2's ListWorkspaces) to pick from. Later the owner can allow one workspace and withdraw one, each one at a time, each recorded; a non-owner is refused. Central's admission reads the authoritative allowances live (4a).

S5 · Revoke at once

From M6. Revoking MUST, in one Central transaction, end the enrollment, withdraw its allowances, remove its sessions, bump the generation and write a record; then the old connection is closed and the sign-in service disables that enrollment's client. The next renewal is refused and the Router asks for a new code. If the close or the disable is lost, every decision still reads the enrollment live and the token ends at its expiry.

S6 · Renew with no one acting

From M5. The Router MUST refresh at the sign-in service before grant_expires_at (each refresh asks Central DecideMachineToken, read live) and send the fresh token on the open connection with RenewMachineToken (Lead A's 4a); Central answers renewed or refused. After one refusal it refreshes once more; on a second refusal, or enrollmentNotActive, it stops and asks for a new code. A machine idle for 30 days is refused as idleExpired.

S7 · A stale login never replaces a newer one (BA1)

Each approval records the machine's generation; its first token activates only if the generation is unchanged, then supersedes the old enrollment and bumps it. Otherwise it is refused and can never activate. A revocation bumps too, so every approval made before it is dead. B3 confirms machine_enrollment.rs on Central's main (merged in #281) enforces this and the 30-day idle expiry, and changes it if not.

S8 · The Router keeps its secret safely

From M7. The login code uses only RefreshCredentialStore. The host injects [MacKeychain] on macOS and nothing elsewhere. Classification: the first usable source supplies the key for the encrypted envelope; if all are absent and the store classifier allows it, memory only, and the login says so; a present but locked, denied or damaged source is an error with no fallback. No plaintext credential is ever written. Saving is ordered: confirm the credential, replace the public fleet_login row, retire older credentials.

S9 · UUIDv7 re-key and link switch

From M8. At the first B3 login the machine's ID becomes its peer UUIDv7; a former service ID it sends maps once to that ID and keeps its sessions, allowances and board relationships; the same mapping later is accepted, a different one refused. Re-login while active keeps sessions and allowances and closes the old connection; B3 decides when to switch and calls Lead A's link client re-enrolled entry (central-link-client/src/link_state.rs:344), with R10/R10a's same-central and other-central rules.

S10 · Production stays on today's login

Central's machineLogin setting is step 1 in production and step 2 on test deployments. Switching production is your step.

S11 · Machines and Hegel

Device-code decisions (M1), enrollment with BA1 (M2), the Router's login (M3) and on-connection renewal (M4) MUST be closed unions with pure transitions, inline exhaustiveness (x satisfies never in TypeScript; exhaustive match with no wildcard in Rust), effects as data, and Hegel families: @hegeldev/hegel in TypeScript, and hegeltest (hegel-rust) in Rust, pinned to the same version Lead A pins for Central's reducers (your 15 Nov “use hegel” rule). There is also a real race of two pollers redeeming one code, on both databases.
