Machine claim: one Mac, one organization

The rule: a machine ID belongs to the first organization that enrolls it, permanently.

How: sign-in writes one claim row per machine ID at the first approval, and never changes it. Sign-in refuses any other organization's approval of that ID, and any token forward for it. Every approval and token request already passes through sign-in, so central changes nothing.

Moving organizations: a Mac that really needs to join another organization does so as a new machine. Its Router takes a new machine ID, which is in the Mac Lead's set.

The owner's rulings

  • 20 Nov, asked "may one machine be enrolled in two organizations at once?": "no it may not, but how we ensure this / only by the router righ?"
  • 20 Nov, asked "when a machine moves to another organization, is the old enrolment ended or only blocked?": "a machien cannot move to another organization".

Both are his exact words, as recorded by the central Lead at codex-router design/central-and-mac ed703c34b, deliverables/04-fleetruntime/decisions.html#claim-no-move. "Belongs to the first organization for good" is the central Lead's reading, labelled as his reading there, and I share it.

Sign-in's claim table

Sign-in Lead proposal; the name is the owner's decision. It uses Drizzle on D1 and better-sqlite3, with the login_ prefix.

CREATE TABLE login_machine_claims (
    machine_id       TEXT PRIMARY KEY,  -- the Router's own UUIDv7
    organization_id  TEXT NOT NULL,     -- the first organization to approve it; never changes
    claimed_at       INTEGER NOT NULL,  -- injected clock
    first_request_id TEXT NOT NULL      -- the device-login request that created the claim
);

There are no CHECK constraints. Nothing ever updates or deletes a row.

Sign-in's rules

  1. Approval of machine M by organization X, before forwarding to central's existing device-login route:
    • no row: INSERT (M, X). The primary key makes it atomic. If two organizations approve at once, one insert wins and the other reads the row.
    • a row for X: forward. That covers re-approval and re-enrolling in the same organization.
    • a row for another organization: refuse, and forward nothing.
  2. Token forward (first grant or refresh) for an enrollment of organization X: read M from the OAuth client's metadata (see trusted ID). Forward only if the row is (M, X). Otherwise refuse with the existing EnrollmentNotActive. This can only happen to a pre-cutover or forged credential.
  3. Revoke, idle expiry and lapse don't touch the claim. The organization keeps M. Its owner can approve M again later, as a new enrollment.

Why this is safe without a fence: the claim never moves, so no message in flight can be overtaken by a move. Central only ever receives approvals and token forwards for M from M's own organization, because sign-in is the only caller of those routes.

A trusted machine ID

  • When an approval binds the OAuth client for an enrollment, sign-in stores the canonical machineId in the client's metadata. Token forwards read it from there, never from the request.
  • The deviceCode table's two-ID columns (machineInstallationId, machinePeerId; sign-in-schema.ts:308–332 at Switchboard main 7e32e00e) become one machineId, under the owner's one-ID rule of 18 Nov.

Turning it on

The gate turns on at the central identity cutover. Central's owner record says it starts fresh then. The order:

  1. Drain and stop the old sign-in deployment, so no ungated approval or token forward is still in flight (review R2-4's held-request schedule).
  2. Open fresh central stores and an empty login_machine_claims.
  3. Start the gated sign-in.

Old device codes and token families point at enrollments that don't exist in the fresh stores, so central refuses them. Central needs no epoch and no switch, because sign-in is its only caller for these routes.

  • A dependency: if the cutover is not fresh, existing enrollments would need a seeding design before the gate can turn on.
  • Restore: if login_machine_claims is restored from an older backup, a machine could be approved by a second organization. So a restore of this table suspends approvals until it's reconciled against the central stores, an owner-run operation. Ordinary reopen of the same intact database isn't a restore.

Limits

  • Scope: one sign-in deployment (one issuer).
  • The machine ID is chosen by the Router install. A new machine ID is how a Mac legitimately joins another organization. The claim binds IDs, not hardware.
  • The gate requires a fresh cutover.
