Machine claim: one Mac, one organization

The rule: a machine ID is enrolled in at most one organization, and the server enforces it.

How, in four pieces:

  1. The claim: sign-in keeps one claim row per machine ID, with a version. Every approval and token request already passes through sign-in, and each forward now carries that version.
  2. The question: when a second organization approves a machine another organization holds, sign-in asks the holder's store one question over the existing private link.
  3. The fence: that question is a small guarded write. The holder's store raises its fence for that machine to the new version and answers Live or NotLive from the same snapshot.
  4. The effect: from then on the holder's store refuses any forward carrying an older version. A delayed or retried old approval or token can never commit after the claim moves, whatever its clock says.

Still one-way: sign-in asks, central answers.

What would reach the owner:

  • a claim table in sign-in's database;
  • a small fence table in each organization's central store;
  • a new claimVersion field on the two existing decision requests;
  • a new retryable refusal.

The central Lead writes central's half and puts option B (one central registry) beside it.

The shape

Sign-in's claim table

Sign-in Lead proposal; the name is the owner's decision. It uses Drizzle on D1 and better-sqlite3, with the login_ prefix.

CREATE TABLE login_machine_claims (
    machine_id      TEXT PRIMARY KEY,   -- the Router's own UUIDv7
    organization_id TEXT NOT NULL,      -- the holder
    state           TEXT NOT NULL,      -- Rust/TS union ClaimState { Held, Checking }
    checking_for    TEXT,               -- the organization asking, while Checking
    checking_since  INTEGER,            -- injected clock; a stale Checking can be taken over
    busy_until      INTEGER,            -- injected clock: a token issuance (first grant or refresh) is reserved until this time
    version         INTEGER NOT NULL,   -- incremented on every write; every write is conditional on it
    updated_at      INTEGER NOT NULL
);

There are no CHECK constraints.

Issuance reservation (review R2-3)

Better Auth 1.7.11 consumes a one-time device code in redeemDeviceCode before issueTokens, and a refresh rotates its refresh token in the same way. So sign-in must never return a "retry" after Better Auth has consumed anything. The order for every token issuance (a device-code poll or a refresh) for machine M at holder X is:

  1. Before Better Auth consumes anything, a conditional write on Held(X, v) sets busy_until to one request timeout plus SD8 (injected clock).
    • If the row is Checking: answer before consuming. A device-code poll gets authorization_pending (RFC 8628: keep polling, the code is untouched). A refresh gets the retryable transient outcome (the refresh token is untouched).
  2. Redeem or rotate, then forward to central with claimVersion = v.
  3. Clear busy_until when central answers.

No check while a reservation is held: a write to Checking requires busy_until to be empty or past, otherwise the other organization's approver gets "try again". So a check can never start between the reservation and the forward, and the consumed code or token is always followed by a forward under a version no fence has passed. A crashed reservation runs out by itself, and the Router's retry after a lost response follows Better Auth's own replay rules for that code or token.

A trusted machine ID at every forward (review B5)

  • When an approval binds the OAuth client for an enrollment, sign-in stores the canonical machineId in that client's metadata. Before every token forward, sign-in reads it from the client, not from the request.
  • The deviceCode table's two-ID columns (machineInstallationId, machinePeerId; sign-in-schema.ts:308–332) become one machineId, under the owner's one-ID rule of 18 Nov.
  • Cutover: the gate turns on at the central identity cutover. Central's owner record says it starts fresh then, so every central store and this table start empty together, and there's nothing to reconcile.
    • A dependency: if the cutover is not fresh, the gate can't be turned on. Reconciling existing enrollments would need its own design.
    • Before the gate: forwards carry no claimVersion, and central behaves as main.
    • Once it's on: central refuses a forward without one. The central Lead names where that switch lives.

After the answer to FenceAndReport(M, u):

  • NotLive gives Held(Y, u+1). Y's forwards carry u+1. Y's store has no fence for M, or a lower one.
  • Live gives Held(X, u+1). X's forwards carry u+1, which is above X's fence u.
  • Unavailable gives Held(X, u+1) as well. The fence may already be set, and the higher version keeps X's later forwards valid.
  • A StaleQuestion answer (the carried version is at or below the stored fence) is discarded. Only the request that wrote that version may act on it.

Every conditional write checks the version it read. If the version moved underneath it, the write fails and the request reads again.

Handling ClaimVersionStale

When a forward carrying an old version reaches a store whose fence is higher, central answers the new, retryable ClaimVersionStale (central's contract, condition 3). Sign-in never passes it to the Router. Instead it re-reads the row:

  • still Held(X): re-forward once with the current version. This is the refresh that was in flight during a Live check;
  • Held(other): the terminal answer. For a token it's EnrollmentNotActive. For an approval, the approver is told the Mac is in another organization;
  • Checking: the retryable transient outcome.

Activation and restore (review R2-4)

  • One authority epoch: at cutover, a new authorityEpoch (UUIDv7) is set once for the issuer and its complete set of central targets. Every forward carries it, beside claimVersion.
  • The order:
    1. Quiesce old ingress.
    2. Open fresh central stores and an empty claim table with the epoch.
    3. Retire old device codes and token families. They carry no epoch, so they fail.
    4. Open versioned ingress.
  • Where it's enforced: central checks the epoch under the owning turn, at the admission and commit boundary. An unknown, missing or mixed epoch fails closed.
  • Restore or loss: if either side's authority store (the claim table, or a central store with fences) is restored from a backup, or lost, that side starts in a suspended state. Machine approvals and first grants fail closed until a reconciliation run (an owner-run operation, designed separately) checks it, or a new epoch is cut. Ordinary reopen of the same intact SQLite isn't a restore.
  • Ownership: the epoch switch lives in central's contract (the central Lead names where). The sign-in side carries it and refuses to forward without it once it is set.

Central's contract, as sign-in relies on it

Central's half owns this; listed here so the pair can be read together. Agreed 20 Nov.

  • FenceAndReport { organizationId, machineId, claimVersion }. Under the organization's turn, in one batch, the store raises fence(M) to claimVersion and answers Live { Approved | Enrolled } or NotLive { reason } from the same snapshot. The fence lives in login_machine_claim_fences(machine_id PK, fence_version, updated_at), a working name.
  • The fence only goes up. A question whose version equals the stored fence writes nothing and answers from the rows, so a replay is safe. A version below the fence answers StaleQuestion.
  • Both existing decisions (device login, machine token) read fence(M) under the turn and refuse a forward whose claimVersion is below it, with ClaimVersionStale.
  • Live is computed from the machine row and every candidate row, with the same predicates the token decision uses, generation included (review correction 1).
  • A store that can't give a stamped, valid answer means unavailable: retry, and the claim is kept.
  • Both hosts mount the route.

State machine

What the fence does not do

It doesn't end A's stored row, close A's sockets, or withdraw a token already issued. With a NotLive answer, A has no grantable enrollment, so a still-valid A token can exist only with a skewed clock, and it lasts at most ten minutes. The rule this enforces is about grantability. A's Machines list keeps showing its row as it is stored, with its last token grant.

Limits

  • Scope: one sign-in deployment (one issuer).
  • The machine ID is chosen by the Router install. The claim keeps honest Routers consistent; it doesn't prove physical identity.
  • Organization deletion: main has no organization removal. If one is added, releasing that organization's claims is part of that feature. Until then, an organization whose store can't answer keeps its claim.
  • The gate requires a fresh cutover. Without one, existing enrollments would need a reconciliation design.
  • Clock assumption: the stale bounds (checking_since, busy_until) use sign-in's injected clock. A backward step only delays recovery, it doesn't break exclusivity, because exclusivity rests on the version and the fence, not on time.
