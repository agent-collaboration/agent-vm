Machine claim: one Mac, one organization

The rule: a machine ID is enrolled in at most one organization, and the server enforces it.

How: sign-in keeps one claim row per machine ID in its own database. Every approval and token request already passes through sign-in, so sign-in is the gate. When a second organization approves a machine that another organization holds, sign-in asks central one new, read-only question over the existing private link: "is this machine's enrollment live in that organization?". Central never calls sign-in, and central writes nothing new.

What the owner decides: a new table in sign-in's database (storage is his), plus one read route on central. This page is the Sign-in Lead's half. The central Lead writes central's half in the FleetRuntime set. One independent review reads both together.

The shape

Sign-in's claim table

Sign-in Lead proposal. The table name is the owner's decision. It uses Drizzle, on D1 (Cloudflare) and better-sqlite3 (Node), with the login_ prefix like the other machine-login tables.

CREATE TABLE login_machine_claims (
    machine_id      TEXT PRIMARY KEY,   -- the Router's own UUIDv7
    organization_id TEXT NOT NULL,      -- the holder
    state           TEXT NOT NULL,      -- Rust enum ClaimState { Held, Checking }
    checking_for    TEXT,               -- the organization asking, while Checking
    checking_since  INTEGER,            -- injected clock; a stale Checking can be taken over
    version         INTEGER NOT NULL,   -- incremented on every write; all writes are conditional on it
    updated_at      INTEGER NOT NULL
);

There are no CHECK constraints. ClaimState is a closed Rust or TypeScript union: Held{organization} or Checking{holder, asker, since}.

Related sign-in change: the deviceCode table (sign-in-schema.ts:308–332, Switchboard main 7e32e00e) still has the old two-ID columns, machineInstallationId and machinePeerId. These become one machineId under the owner's one-ID rule of 18 Nov. That's needed anyway.

The question to central (the contract)

I accept the central Lead's contract points 1–4 and 7 as stated:

  • The route: IsEnrollmentLive { organizationId, machineId }, read-only, answered under that organization's own turn. It writes nothing and fences nothing. Both hosts mount it: Cloudflare and the self-hosted one.
  • The answer is a closed variant: Live { Approved | Enrolled } or NotLive { reason }. The reason is one of: ended (Lapsed | Expired | Revoked), UnknownMachine, ApprovalPastDeadline, IdleExpired (central applies the 30-day rule on read without writing), or NoSuchOrganization.
  • A deleted or never-provisioned organization gives a definite NotLive{NoSuchOrganization}. Only a transport failure, or a store that exists but didn't answer, means "retry".

Why no fence in central is needed. Live covers exactly the enrollments that could still be granted a token. A first grant needs an Approved row before its deadline (machine_token_decision.rs:76–92). A refresh needs an Enrolled row that isn't idle (:42–43). Ended states are terminal (machine_login_writes.rs:333–352). So an enrollment that reads NotLive can never be granted again. The only way back into that organization is a new approval, and every approval passes through sign-in's claim row. As a second safeguard, sign-in also refuses to forward a token decision for an organization that doesn't hold the claim.

Sign-in's rules: what sign-in owns

  1. Approval for org X, machine M (before forwarding to central's existing device-login route). All writes are conditional on version.
    • No row: insert Held(X), then forward.
    • Held(X): forward (the same organization re-approving or re-enrolling; the claim stays).
    • Held(Y), Y ≠ X: write Checking(holder Y, asker X), then ask Y IsEnrollmentLive.
      • NotLive: write Held(X), then forward.
      • Live: write Held(Y), then refuse.
      • Retry (transport): write Held(Y), then answer "try again".
    • Checking by another request: answer "try again". If checking_since is older than the stale bound (one request timeout plus the 5 s SD8 window, on the injected clock), take it over and ask again.
  2. Token decision for org X (first grant or refresh): forward only if the row is Held(X). Otherwise refuse with the existing EnrollmentNotActive, which the Router already treats as "get a new code" (B3 M4).
  3. Revoke, lapse and idle expiry need no release call. The row stays Held(X) until another organization asks, and the question then finds the ending.

Limits

  • Scope: one sign-in deployment (one issuer). Separate deployments don't share claims.
  • The machine ID is chosen by the Router install: the claim keeps honest Routers consistent. It doesn't prove physical identity.
  • Endings inside central that sign-in never sees (a store reset, an organization deletion or a manual repair) leave a stale row. It resolves on the next question, so it can't block forever.
