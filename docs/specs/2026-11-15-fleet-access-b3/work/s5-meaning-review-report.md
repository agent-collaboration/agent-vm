### B3. The global claim options need a lifecycle before they can be compared against the same rule

S5:77 and :102 keep the choice open. A and B correctly disclose that only the claim write is atomic within its store. The release and failure descriptions remain incomplete. The Lead's answer binds the rule to an active enrollment. Approval only creates a pending row. An approval can lapse, a same-org re-login can supersede, and the claim and the organization write can disagree after an interrupted decision. A crash can leave that disagreement indefinitely until reconciliation. Releasing on a later unspecified refusal provides no evidence that the enrollment owning the claim ended. Define reservation versus activation, the scope of the shared authority across deployments, how every decision reaches it, how an unresolved decision recovers, and the ending enrollment or generation a release must match. Cover both pending lapsed approvals and an ending callback that arrives after a newer claim.

D guarantees one locally selected enrollment. Its server-side release depends on another successful operation. Main's private revoke requires an authorized person's recent signed proof and the enrollment ID. The Mac-local switch supplies neither that authorization nor an atomic transfer. Two server enrollments can remain active after the switch, even with an honest Router. That makes the claimed equivalence at :102 false for one active server enrollment per machine ID. C and D can be presented as changes to the invariant for the owner to weigh. The self-asserted ID limits what A and B say about physical identity, while their shared write still serializes claims for the same ID. ### B4. The live idle behavior and its proof disagree with the grant clock and the renewal path

S5:139 correctly identifies the missing `last_grant_at` check in `validate_live`. Its production example cannot follow normal issuance. Each successful grant sets `last_grant_at` and returns a grant deadline 600 seconds later. The verifier hard-caps the connection at that deadline. Waiting 30 days on a normally issued token hits token expiry first even in the wrong build. A real-path check needs an explicit fixture with an aged stored grant and an independently valid test token/current attachment. Force the verification wait across the idle boundary while both token deadlines are still live, and assert that omission of the idle check admits or renews that same input. That witnesses defensive live admission using controlled inputs. Keep it distinct from normal issuance.

The draft also calls the renewal answer `MachineTokenRefusal::IdleExpired {}`, which is a **mint** refusal. Core and the two host adapters use the distinct `MachineTokenRenewalRefusal` and link refusal types, with no current idle variant. Workerd pre-restores the attachment before calling core renewal. Core restores again before verification, then re-reads under the turn. A new shared `validate_live` rule also affects socket registration, restore, and request admission. A refusal at the first restore can bypass the proposed expiry writer or flatten its result to `EnrollmentNotActive`. Specify the call sites, a typed result for each host and link mapping, and where the guarded write and post-commit invalidation occur. Test connect and renewal independently, including restore, no-write unavailability, and the old attachment or pending approval after reopen.
