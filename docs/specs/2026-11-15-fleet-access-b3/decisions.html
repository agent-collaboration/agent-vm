B3 · Machine login: Decisions

B3 lets a machine (a Router on a laptop or server) log in to your organization with a device code you approve once. Its token then renews itself while it stays connected, and you can revoke it from the admin page. Two storage choices and one SQL approval are yours; the merge question is mine (decided below). Each is explained with background and an example.

2 · How Central stores each login (“enrollment storage”)

Background. Each time you approve a machine's code, Central records an enrollment: who approved it, when, which machine, and later how it ended (revoked, replaced, or idle for 30 days). Central already stores enrollments as their own rows, one per login (A, merged in #281, machine_enrollment.rs). On the earlier audit page you picked A but wrote “whats teh cons i don tkudnetand fully”, and you never confirmed it after the explanation. So this asks again, with the costs spelled out.

Example. You log in your laptop in March, revoke it in June after losing it, then log in a new laptop under the same name.

What you get

Both logins stay as rows: March to June, revoked by you; then the new one, active. You can always answer “who let this machine in, and when did that end”. Only one row per machine can be active at a time.

What it costs

About ten columns per row, and ended logins stay as small rows forever. No rework.

Picture

What you get

The machine row says only “current login: June, approved by you”. The March login is overwritten.

What it costs

Login history is lost; login state is split across two tables during approval; Central's merged code is reworked.

Picture

It keeps the history you'd want after a lost machine, and it's already built and tested.

3 · Where a machine's allowed workspaces live

Background. When you approve a machine you pick which workspaces it may use, and later you can allow or withdraw one at a time. Central already has a column for this, machines.allowed_workspaces (0001_workspace_requests.sql:3). Central's admission reads it live on every request (Lead A's 4a). The approved B3 sketched a separate table, to be reconciled with existing columns.

Example. You approve your laptop for “billing” and “docs”, then withdraw “docs” a month later.

What you get

The column goes from [billing, docs] to [billing]. The history page shows “docs withdrawn by you” as an allowanceChanged record. Admission stops allowing “docs” on the next request.

What it costs

Per-workspace history lives in the record list, not in its own table.

Picture

What you get

One row per machine and workspace with its own state: billing active, docs withdrawn.

What it costs

A migration, the column retired, and Lead A's admission read moved to the table.

Picture

No new table and no second place holding the same truth; the history is still visible as records.

B3 can't start: the commands and admission depend on it.

4 · The re-key column (SQL approval at build time)

Background. Today a machine is known on Central by an older routing ID. At its first B3 login it takes its permanent ID: the Router's own UUIDv7. To keep its sessions, allowances and queued mail, Central renames the machine in one transaction and records the old ID, so that a retried login with the same mapping is accepted and a different mapping is refused. Recording it needs one new column on Central's machines table (former_installation_id).

Example. Your laptop's Router logs in, and the reply is lost. It retries with the same old-to-new mapping: accepted, with nothing duplicated. A different machine claiming the same old ID is refused.

The exact SQL comes to you before it's built: one nullable column on machines, filled once at re-key. Nothing is written until you approve it.
