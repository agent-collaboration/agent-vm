Why --device doesn't exist

sign-in-owner-cli/src/owner-cli.ts:43–46 exits 1 with “not available”, citing the 8 Nov deferral (push 01a1ba36-49af). The cause, from the pinned library:

  • The OAuth provider's device grant redeems a code and issues tokens with user, scopes and key confirmation but no session ID (@better-auth/oauth-provider dist/index.mjs:50–99). Our contributor refuses that (person-access-token-claims.ts:45).
  • Better Auth's own first-party device flow (deviceAuthorization()) creates a real session when the code is redeemed and returns it as a bearer session token (dist/plugins/device-authorization/routes.mjs:433–475); approval only records the user (:616–627). The OAuth wrapper refuses first-party redemption of its own codes (oauth-provider dist/index.mjs:176–181).
  • Better Auth's bearer() plugin turns a bearer session token into the session cookie for a request (dist/plugins/bearer/index.mjs:24–47); it isn't configured today. Its after-hook exposes session cookies as a set-auth-token header on every response (:54–66).
  • OAuth authorize reads the session with getSessionFromCtx (oauth-provider dist/authorize-*.mjs:59) and for a client that skips consent issues a code tied to that session. Our Fleet CLI client is PKCE and skips consent (better-auth/owner-client-bootstrap.ts).

So a device login that keeps a real session is possible with Better Auth's own parts: first-party device code → session → OAuth authorize with that session → the existing token exchange. It has costs, set out on Decisions.

Nothing shows revocation status

authorization-revision-delivery-store.ts:316–370 has readSynchronization for three scopes (a person in an organization, a person everywhere, an organization), answering synced or pending, with missing rows pending and storage failure unavailable. The only callers are the store composition and tests. The approved additions require “revoked everywhere” to be shown only with Central's acknowledgements.
