Open: how does --device keep a session?

What a person sees

--device says it's not available; headless machines can't sign in.

What changes

Nothing.

What it costs

Your 7 Nov choice isn't delivered.

Picture

What a person sees

A code to approve in their browser; then, if needed, an organization pick and a second-factor prompt in the CLI.

What changes

Better Auth's own deviceAuthorization(); browsers refused on the device routes; the terminal's session converted to Better Auth's own signed cookie on six paths before dispatch; the CLI completes the existing PKCE login with the new session and stores the session secret beside its key.

What it costs

A long-lived session secret on the machine (Keychain or memory). A small terminal adapter in the outer handler and its containment tests.

Picture

What a person sees

A code to approve; signed in.

What changes

The OAuth device grant as shipped; a new token profile without a session; the contributor and Central's admission change.

What it costs

There's no device session to end or expire, so ending “the device's login” has no handle; a device token still dies on any role or membership change, on any session end for that person (person-wide), and at expiry. Its refresh lifetime needs designing. A changed contract on both sides.

Picture

Cost: your choice undelivered.

Cost: a session secret on the machine; containment rules.

Cost: no device session to end; refresh lifetime to design.

It delivers --device and keeps “ending the session ends the token”, using only Better Auth's own parts.

B2X can't start: it would ship with device login unfinished.
