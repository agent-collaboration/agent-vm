How --device keeps a session (decided)

How it got here. On 8 Nov the Implementer stopped: Better Auth's OAuth device grant gives a token with no session, which our token contributor refuses. I deferred --device and promised you a decision page (push 01a1ba36-49af). It reached you on 15 Nov, and you picked Better Auth's own device flow with a real session.

What it means in practice.

  • A lost or stolen terminal: sign out its session S. Its refresh fails, and after Central's acknowledgement its token is refused. Ending a session raises your person revision, as r3 §3 requires (storage/authorization-fence-mutations.ts:233–244). So your other sessions stay signed in, but their current tokens are no longer accepted. The CLI refreshes at the start of each command (fleet-credential.ts:154–160), so the next command just works. A command already in flight when the change landed can be refused with refreshRequired, and you rerun it; the CLI doesn't retry that by itself (fleet-admin-command.ts:129–140).
  • A protected command asks for a recent second factor: the CLI asks for your app or recovery code and confirms S, because confirmations belong to a session.
  • Central needs no change: the token has the same shape as a browser-login token.
  • On the terminal: the key, the refresh credential and S's secret. All three go in Keychain on macOS, otherwise memory only, never a file.
