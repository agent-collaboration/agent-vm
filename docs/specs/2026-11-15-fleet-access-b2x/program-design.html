B2X · Person tokens and revocation: Program Design

How it's built. Sign-in core paths are under packages/sign-in-core/src/; CLI paths under packages/sign-in-owner-cli/src/. The detail follows the recommended device option B.

The three things for you

Device login uses Better Auth's own device flow; browsers can't call the device routes, so page script never gets the session token, and only terminal requests on six paths can use it. The sync view counts person changes too, and still answers for a removed person.

Branch notes give A and C.

Device login, option B

  • Configuration. deviceAuthorization() from Better Auth 1.7.11 with validateClient admitting only the Fleet CLI client ID; its own expiry and polling interval. Approval is Better Auth's endpoint, reached from our approval page; the approving browser must be signed in. Better Auth stores and expires the code; redeeming creates the session (routes.mjs:433–475).
  • Terminal requests only. /api/auth/device/code and /api/auth/device/token are admitted only for terminal requests. In sign-in-request-handler.ts, before dispatch, a request is a browser request if it carries any of Origin, Sec-Fetch-Site, Sec-Fetch-Mode or Cookie; browser requests to those two paths get 404. Origin is a header page script can't remove or set, and browsers send it on every POST, same-origin included, even when Fetch Metadata is withheld (which happens for origins that aren't potentially trustworthy) and cookies are omitted. The CLI and Router clients send none of the four. Residual: a browser too old to send Origin on same-origin POST is not covered; named as unverified. So page script can't obtain the session token that /device/token returns in its JSON body (routes.mjs:455–475). Approval stays a normal cookie request from the signed-in browser.
  • Using the session from the terminal, without bearer(). Better Auth's bearer() plugin is not added: its conversion only takes effect after every before-hook has run (dist/api/dispatch.mjs:64–106,209–220), so our factor and actor hooks would see no session, and its after-hook puts session tokens in a set-auth-token header. Instead, the outer handler converts a terminal request's Authorization: Bearer <session token> into Better Auth's own signed session cookie before dispatch, using the same serializeSignedCookie from better-call and the configured secret that bearer() itself uses (bearer/index.mjs:3,34–47), and removes the Authorization header. Every hook then sees an ordinary session. The conversion happens only for terminal requests on six paths: GET /api/auth/oauth2/authorize, GET /api/auth/organization/list, POST /api/auth/organization/set-active, POST /api/auth/two-factor/verify-totp, POST /api/auth/two-factor/verify-backup-code, POST /api/auth/sign-out. Anywhere else a bearer session is simply not a session (Better Auth reads only cookies), so nothing else changes. GET /api/auth/organization/list is admitted by the outer route table only on this terminal path.
  • Authorize and exchange. The CLI calls authorize with the bearer session, S256 PKCE and redirect: 'manual', reads the code from the Location header of the registered loopback redirect without listening on it, and exchanges as today. Authorize reads the session through getSessionFromCtx and the Fleet CLI client skips consent (owner-client-bootstrap.ts), so the code carries the session; the existing contributor and Central accept the token unchanged.
  • Organization. A fresh session with one membership selects it; with several, the CLI calls Better Auth's native GET /api/auth/organization/list (crud-org.mjs:436–453) through the terminal path, shows the person's organizations, and calls set-active with the chosen ID before authorizing.
  • Second factor. The new session has no confirmation. When Central answers secondFactorRequired, the CLI prompts for an app or recovery code and posts it with the bearer session, which confirms that session. The approving browser's confirmation is never copied.
  • Custody. ProofKeyStore (fleet/proof-key-store.ts:11–27) gains the session secret beside the key and refresh credential: macOS Keychain through the injected runner, otherwise memory for that command only, never a file. Losing any of the three clears all three.

The owner's sync view

Today's readSynchronization({ kind: 'organization' }) reads only the organization fence (authorization-revision-delivery-store.ts:338–344), but removals and role changes advance person fences only. So the store gains one scope, { kind: 'organizationWithPeople', organizationId }: one Drizzle read of the organization fence and every retained person fence in that organization, synced only if every row's ACK equals its revision, missing rows pending.

better-auth/access-sync.ts: POST /api/auth/organization/access-sync with { organizationId, email? }. Checks the person's current organization and organization:view. Returns organization from organizationWithPeople; with an email, finds the retained authorization subject for that person in this organization (it survives removal) and returns person from personInOrganization for that subject, or none if this organization never had them. Reply { organization: 'synced' | 'pending', person?: 'synced' | 'pending' | 'none' }, 503 unavailable; no-store; email in the body, never the URL. Shown on B2's admin page status card (“All access changes have reached Central” / “Waiting for Central”) and on B1-C's lookup page for a member or a removed person (“removed; waiting for Central” / “removed; reached Central”).

M2 · The view in the browser

States loading | synced | pending | unavailable, each with a request generation; events refresh, reply(generation, value), failed(generation). Only the current generation settles; refresh is manual or on page entry, no polling.
