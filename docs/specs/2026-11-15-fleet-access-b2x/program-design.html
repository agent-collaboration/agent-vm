B2X · Person tokens and revocation: Program Design

How it's built. Sign-in core paths are under packages/sign-in-core/src/; CLI paths under packages/sign-in-owner-cli/src/. The detail follows the recommended device option B.

The three things for you

Device login uses only Better Auth's own parts; the session token never reaches a page script because the release layer strips the bearer plugin's header and only terminal paths accept a bearer session. The sync view is a read with no side effects.

Device login, option B

  • Configuration. deviceAuthorization() from Better Auth 1.7.11 with validateClient admitting only the Fleet CLI client ID; its own expiry and polling interval. Approval is Better Auth's endpoint, reached from our approval page; the approving browser must be signed in. Better Auth stores and expires the code; redeeming creates the session (routes.mjs:433–475).
  • Bearer sessions, contained. bearer() is added so the CLI can use that session. Its after-hook would put the session token in a set-auth-token header on any reply carrying a session cookie (bearer/index.mjs:54–66); the release layer deletes that header and removes it from access-control-expose-headers on every reply, so no page script ever sees it. Before dispatch, an Authorization: Bearer value without dots (a session token, not a JWT) is accepted only on: GET /api/auth/oauth2/authorize, POST /api/auth/organization/set-active, POST /api/auth/two-factor/verify-totp, POST /api/auth/two-factor/verify-backup-code, POST /api/auth/sign-out; elsewhere it gets 401.
  • Hook order. Better Auth runs the user before-hook before plugin before-hooks. The organization actor capture in provider-configuration.ts:230–238 runs before bearer converts the header, so for a bearer request to set-active it would see no session. The capture moves into a small plugin registered after bearer(), keeping the same behaviour for cookie requests.
  • Authorize and exchange. The CLI calls authorize with the bearer session, S256 PKCE and redirect: 'manual', reads the code from the Location header of the registered loopback redirect without listening on it, and exchanges as today. Authorize reads the session through getSessionFromCtx and the Fleet CLI client skips consent (owner-client-bootstrap.ts), so the code carries the session; the existing contributor and Central accept the token unchanged.
  • Organization. A fresh session with one membership selects it; with several, the CLI lists them and calls set-active with the bearer session before authorizing.
  • Second factor. The new session has no confirmation. When Central answers secondFactorRequired, the CLI prompts for an app or recovery code and posts it with the bearer session, which confirms that session. The approving browser's confirmation is never copied.
  • Custody. ProofKeyStore (fleet/proof-key-store.ts:11–27) gains the session secret beside the key and refresh credential: macOS Keychain through the injected runner, otherwise memory for that command only, never a file. Losing any of the three clears all three.

The owner's sync view

better-auth/access-sync.ts: GET /api/auth/organization/access-sync?organizationId=…[&personId=…]. Checks the person's current organization and organization:view. Calls readSynchronization({ kind: 'organization', organizationId }) and, when personId is given and is a member, { kind: 'personInOrganization', … }. Reply: { organization: 'synced' | 'pending', person?: 'synced' | 'pending' }, or 503 unavailable; no-store. Shown on B2's admin page status card (“All access changes have reached Central” / “Waiting for Central”) and beside a member answer on B1-C's lookup page.

M2 · The view in the browser

States loading | synced | pending | unavailable, each with a request generation; events refresh, reply(generation, value), failed(generation). Only the current generation settles; refresh is manual or on page entry, no polling.
