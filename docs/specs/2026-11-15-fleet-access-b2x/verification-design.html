B2X · Person tokens and revocation: Verification Design

How each rule is shown to hold, on both sign-in hosts paired with the real current Central. Nothing has run.

The three things for you

V2 signs in with --device, then deletes the device session and requires Central to refuse the token. V4 removes a member, holds Central's ACK, and requires “waiting”, then “reached” only after the ACK lands. The r3 table gives every counterexample an owner.

V2 proves your pick: device login with a real session.

Each row traces to Specification. A recording Central peer never stands in for real Central here.

Where it runs

The joint fixture (sign-in-test-support/src/test-fixtures/b2e/) pairs local workerd + D1 sign-in with Central's Worker, and Node + better-sqlite3 sign-in with native Tokio Central, using B2E_CENTRAL_* inputs; pins move to Central's final artifacts. Faults: the link fault proxy (hold, drop a reply). Controlled clocks; barrier waits. Heavy runs on Sunclaw.

Kept and run against real Central: person-fleet-token.host.e2e.test.ts:198–344, fleet-cli.host.e2e.test.ts:173–243. V2 · Device login with a real session (S3, S4)

  1. Run the real CLI with --device and controlled waits; a test browser session approves the printed code on the approval page. The CLI ends signed in; the stored token's claims name a real session ID; a Fleet command succeeds against Central.
  2. Redeem the same device code again: refused. Deny a second code: CLI ends failed. Expire a third on Better Auth's clock: failed.
  3. Two memberships, through the real outer handler with only the device session: the CLI's organization/list returns both; the token names the chosen organization.
  4. A protected command gets secondFactorRequired; with no Cookie header and no injected session, the CLI posts a valid TOTP (then a recovery code) with the device session through the production handler; only that session's confirmation changes; the approving browser's is unchanged; a same-key refresh then the retried command succeed.
  5. Delete the device session: revisions bump; after Central's ACK the old token gets RefreshRequired; refresh fails; custody is cleared.
  6. Containment on a non-loopback plain-HTTP issuer (where Chrome sends no Fetch Metadata): page script posts to the device code and token routes with credentials: 'omit'; the request still carries Origin and gets 404 with no credential. Wrong build: classify by Fetch Metadata and Cookie only (this case gets the token).
  7. Containment in real Chrome: same-origin page script tries the whole device sequence (create code with the Fleet CLI client ID, approve as the signed-in person, poll the token route); every device-route call gets 404 and no response body or header contains a session token. A terminal bearer session on a non-allowlisted path is not a session there (for example get-session returns null), in both the raw and the signed form issued by Better Auth.

Wrong builds: use the OAuth device grant (token without a session, step 1 fails); admit browser requests to the device routes (step 6 sees the token in the JSON body); rely on bearer() hook order (step 4 gets 401); copy the browser's confirmation (step 4).

V3 · Revocation and delivery (S5, S7)

  • Kept: authorization-fence.host.e2e.test.ts (add, change, remove, rejoin, session fan-out), authorization-revision-drain.host.e2e.test.ts, now against real Central.
  • Drop an ACK: the row stays pending; the next Fleet call pushes it before its own work, and Central saw the push first.
  • Advance the source during an ACK: the newer revision stays pending and is pushed next.
  • The 7/8 interleaving on both stores and real Central: runner A holds a push of 7, runner B pushes 8, A's push lands and Central ACKs 8: recorded with source 8. ACK 9 with source 8: discrepancy. ACK 7 with source 8: recorded, row still pending.
  • No timer exists: with the clock advanced and no Fleet call, nothing is pushed.

Wrong builds: record an ACK above the source revision; lower a revision on discrepancy.

V4 · The owner's sync view (S6)

  1. Start with the organization row already acknowledged. Owner removes a member through the real people flow (only that person's row advances); hold Central's ACK at the fault proxy.
  2. The admin card shows “waiting for Central” although the organization row alone is synced; the lookup page, looking up the removed person by email, shows “removed; waiting for Central”.
  3. Release the ACK; refresh: “all access changes have reached Central” and “removed; reached Central”. Another organization's retained person can't be looked up this way (none).
  4. Fail the store read: unavailable. A member calling the endpoint: 403. The read issues no push (proxy counter unchanged).

Wrong builds: show synced from the source commit alone; read only the organization fence for the card (step 2 shows synced); require current membership for the person line (step 2 shows nothing); trigger delivery from the read.
