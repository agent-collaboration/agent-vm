Tokens

S1 · Issuance stays as built

From X1, X2. Issuance MUST keep its one-snapshot read and every refusal in person-fleet-issuance.ts, the fixed snapshot bound S+L (L ≤ 300,000 ms), the session and native bounds with equality expired, and the policy-mismatch refusal. A token never outlives the minimum of the three.

S2 · Refresh with the same key

From X3. Refresh MUST need the same key; another key fails without consuming the valid refresh. Each refresh is a fresh issuance from a fresh snapshot. A failed refresh clears the CLI's stored key and refresh credential.

S3 · --device login (your choice)

From X4. B (recommended), Better Auth's own device flow with a real session: --device prints a code and URL; the person approves it in a signed-in browser; the CLI polls, redeems the code once and receives a new native session; it then completes the existing PKCE authorization with that session and exchanges as today, so the token carries that session's ID. A redeemed, denied or expired code can't be redeemed again. The new session starts with no second-factor confirmation; protected actions ask for it in the CLI. With several memberships the CLI asks which organization. The session secret is kept like the refresh credential (Keychain, else memory only). A, sessionless tokens: the OAuth device grant as shipped; tokens carry no session; their revocation rests on person and organization revisions and expiry alone; the contributor and Central change to accept them. C, browser only: --device keeps saying it's not available.

S4 · Ending the session ends the device token

Under B: signing out or deleting the device session MUST bump the person's revisions exactly as for a browser session; Central refuses the old token after the ACK; refresh fails. Under A this rule is replaced by S5 alone.

Revocation

S5 · Revocation follows the real change

From X6. A role change, removal or session end MUST bump the right revisions in the same batch as Better Auth's write. A failed or zero-row write bumps nothing and claims no revoke. Rejoining keeps the same subject with a higher revision. Ending one session bumps every retained pair of that person.

S6 · The owner sees when Central has caught up

From X7. The owner (permission organization:view) MUST be able to see, for their organization, either “all access changes have reached Central” or “waiting for Central since …”, and for a looked-up member the same for that person. The answer comes from a fresh readSynchronization; missing rows count as pending; a storage failure shows unavailable. Reading changes nothing and starts no delivery. Nothing anywhere says “revoked everywhere” while pending. The view reveals no token, key or statement.

S7 · Delivery: on use, retried, no timers

From X8. After a committed change, a hint asks for delivery; before every Fleet call, all pending rows of that organization are pushed, organization row first. Only Central's acknowledgement after its commit is recorded, and only if it is newer and not above the current revision. A lost ACK stays pending. A row that moved on during an ACK is pushed again at its new revision. A discrepancy (Central acknowledged more than the source has) is reported, never repaired by lowering the source. No cron, timer or startup job.

S8 · Central's side, observed

From X9. Every r3 §9 counterexample MUST be observed on the real issuer → Rust Central path, controlled time and barriers, both pairings. The sign-in rows are B2X's to build and prove; the Central rows (DPoP, used requests, watermark, backup recovery) are Lead A's to build and B2X's to observe. The r3 table lists each with its owner.

Code and proof

S9 · Old code removed

Remove the “not available” exit for --device once the chosen device path ships (kept under C); replace the drainer's inline decisions with M1; correct the stale periodic comment.

S10 · Machines and Hegel

Row delivery (M1), the owner's sync view (M2) and the CLI's device login (M3, under A or B) MUST be closed unions with pure transitions, inline x satisfies never, effects as data run after commit, and Hegel families. Issuance's existing pure decision gets its own Hegel family. Real conditional-write races run on D1 and better-sqlite3.
